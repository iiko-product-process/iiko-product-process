## Приложение Г. Прежний формат «задача в 8 разделов»

Использовать, только если артефакт нужен именно как **PB-задача в Jira/Confluence** (а не PRD по стандарту «Формат PRD»). Основной формат скилла — PRD (см. `references/prd-format.md` и SKILL.md → «Артефакт: PRD»).

Обязательные элементы в начале файла (правило пользователя): **оглавление** (в Confluence — макрос TOC, в md — список разделов) + **номер PB-задачи** (например `PB-5671`).

### 8 разделов (порядок фиксирован)

1. **Общая информация** — PB-задача и связанные задачи, что делаем, где в интерфейсе, источник требований, статус + блок «что уже реализовано сейчас» (as-is факты для разработки).
2. **Модуль ID / фича-флаг** — модуль, ID модуля (если не известен — «уточнить»), нужен ли фича-флаг.
3. **Цель** — проблема, цель доработки, критерий успеха, для кого.
4. **US** — основная и дополнительная user story.
5. **Прототип** — макеты/HTML-прототипы + состав и поведение экрана (таблица: наименование / тип / обязательность / требования) + бизнес-логика переключателей и режимов.
6. **Критерии приёмки** — нумерованный список: что должно работать, поведение после действия, валидации, права, технические требования (ФТ и НФТ сводятся сюда, дубли сливаются).
7. **Основные сценарии** — «Сценарий N: <роль + условие>» в формате Дано / Когда / Тогда.
8. **Примечания** — всё остальное: scope и out of scope, источник правды, бизнес-правила, данные, интеграции и API (маппинг, эндпоинты), схемы и диаграммы, ошибки и edge cases, права и роли, НФТ, зависимости, открытые вопросы, декомпозиция Jira.

### Правила оформления

- **Scope / Out of scope — в «Примечания»**, отдельным разделом не выводить.
- **Не добавлять раздел самопроверки** («Что проверено», «Самопроверка по чек-листу скилла») — самопроверка внутренняя.
- **Не писать служебные пометки** вида «(решение продакта, дата)», «(Q13 закрыт)» — решения формулируются как обычные утверждения.
- **Не писать мета-шапку документа:** кто и чем составил, блок «Источник: Confluence … (page …, v17)», статус «черновик, не approved». Документ начинается с заголовка, PB-номера и оглавления; ссылки на ТЗ/Jira — внутри «Общей информации» и «Прототипа».
- **Название документа и страницы** = название доработки, без «— спецификация к разработке».
- **В шапке задачи (Confluence)** — макрос Jira (PB-номер) + макрос TOC; никакого H1 и текста «PB-5671 · iikoWeb».
- **Прототип — файлом** (вложение + download-ссылка), рядом — что в прототипе нужно поправить.
- **US — с переносами строк** (три абзаца, ведущее слово жирным): `**Как** <роль>,` / `**я хочу** <действие>,` / `**чтобы** <результат>.` Дополнительную US не добавлять, если не просили.
- **Сценарии — всегда с переносом строки**, каждый блок отдельным абзацем: `**Сценарий N: <название>.**`, пустая строка, `Дано: …`, пустая строка, `Когда: …`, пустая строка, `Тогда: …`.
- **Решения по уточняющим вопросам — в тексте задачи** (бизнес-правила, критерии приёмки, edge cases). Отдельный блок «Решения» — только для того, что не покрывается по тексту.
- **Не выводить блок «Зависимости»** и перечни макетов/файлов: зависимости — в открытых вопросах и примечаниях, прототип — только ссылкой.
- **Не писать технические примечания про отрисовку** («Отрисовка: file.png (§3); исходники — d-as-is.mmd») — просто вставлять картинку диаграммы.
- **Исходные ФТ не тащить отдельным приложением «дословно»** — сводятся в критерии приёмки, дубли сливаются.
- **Приложения с источниками и артефактами не добавлять** — ссылки на ТЗ, Jira и макеты идут в «Общую информацию» и «Прототип».
- **Декомпозиция Jira** — в «Примечания», таблица: `| # | Задача | Тип | Зависимости | Критерии приёмки |`.
