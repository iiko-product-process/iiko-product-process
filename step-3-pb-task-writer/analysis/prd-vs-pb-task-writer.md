# Разбор: `pb-task-writer` (наш шаг 3) vs стандарт «Формат PRD» + `spec-writing 2.0`

> **РЕШЕНИЕ (30.09.2026, обсуждение Павла с Александрой):** остаются **два отдельных шага**, слияния нет.
> **3а — сбор продуктовых требований** (наш скилл `pb-task-writer`): перед передачей задачи аналитику и дизайнеру или перед самостоятельной отрисовкой прототипа.
> **3б — спека для разработчиков** (скилл `spec-writing 2.0`, стандарт «Формат PRD»): минимум лишней продуктовой информации, всё для быстрой работы над задачей.
> Варианты A/B/C ниже — история обсуждения; принят вариант «два шага с чётким швом» (близко к C, но без слияния шаблонов): наш скилл доводим как этап 3а, спеку пишет spec-writing на этапе 3б.

## 1. Короткий вывод

Это **два поколения одного и того же инструмента**. Наш `pb-task-writer` — оформитель задачи в 8-блочном формате (по сути Приложение Г скилла spec-writing: «прежний формат „задача в 8 разделов“»). «Формат PRD» — новый стандарт компании (SDD-подход OpenAI): 14 разделов + доп. разделы, артефакт = статья Confluence + MD-файл, а задачи Jira — уже *следствие* (шаг 9 «Передача в разработку»).

**Сметчить можно и нужно.** Наш скилл содержит то, чего нет в PRD (Jira field map PB, ТРИЗ, НПА-блок, ICE-метрики, подтип «ресёч»), а PRD содержит обязательное, чего нет у нас (Лицензии/фича-флаги/права, User Story, Визуальное описание, Сценарии, Вопросы к разработке, НФТ, Данные, Бизнес-правила, Ошибки/edge cases).

## 2. Отличия по слоям

| Аспект | `pb-task-writer` (наш) | «Формат PRD» + `spec-writing 2.0` |
|---|---|---|
| **Артефакт** | Epic/Story сразу в Jira (PB) | PRD: статья Confluence **+ обязательный MD-файл** с тем же содержанием; после заголовка — макрос Jira + оглавление (TOC); визуальные материалы — вложениями. Jira-задачи — отдельный шаг (декомпозиция на backend/frontend/QA/…), а не сам PRD |
| **Процесс** | 7 шагов: вход → разбор → тип/поля → опрос → согласование → создание в Jira → отчёт | 9 этапов с гейтами: бизнес-постановка → as-is → to-be → системное взаимодействие → сценарии → вводные/ограничения → PRD → ревью → передача. Гейты: «Делаем/откладываем», «Новое/доработка», «Approve» и др. |
| **Модель разделов** | Блоки-таблицы (Epic/Story): Summary, Component/Labels, бизнес-контекст, AS-IS, TO-BE, состав доработок, критерии приёмки, зависимости, источники, НПА, метрики, out of scope, ТРИЗ, «важное вне формата» | 14 разделов (2, 6, 7, 8, 10 — обязательные) + доп. разделы по необходимости: данные, бизнес-правила, системное взаимодействие, интеграции (маппинг/эндпоинты), НФТ, аналитика, миграция, **ошибки и edge cases**, состав и поведение экрана |
| **Обязательное, чего у нас нет** | — | Лицензии/фича-флаги/права (ID модуля/флага, поведение при включении/выключении, роли и права), User Story «Как…/я хочу…/чтобы…», Визуальное описание (минимум 1 материал обязателен), Критерии приёмки как чек-лист под автотесты AQA, Основные сценарии (участник/предусловия/шаги/результат), «Вопросы к разработке» (обязательная группа интервью) |

| **Размер истории** | «одна законченная ценность ≈ один спринт» | **до одной недели разработки** (тест/приёмка и докатка в срок не входят); исключение — неделимая архитектурная разработка (≤10–15 задач в год на компанию) |
| **Визуальные материалы** | прототип по запросу, стиль iikoWeb (синий #448AFF и т.д.) | минимум один материал: прототип / **промпт к прототипу** / скриншот-макет; правила к каждому (демо-переключатели отделены, упрощения обозначены, промпт не зависит от истории чата) |
| **Интервью** | по одному вопросу, с вариантами и «пропустить», прогресс `~N%` | банк вопросов по 14 группам; отдельные обязательные группы: ограничения, вопросы к разработке, схемы; «как фиксировать ответы» |

## 4. Варианты «сметчить»

**Вариант A — PRD как основной артефакт, Jira как следствие (рекомендую).**
Один процесс: сбор требований один раз → **PRD** (Confluence + MD по стандарту) → **создание задач**: наш слой отвечает за PB-специфику (эпик/стори, Epic Link, Component/Labels, ТРИЗ, НПА, «ресёч»), PRD-слой — за полноту требований. Плюсы: один стандарт на компанию, задачи Jira не расходятся с PRD, наш field map и ТРИЗ сохраняются. Минусы: нужен доступ в Confluence (токен) и скилл публикации.

**Вариант B — слить в один скилл (spec-writing v3).**
Взять `spec-writing 2.0` как основу (9 этапов, банк вопросов, формат PRD) и дорастить раздел «Передача в разработку» нашими правилами PB (тип задачи, Epic Link, Component/Labels, приоритеты) + добавить опциональные разделы ТРИЗ/НПА/Метрики-ICE. Плюсы: один источник правды, нет дублирования шаблонов. Минусы: скилл станет большим; нужно согласовать с Александрой (владелец spec-writing).

**Вариант C — минимальный (быстрый).**
Оставить два скилла, но привести `pb-task-writer` к суперсету разделов PRD: добавить обязательные блоки (2, 6, 7, 8, 10, 13 + доп.), поправить размер истории на «≤1 недели», добавить шаг «опубликовать PRD (Confluence+MD)» перед созданием Jira и синхронизировать правила аппрува/чек-листы. Плюсы: не трогаем чужой скилл. Минусы: два шаблона продолжают жить рядом.
