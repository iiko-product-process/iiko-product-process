# Продуктовый процесс iiko

Канон: **https://github.com/iiko-product-process/iiko-product-process** (private, организация `iiko-product-process`).

Репозиторий продуктового процесса iiko web: скиллы по шагам, реестр скиллов, шаблон задачи и правила работы.

## Что внутри

| Папка | К чему относится |
|---|---|

| `02-hypotheses/` | Шаг 2 — гипотезы, приоритизация, ICE |
| `03-story/` | Шаг 3 — задача в Jira PB |
| `04-design/` | Шаг 4 — дизайн и прототипы: `Design-System/` и `Prototype-Guide/` — точные копии репозиториев дизайнеров, обновляются автоматически |
| `05-specification/` | Шаг 5 — спецификация (PRD) |
| `06-development/` | Шаг 6 — разработка: выгрузка задач Jira, актуализация требований |

## Где что лежит

| Место | Что лежит | Кто меняет |
|---|---|---|
| **Папка процесса в Hermes** | скиллы шагов, `skills/`, `INDEX.md`, правила, README шагов | администратор |
| **`ARTIFACTS/` внутри папки процесса** | все артефакты задач: `ARTIFACTS/<слаг>/` — карточка проблемы, гипотезы, Story, PRD, прототипы, транскрипты, встречи, журнал | сотрудник |

Сотрудник не работает с git. Папку процесса подключает администратор, обновления тоже приходят
от него; вся работа по задачам — в `ARTIFACTS` внутри этой папки. GitHub — только источник
обновлений, не рабочее место.

## Подключение папки и джобы

Подключение выполняет Hermes одной командой: получает папку процесса, ставит скиллы, создаёт
`ARTIFACTS`, обёртки задач и проверяет результат.

```bash
bash <папка процесса>/scripts/setup-all.sh --repo <папка процесса>
```

Флаги: `--repo PATH`, `--home PATH`, `--artifacts PATH`, `--dry-run` (только показать, что будет сделано).

Правила:

1. **Сотрудник не работает с git.** Папку процесса готовит и обновляет администратор — никаких
   действий в GitHub со стороны сотрудника нет.
2. **Одно рабочее место.** Скиллы и `ARTIFACTS` лежат в одной папке; сотрудник открывает её в Hermes
   и больше никуда не ходит.
3. **Артефакты — только в `ARTIFACTS`.** Ничего не дублируется в GitHub: там только скиллы и правила.
4. **Скиллы — из папки процесса.** Ставятся в `$HERMES_HOME/skills`; вручную правленная копия
   не перезаписывается и попадает в отчёт.
5. **Джобы — без агента и молчаливые.** Пустой вывод = изменений не было, уведомление не отправляется.
6. **Секреты — только в `.env`.** Токен и ключи берутся из `$HERMES_HOME/.env`, в чат и папку
   процесса не попадают.
7. **Настройка заканчивается проверкой.** `scripts/check-setup.sh` печатает чек-лист; строка «НЕТ»
   означает незакрытый шаг.

| Джоба | Расписание | Скрипт | Что делает |
|---|---|---|---|
| Обновление шага 4 | воскресенье, 09:00 МСК (`0 6 * * 0`) | `design-update-weekly.sh` | обновляет папку процесса и переустанавливает скиллы — в понедельник свежая ДС |
| Сбор наработок | пятница, 10:00 МСК (`0 7 * * 5`) | `skills-collect-weekly.sh` | новые и изменённые скиллы → архив в `$HERMES_HOME/skill-reports` |

Обе задачи создаются в Hermes в режиме «без агента»: расписание, скрипт из `$HERMES_HOME/scripts`,
пустой вывод при отсутствии изменений.

Проверить, что всё сошлось: `bash scripts/check-setup.sh` — папка процесса, токен, скиллы (37),
`ARTIFACTS`, обновление шага 4, MCP.

## Кто что делает: Гермес и сотрудник

Правило: **Гермес готовит и предлагает, сотрудник решает.** Если для шага не хватает данных, доступа
или продуктового решения — Гермес останавливается и спрашивает, а не додумывает. Выдуманных фактов,
цифр и требований в артефактах быть не должно.

| Шаг | Гермес делает | Сотрудник делает | Гермес спрашивает |
|---|---|---|---|
| 1. Проблема | Собирает формулировку и карточку, тянет данные (Matomo, Pyrus), примеры конкурентов и бенчмарки, готовит гайд интервью и итог исследования | Приносит сигнал и контекст, решает, что считать проблемой, проводит интервью, подтверждает выводы и развилку | Какой сегмент и метрика важны; есть ли доступ к источнику; подтверждена ли проблема; куда идём дальше |
| 2. Гипотезы | Формулирует гипотезы по формату, считает I · C · E с весами целей, ведёт список и прототип | Задаёт цели и веса, выбирает, что брать в работу, решает, как проверять | Какие цели компании и веса; какие гипотезы в работу; что делать с проверкой |
| 3. Story | Опрашивает по блокам, собирает Epic/Story, создаёт задачи в Jira с label `Hermes` | Отвечает на вопросы, принимает продуктовые решения, подтверждает структуру до создания | Любой пропуск в требованиях; Component и Labels; подтверждение декомпозиции |
| 4. Дизайн | Собирает прототип на ДС, проверяет и правит тексты интерфейса | Решает структуру и сценарии, проводит дизайн-ревью | Какой сценарий и экраны; можно ли отступать от ДС |
| 5. Спека | Ведёт интервью по банку вопросов, собирает PRD, публикует статью | Отвечает, проходит гейты, принимает решения по объёму | Технические детали и маппинги; гейт «делаем / откладываем» |
| 6. Разработка | Собирает статусы, готовит материал для правок, предлагает правку описания | Подтверждает правку, ведёт приёмку, решает по релизу | Любая запись в Jira — только после «да» |
| 7. Пилот | Папка создана, скиллов пока нет | — | — |

Сквозные скиллы:

| Скилл | Когда использовать | Когда не использовать |
|---|---|---|
| `task-workspace` | Начинается задача, пришёл артефакт, нужна история по задаче | Разовая работа без артефактов |
| `share-to-common` | «Добавь в общую папку», «чтобы видели все», «хочу поделиться» | Это артефакт задачи или личный черновик |
| `teams-meeting-pipeline` | Нужны итоги встреч Teams: транскрипт, решения | Встреча без записи и транскрипта |
| `meeting-transcript-summaries` | Есть транскрипт, нужны итоги и план действий | Нужен полный протокол с таймкодами — это не он |
| `notes-inbox` | Сотрудник присылает заметку или файл | Нужен поиск по уже сохранённому — `notes-search` |
| `notes-search` | Найти заметку или артефакт в вики | Нужно сохранить новую заметку — `notes-inbox` |
| `hermes-wiki` | Нужна структура артефактов: `ARTIFACTS/<слаг>/`, карточка задачи, журнал | Артефакт один и разовый — хватит `notes-inbox` |
| `process-setup` | Продакт впервые настраивает процесс: папка, скиллы, `ARTIFACTS`, cron, MCP | Настройка уже сделана — сразу к задаче |
| `git-skills-install` | После обновления папки процесса нужно обновить скиллы в Hermes | Скиллы уже свежие, изменений не было |
| `skills-inbox` | Нужно собрать наработки команды | Наработки уже в общем слое |
| `mirror-skill-to-repo` | В контейнере появился новый скилл, которого нет в репозитории | Скилл уже в каноне (это правка) или скилл личный рабочий |

Подробные таблицы «когда использовать / когда не использовать» по всем скиллам — в README
соответствующего шага.

## Как предложить идею в общий слой

Наработка, которой должны пользоваться все — скилл, шаблон, документ шага, правка общего скилла —
попадает в общий слой через администратора. Разбираться в git не нужно: скажи в чат «поделись
с командой», «добавь в общую папку», «чтобы видели все», «сделай общим» — скилл
[`skills/share-to-common/`](skills/share-to-common/SKILL.md) соберёт пакет (файл + 2–3 строки «зачем»)
и передаст администратору.

| Что | Правило |
|---|---|
| Кто отправляет | автор идеи, прямо из чата |
| Что в предложении | один скилл или одна правка + строка «зачем» |
| Что не отправляется | артефакты задач, личные черновики, токены, большие бинарники |
| Что делает админ | проверяет, вносит в общий слой, обновляет `INDEX.md` и версию |
| Что видит команда | обновлённую папку процесса в Hermes после обновления |

## История

Снимок-объединение двух процессных репозиториев (`iiko-product-process-main` + `iiko-product-process`) от 19.10.2026. Репозиторий живёт в организации `iiko-product-process`: сотрудники получают доступ только на чтение, обновления вносит администратор, артефакты задач — в Hermes wiki.

История git начинается с этого снимка — правки до 19.10.2026 в ней не отражены. С этого момента каждая правка скилла — отдельный коммит с сообщением «что изменено», поэтому откатить правку можно через `git revert` или `git checkout <sha> -- <путь>`.

## Версии

У каждого скилла в frontmatter есть `version:`. Правило: содержательная правка скилла → поднять версию (patch для уточнений, minor для новых шагов работы), новая запись в `INDEX.md` — если меняется состав скиллов.
