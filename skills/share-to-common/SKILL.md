# Share to common — предложение в общий репозиторий

Скилл закрывает одну ситуацию: у продакта появилась наработка (скилл, шаблон, документ шага,
правка общего скилла), и он говорит, что хочет поделиться ею со всеми. Дальше **не надо объяснять
ему git** — надо собрать предложение, отправить PR и сказать, что осталось за админом.

Репозиторий процесса: `iiko-product-process/iiko-product-process` (приватный, в организации
`iiko-product-process`). У продакта — **только чтение** общего репозитория, поэтому изменения
попадают туда единственным путём: форк → ветка → PR → апрув админа.

## Фразы, после которых предлагаем PR

Если в чате прозвучала любая из этих фраз — не выполнять «просто сохранить файл», а предложить:
*«Собрать из этого предложение в общую папку и отправить PR?»*

| Фраза пользователя | Что значит |
|---|---|
| «добавь в общую папку», «в общий репозиторий», «в канон» | предложить наработку команде |
| «чтобы видели все», «чтобы было у всех», «чтобы пользовалась команда» | то же, акцент на доступности |
| «хочу поделиться со всеми», «поделись с продуктами», «с командой» | то же, акцент на передаче |
| «сделай общим», «выложи в общий скилл», «сделай достоянием команды» | то же |
| «пусть это будет в процессе у всех» | изменение общего слоя процесса |
| «оформи как PR в общую папку» | прямое указание на PR |

Рядом стоящие, но **другие** фразы: «сохрани в папку задачи», «положи в задачи», «запиши в
журнал», «сделай заметку» — это личное пространство (`personal`, папка `tasks/`), PR не нужен.

## Что делать

1. **Понять, что именно уходит.** Файл, папка скилла, шаблон, документ шага или правка
   существующего скилла. Если непонятно, куда это относится — спросить: шаг 1–7 или сквозные
   `skills/`.
2. **Проверить, что это общее, а не личное.** Артефакты задач (`tasks/**`), черновики, выгрузки,
   презентации по конкретной задаче остаются на `personal` — в PR они не идут.
3. **Довести до формата репозитория:**
   - скилл — папка `step-N/skills/<имя>/SKILL.md` или `step-N/skill/SKILL.md`, плюс строка в
     `INDEX.md`, плюс поднятый `version:` в frontmatter;
   - документ шага — папка шага, и если это новый раздел — строка в README шага;
   - правка существующего скилла — только файл скилла + поднятая версия.
4. **Ветка от свежего канона**, не от `personal`:

```bash
git fetch canon
git switch -c feature/<слаг-идеи> canon/main
```

5. **Коммит и пуш в свой форк:**

```bash
git add -A
git commit -m "<что> (шаг N): <одна строка, что меняется>"
git push -u fork feature/<слаг-идеи>
```

6. **PR в общий `main`** (API или веб-интерфейс):

```bash
curl -sS -X POST \
  -H "Authorization: token $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/iiko-product-process/iiko-product-process/pulls \
  -d '{"title":"<что> (шаг N)","head":"<мой-логин>:feature/<слаг-идеи>","base":"main","body":"<тело PR>"}'
```

Тело PR — три коротких блока:

```markdown
## Что меняется
- `hypotheses/skills/<имя>/SKILL.md` — новый скилл: <одна строка>
- `INDEX.md` — строка реестра, версия 1.0.0

## Зачем
<какую работу это ускоряет или какую ошибку убирает — 1–3 предложения>

## Как проверить
<что открыть/запустить, чтобы убедиться>
```

7. **Объяснить, зачем нужна ветка и как от неё избавиться.** Ветка `feature/*` — это «контейнер»
   для PR: именно её GitHub показывает как head пул-реквеста, поэтому без отдельной ветки
   предложение не отправить. Она не заменяет `personal` и не мешает ему, если после отправки
   вернуться на свою ветку. Что сказать человеку в чате:

   > «Создал ветку `feature/<слаг>` — это упаковка для PR, в ней только файлы предложения.
   > Работать в ней не нужно: после отправки возвращайтесь в `personal`, там ваши задачи целы.
   > Ветку удалим, как только PR смержат (или сразу, если передумали).»

   Как убрать ветку после отправки PR (локально и в форке):

```bash
git switch personal                     # вернуться в свою рабочую ветку
git branch -d feature/<слаг>            # удалить локальную ветку (после мерджа PR)
git push fork --delete feature/<слаг>   # удалить ветку в форке (если не удалилась автоматом)
```

   Если PR ещё не смержен, но ветка мешает — удалять её не нужно: достаточно `git switch personal`,
   ветка останется на GitHub до мерджа. Если предложение отменено — сначала закрыть PR, потом удалить
   ветку теми же двумя командами (или кнопкой «Delete branch» в PR).

8. **Сказать в чат коротко:** что собрано, номер и ссылка PR, кто апрувит. Например:
   *«Собрал предложение: скилл `<имя>` + строка в INDEX.md. Ветка `feature/<слаг>`, PR #12 →
   ссылка. Дальше апрув и мердж — у админа репозитория.»*

## Чек-лист перед PR

- [ ] в diff нет `tasks/**`, личных черновиков, `.env`, токенов и паролей;
- [ ] у нового скилла есть строка в `INDEX.md`, у изменённого — поднят `version:`;
- [ ] относительные ссылки в изменённых файлах ведут на существующие файлы;
- [ ] нет файлов больше ~5 МБ (презентации, pdf, картинки-снимки) — если нужны, спросить отдельно;
- [ ] ветка отведена от свежего `canon/main`, а не от `personal`;
- [ ] один PR = одна идея (не «заодно поправил ещё пять скиллов»).

## Правила мерджа в общем репозитории

- **Мержит только админ**, и он же ставит апрув. Автор PR — отдельный аккаунт, поэтому ревью честное.
- **Squash and merge**: в `main` попадает один коммит с внятным сообщением, история ветки не тянется.
- После мерджа **ветка `feature/*` удаляется**, локальный `main` подтягивается: `git fetch canon`.
- Если PR устарел (в `main` уже уехали другие правки) — автор перебазирует ветку на `canon/main` и
  пушит с `--force-with-lease`; админ не мержит PR с конфликтами.
- Прямой push в `main` общего репозитория невозможен по правам: у продактов роль read.

## Если что-то не настроено

| Симптом | Что сказать |
|---|---|
| нет форка репозитория | «Форкни репозиторий (кнопка Fork) и я соберу предложение из твоего форка» |
| `push` отвечает 403 | токен без прав на форк → перевыпустить токен и обновить remote |
| нет ветки `canon`/`upstream` | `git remote add canon https://github.com/iiko-product-process/iiko-product-process.git` |
| правки случайно сделаны на `personal` | перенести файлы в ветку `feature/*` от `canon/main`, `personal` вернуть в исходное состояние |

## Чего не делать

- не отправлять PR из ветки `personal` — в него попадёт личная работа и вся история задач;
- не пушить напрямую в `main` и не просить об этом админа «по-быстрому»;
- не заливать бинарники и выгрузки «на всякий случай» — для них есть папка задачи;
- не переписывать чужие скиллы целиком: правка вносится точечно, чтобы ревью читалось.
