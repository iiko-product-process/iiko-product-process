# Mirror skill to repo — новый скилл в папку репозитория

Правило работы в репозитории `iiko-product-process`: **локальный скилл и канон в репозитории не
должны расходиться**. Как только в контейнере появляется новый скилл (или навык, который тянет на
скилл), надо не оставить его «у себя», а предложить положить в папку шага — чтобы потом отправить
в общую папку через PR.

Предложение делает чат, решение — человек: молча ничего не копируется.

## Когда срабатывает

- создан новый скилл (`skill_manage(action='create')`, `hermes skills install`, рукописный
  `SKILL.md` в `$HERMES_HOME/skills/<категория>/<имя>/`);
- пользователь говорит «сохрани как скилл», «сделай из этого скилл», «заведи навык»;
- замечено расхождение: скилл есть в контейнере, но его нет в репозитории.

Не срабатывает, если скилл уже есть в репозитории — тогда это **правка** существующего канона
(другая процедура: правка файла + поднятая `version:` + PR).

## Шаг 1. Понять, что за скилл и куда он относится

Сначала проверить реестр: есть ли имя в `INDEX.md` репозитория.

```bash
git -C <клон-канона> fetch canon
git -C <клон-канона> show canon/main:INDEX.md | grep -i "<имя-скилла>"
```

Если имени нет — новый скилл, определяем папку шага:

| Тема скилла | Куда класть |
|---|---|
| Проблема, исследования, данные, конкуренты, рынок, интервью | `research-problem/skills/<имя>/` |
| Гипотезы, приоритизация, ICE, списки гипотез | `hypotheses/skills/<имя>/` |
| Story/PB-задача, Jira-постановка, требования | `story/skills/<имя>/` |
| Дизайн, ДС, прототипы, тексты интерфейса | `design/skills/<имя>/` |
| PRD, спецификация, гейты | `specification/skills/<имя>/` |
| Разработка, статусы Jira, актуализация требований | `development/skills/<имя>/` |
| Пилот и запуск | `pilot/skills/<имя>/` |
| Сквозное (папка задачи, шаринг с командой, общие приёмы) | `skills/<имя>/` |

Тема не определяется однозначно — **спросить** одним вопросом: «к какому шагу это относится?»
Предлагать вариант по описанию скилла, но не угадывать молча.

## Шаг 2. Предложить человеку

Формулировка короткая, без объяснения git:

> «Это новый скилл. Скопировать его в репозиторий — `hypotheses/skills/<имя>/` + строка в
> `INDEX.md`? После этого смогу сразу собрать PR в общую папку.»

Если человек согласен — шаг 3. Если «пока не надо» — оставить локально и не возвращаться к вопросу
в этой сессии.

## Шаг 3. Скопировать в папку репозитория

Копируется **весь каталог скилла**, а не только `SKILL.md`: рядом часто лежат `references/`,
`templates/`, `scripts/`.

```bash
SRC="$HERMES_HOME/skills/<категория>/<имя>"
DST="<клон-канона>/<папка-шага>/skills/<имя>"
git -C <клон-канона> fetch canon
git -C <клон-канона> switch -c feature/skill-<имя> canon/main
mkdir -p "$(dirname "$DST")"
cp -r "$SRC" "$DST"
```

Проверить и привести к формату репозитория:

- в `SKILL.md` есть `name`, `description`, `version` (нет — поставить `1.0.0`), `created`;
- `description` начинается с «Use when …» и объясняет триггер;
- в скилле нет локальных абсолютных путей вида `/opt/data/...` — только относительные или
  `$HERMES_HOME`;
- нет секретов: токенов, `.env`, паролей, приватных идентификаторов.

## Шаг 4. Строка в реестре

Добавить запись в `INDEX.md` в раздел своей темы:

```markdown
| <имя> | Шаг N | `step-N-…/skills/<имя>/SKILL.md` | Use when <триггер одной строкой>. |
```

Для сквозных скиллов в колонке «Шаг» пишется `Сквозной`. Обновить счётчик в шапке файла
(`Всего скиллов: **N**`).

## Шаг 5. Проверить и отдать в PR

```bash
git -C <клон-канона> add -A
git -C <клон-канона> diff --cached --stat
```

В diff должно быть ровно два вида изменений: папка нового скилла и `INDEX.md`. Если появилось
что-то ещё — убрать из индекса и разобраться.

Дальше — скилл `share-to-common`: ветка `feature/skill-<имя>` от свежего `canon/main`, коммит
`Скилл <имя> (шаг N): <что делает>`, пуш в свой форк и PR в общий `main`. Мержит админ.

## Если скилл уже есть в репозитории

Это не новый скилл, а правка канона:

1. сравнить контейнерную и репозиторную копии (`diff`), понять, какая новее;
2. решить, что канон — репозиторий (правило репозитория: канон в `main`);
3. правку внести в репозиторий, поднять `version:` у скилла, затем тем же PR обновить контейнерную
   копию — чтобы не разъезжались.

## Чего не делать

- не копировать в репозиторий личные рабочие скиллы (заметки, дайджесты, эксперименты) — им место
  в контейнере;
- не складывать артефакты задач в папку шага: артефакты живут на ветке `personal` в `tasks/`;
- не пушить напрямую в `main` канона;
- не заводить «второй экземпляр» скилла под другим именем — сначала проверить `INDEX.md`.
