# Git skills install — все скиллы репозитория в Hermes одной командой

Репозиторий процесса содержит десятки скиллов, разложенных по папкам шагов. Гермес видит только те,
что лежат в `$HERMES_HOME/skills/`. Этот скилл закрывает разрыв: после клонирования или `git pull`
все скиллы из репозитория устанавливаются в Hermes, и дальше он подтягивает их сам.

**Когда использовать:** сотрудник подключил папку из Git, обновил репозиторий (`git pull`), или
пользователь говорит «скиллы не видны», «поставь скиллы из репозитория», «настрой всё после клона».
**Когда не использовать:** в репозитории появился один новый скилл и его надо предложить в общий
слой — это `mirror-skill-to-repo` + `share-to-common`; или нужно обновить только один скилл.

## Что делает скрипт

`scripts/install-skills-from-repo.sh`:

1. находит все `SKILL.md` в репозитории: `skills/<имя>/`, `<шаг>/skill/`, `<шаг>/skills/<имя>/`
   и плоские `<шаг>/skills/<имя>.md`;
2. отбрасывает дубли по `name:` (актуальной считается копия вне `prototyping-guide/`) и игнорирует
   папку `_inbox/`;
3. копирует каждый скилл в `$HERMES_HOME/skills/productivity/<имя>/` целиком — со всеми
   `references/`, `templates/`, `scripts/`;
4. сравнивает **каталог целиком** (SKILL.md + `references/`, `templates/`, `scripts/`) и пишет манифест
   `$HERMES_HOME/.repo-skills-manifest.tsv` (`name`, отпечаток каталога, `version`, путь в репозитории);
5. **не перезаписывает** скилл, который правили руками после установки — такой попадает в отчёт
   как «пропуск»; `--force` перезаписывает всё.

## Порядок действий

```bash
# 1. клон (если ещё нет)
git clone https://github.com/iiko-product-process/iiko-product-process.git ~/iiko-product-process

# 2. посмотреть, что будет установлено
bash ~/iiko-product-process/skills/git-skills-install/scripts/install-skills-from-repo.sh --dry-run

# 3. установить
bash ~/iiko-product-process/skills/git-skills-install/scripts/install-skills-from-repo.sh
```

Ожидаемый вывод в конце: `install-skills: всего N | установлено … | обновлено … | без изменений … | пропущено 0`.

Дальше — проверка: попросить Гермеса показать список скиллов; в нём должны быть `task-workspace`,
`share-to-common`, `pb-task-writer`, `spec-writing`, `jira-task-digest` и скиллы шагов.

После каждого `git pull` полезно повторить ту же команду: она доставит обновления, не тронув
локальные правки.

## Куда это кладётся и чем отличается от вики

| Что | Куда | Зачем |
|---|---|---|
| Скиллы (`SKILL.md`) | `$HERMES_HOME/skills/productivity/<имя>/` | чтобы Гермес их находил и применял |
| Артефакты задач | `tasks/<слаг>/…` в рабочей копии | история и структура по задаче (скилл `task-workspace`) |
| Заметки и навигация (Obsidian) | хранилище заметок | читать и искать, но не источник истины |

Скиллы не «копируются в вики»: вики — это читалка, а работающий скилл должен лежать в каталоге
скиллов Hermes. Если нужно и представление в заметках — это отдельная генерация из репозитория.

## Проверка подключения папки целиком

1. В корне репозитория есть `.hermes.md` — правила проекта подхватываются автоматически.
2. Скиллы установлены (шаг выше), `skills_list` показывает имена из `INDEX.md`.
3. Артефакты складываются в `tasks/<слаг>/`, а не в папки шагов — это проверяется по факту первой задачи.
4. `git remote -v` показывает ваш форк/клон и канон, если планируются предложения через PR.

## Типовые проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| После установки скилл не виден | Hermes не перечитал каталог | начать новый чат / перезапустить сессию |
| Часть скиллов «пропущена» | локальные копии правились руками | `--force`, если правки не нужны; иначе перенести их в репозиторий |
| Установилось меньше, чем в `INDEX.md` | скилл лежит в нестандартном месте | положить его в `skills/<имя>/` или `<шаг>/skills/<имя>/` |
| Скилл установился дважды под разными именами | в frontmatter `name:` не совпадает с папкой | привести `name:` к имени папки |
