# Git onboarding — подключение сотрудника к репозиторию процесса

Скилл ведёт сотрудника от нуля до рабочего состояния: доступ к организации, форк, клон,
правила для его Гермеса, подключение MCP и первый понятный список «что здесь можно делать».
Задача скилла — чтобы человек не разбирался в git и не спрашивал «а где это лежит».

**Когда использовать:** первый рабочий день с репозиторием, переход на новый ноутбук/контейнер,
«подключи меня к общей папке», «что тут вообще есть».
**Когда не использовать:** рутинные правки уже подключённого репозитория (там работают
`share-to-common` и `mirror-skill-to-repo`) и вопросы про конкретный шаг процесса.

## Что нужно до старта

| Что | Как проверить | Если нет |
|---|---|---|
| `git` | `git --version` | поставить git |
| `python3` | `python3 --version` | поставить Python 3.8+ |
| Аккаунт GitHub | `curl -s -H "Authorization: token $TOKEN" https://api.github.com/user` | зарегистрировать на рабочую почту |
| Токен GitHub (classic PAT) | заголовок `x-oauth-scopes` содержит `repo` | Settings → Developer settings → Tokens (classic), скоупы `repo`, `read:org` |
| Приглашение в организацию | `https://github.com/iiko-product-process` открывается | попросить админа пригласить, принять письмо |

Токен хранится **только** в переменной окружения или файле вне репозитория. В git он не попадает
никогда: ни в `.env`, ни в remote URL, который потом уедет в коммит.

### Где искать токен

Токен **всегда ищется в `.env` в каталоге Hermes**, а не в чате и не в репозитории:

- в рабочем контейнере: `/opt/data/.env` (`$HERMES_HOME/.env`);
- на ноутбуке сотрудника: `~/.hermes/.env`.

Ключ называется `GITHUB_TOKEN`; на некоторых машинах встречается `GITHUB`. Порядок действий:
проверить файл → если ключа нет, **добавить его в `.env`** (инструкция ниже) → проверить запросом.

```bash
ENV="${HERMES_HOME:-$HOME/.hermes}/.env"
set -a; . "$ENV" 2>/dev/null; set +a
TOKEN="${GITHUB_TOKEN:-${GITHUB:-}}"
[ -n "$TOKEN" ] && echo "токен найден (${#TOKEN} символов)" || echo "ключа нет в $ENV — добавить"
```

Дальше в командах используется `$TOKEN` — так скилл не зависит от имени переменной.

### Как положить токен в `.env` через интерфейс Hermes

1. Открыть десктоп-приложение Hermes (или веб-дашборд) и подключиться к своему профилю.
2. В боковом меню найти раздел с файлами Гермеса — он показывает содержимое каталога `~/.hermes`
   (в контейнере `/opt/data`). Название зависит от версии: «Files», «Hermes files», «Файлы»,
   «Настройки → Файлы». Признак нужного раздела: в нём видны `config.yaml`, `skills/`, `.env`.
3. Открыть `.env`. Если файла нет — создать новый: кнопка «+» / «New file», имя ровно `.env`
   (с точкой в начале, без расширения).
4. Дописать строку — без кавычек и без пробелов вокруг `=`:

```dotenv
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
```

   Если в файле уже есть другие ключи (`CONFLUENCE_TOKEN`, `MATRA…`), **дописывать в конец**, не
   перезаписывая их. Один ключ — одна строка.
5. Сохранить (Ctrl/Cmd+S или кнопка Save).
6. Проверить, что токен виден (в чате или терминале):

```bash
ENV="${HERMES_HOME:-$HOME/.hermes}/.env"; set -a; . "$ENV"; set +a
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: token $GITHUB_TOKEN" \
  https://api.github.com/repos/iiko-product-process/iiko-product-process   # ожидаем 200
```

7. Если в интерфейсе файлового раздела нет — открыть каталог системно: кнопка «Open folder» в
   настройках, либо `open ~/.hermes` (macOS), `xdg-open ~/.hermes` (Linux),
   `explorer %USERPROFILE%\.hermes` (Windows), и создать `.env` любым редактором.
8. Перезапускать Гермеса не нужно: `.env` подхватывается при выполнении команд. Перезапустить стоит
   только MCP-сервер, если он уже работал со старым окружением.

**Токен не вставлять в чат.** Всё, что попало в переписку, остаётся в истории сессии — токен
вставляется сразу в файл. Если токен уже засветился в чате, его нужно перевыпустить, а не «надеяться».

## Шаг 1. Организация и репозиторий

- Организация: **https://github.com/iiko-product-process**
- Канон процесса: **https://github.com/iiko-product-process/iiko-product-process** (приватный)

Что важно понять сразу:

- в организации у сотрудника роль **read** — читать можно всё, писать в `main` нельзя;
- изменения попадают в канон только через **PR из личного форка**;
- ветка `main` — общий слой (скиллы, реестр, правила), ветка `personal` — личные артефакты задач.

Проверка доступа:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: token $TOKEN" \
  https://api.github.com/repos/iiko-product-process/iiko-product-process   # ожидаем 200
```

`404` — нет доступа (приглашение не принято). `403` — токен без нужных скоупов.

## Шаг 2. Форк в личный аккаунт

Форк — личная копия, в которой можно делать что угодно; канон она не меняет.

1. Открыть канон → кнопка **Fork** → владелец — свой аккаунт → **Create fork**.
2. Форк приватного репозитория тоже приватный: чужие его не видят.
3. Проверить, что форк появился:

```bash
curl -s -H "Authorization: token $TOKEN" https://api.github.com/user/repos?per_page=100 \
  | grep -o '"full_name": "[^"]*iiko-product-process"' | head
```

Дальше клон и два remote:

```bash
git clone https://github.com/<мой-логин>/iiko-product-process.git
cd iiko-product-process
git remote add upstream https://github.com/iiko-product-process/iiko-product-process.git
git remote -v          # origin — мой форк, upstream — канон
git fetch upstream
```

**Имена remote.** В этой инструкции и в `CONTRIBUTING.md` принято: `origin` — ваш форк,
`upstream` — канон. В служебных клонах админа те же два адреса могут называться `fork` и `canon` —
это другая подпись, а не другая схема. Ориентир один: `git remote -v` в вашем клоне, дальше
используйте те имена, которые уже есть (в примерах ниже — `origin`/`upstream`).

## Шаг 3. Изучить репозиторий (и не гадать)

Порядок чтения — от общего к частному. Гермес проходит его сам и пересказывает сотруднику
коротко, без простыней.

| Что | Зачем |
|---|---|
| `README.md` | что за репозиторий, какие шаги, кто что делает, правила PR |
| `.hermes.md` | правила для Гермеса внутри этой папки (подхватываются автоматически) |
| `INDEX.md` | реестр скиллов: имя, шаг, путь — единственный источник «что вообще есть» |
| `CONTRIBUTING.md` | форк → ветка → PR → мердж: как предложить свою наработку |
| `step-N-…/README.md` | что делает шаг, что лежит в папке, когда какой скилл брать |
| `skills/*/SKILL.md` | сквозные скиллы: папка задачи, шаринг с командой, зеркалирование скиллов |

Быстрый обзор без чтения всего:

```bash
git ls-tree -r --name-only upstream/main | wc -l          # сколько файлов
git show upstream/main:INDEX.md | head -40                # реестр скиллов
git show upstream/main:README.md | sed -n '1,60p'         # что за процесс
```

**Чек-лист «я понял репозиторий»** (Гермес подтверждает вслух или в чате):

- [ ] какие шаги есть (1–7) и что делает каждый;
- [ ] где лежат скиллы и где артефакты задач (это разные ветки);
- [ ] как предложить изменение (`feature/*` → PR → апрув админа);
- [ ] что мой `personal` — личное, в канон он не уходит;
- [ ] какой скилл брать под мою задачу (см. таблицы «когда брать» в README шага).

## Шаг 4. Правила для Гермеса сотрудника

У каждого сотрудника Гермес должен **сначала смотреть в репозиторий, а потом отвечать**. Иначе он
начинает импровизировать там, где уже есть готовый скилл, шаблон или формат.

Создать в корне клона `.hermes.md` (Hermes читает его автоматически, приоритет выше `AGENTS.md`,
работает и в подпапках репозитория):

```markdown
# Правила работы с репозиторием iiko-product-process

- Канон: https://github.com/iiko-product-process/iiko-product-process (роль read), мой форк — origin.
- Перед ответом по процессу проверить репозиторий: `INDEX.md` (какие скиллы есть),
  `step-N/README.md` (что делает шаг, когда какой скилл брать), `skills/*/SKILL.md` (сквозные скиллы).
  Если в репозитории есть подходящий скилл — подтянуть его, а не сочинять заново.
- Процесс: `git fetch upstream` → ветка `feature/*` от `upstream/main` → PR → апрув админа.
- Артефакты задач — только в `tasks/<слаг>/…` на ветке `personal`, в `main` их не бывает.
- Не выдумывать цифры, требования и решения: нет данных — спросить сотрудника.
- Каждая задача в Jira, созданная с Hermes, помечается label `Hermes`.
```

Обновлять этот файл при изменении правил: он живёт локально у сотрудника, в канон не уходит.

## Шаг 5. Подключить MCP (по одному, по мере надобности)

MCP — это доступ Гермеса к рабочим системам. Без них он умеет только читать репозиторий.

| MCP | Что даёт | Без него |
|---|---|---|
| **Atlassian (Jira + Confluence)** | создавать и читать Epic/Story, статусы, комментарии, публиковать PRD | задачи и спеки оформляются вручную, статусы не собрать |
| **Matomo** | уники, устройства, воронки, разрешения, почасовые срезы | анализ данных шага 1 только по выгрузкам сотрудника |
| **Pyrus** | обращения, реестры, формы | нет источника реальных сбоев |

Порядок для каждого: получить токен → прописать в окружение → проверить одним запросом →
убедиться, что инструмент виден Гермесу. Токены — вне репозитория.

```bash
# пример проверки Jira (Atlassian MCP использует тот же токен)
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $JIRA_TOKEN" \
  "https://jira.iiko.ru/rest/api/2/myself"
```

Чек-лист MCP:

- [ ] токены в окружении, не в git;
- [ ] каждый MCP отвечает на пробный запрос;
- [ ] в чате видно, что инструмент доступен (Гермес перечисляет, что умеет);
- [ ] если токена нет — записать в список «что попросить у админа», не блокировать онбординг.

## Шаг 6. С чего начать работу

Два входа — выбирает сотрудник, оба рабочие:

**А. Сначала инфраструктура.** Подключить MCP (шаг 5), проверить доступы, настроить `.hermes.md`.
Подходит, если задача ещё не пришла.

**Б. Сразу задача.** Выбрать по типу работы:

| Что нужно | Скилл | Шаг |
|---|---|---|
| Разобраться, проблема это или готовая задача | `problem-validation` | 1 |
| Сформулировать проблему, собрать данные и конкурентов | `problem-formulation`, `data-analysis`, `competitor-analysis` | 1 |
| Гипотезы и приоритизация | `iiko-hypotheses` | 2 |
| Оформить Epic/Story в Jira | `pb-task-writer` | 3 |
| Собрать прототип на дизайн-системе | гайд `step-4-design/prototyping-guide/` + `ux-writing-iiko` | 4 |
| Написать спеку (PRD) | `spec-writing` | 5 |
| Статусы разработки и актуализация описаний | `jira-task-digest`, `requirement-actualization` | 6 |

Первый шаг в любом случае — **завести папку задачи** скиллом `task-workspace` (ветка `personal`),
чтобы артефакты не расползались по чатам.

## Шаг 7. Вывести сотруднику «что здесь есть»

После изучения репозитория — короткая сводка, не список из 21 строки. Собрать её из `INDEX.md`
и README шагов:

1. прочитать `INDEX.md`, сгруппировать скиллы по шагам;
2. взять из `step-N/README.md` одну строку «что делает шаг»;
3. вывести в чат таблицей **по шагам**, а не по скиллам:

```markdown
| Шаг | Что делает | Ключевые скиллы |
|---|---|---|
| 1. Проблема | формулировка, данные, конкуренты, исследования | problem-validation, problem-formulation, data-analysis, interview-guide |
| 2. Гипотезы | формулировка, ICE, приоритизация | iiko-hypotheses |
| 3. Story | Epic/Story в Jira PB | pb-task-writer |
| 4. Дизайн | прототипы на ДС, тексты | ux-writing-iiko, iiko-design-system |
| 5. Спека | PRD по стандарту | spec-writing |
| 6. Разработка | статусы, актуализация | jira-task-digest, requirement-actualization |
| 7. Пилот | папка создана | — |
```

4. закончить вопросом: **«С чего начнём — подключим MCP или берём задачу?»** и предложить
   конкретный следующий шаг (например, «давайте заведём папку задачи по вашей теме»).

Если `INDEX.md` недоступен (нет клона) — тот же список собирается обходом `step-*/README.md`;
врать про «есть такой скилл» нельзя.

## Постоянная привязка, а не разовая настройка

Онбординг не считается завершённым, пока «токен прописан»: после разовой связки Гермес в новой
сессии снова ничего не знает про канон. Нужны три уровня, и все три проверяются.

| Уровень | Что даёт | Как проверить |
|---|---|---|
| **Скиллы в контейнере** | скиллы из репозитория скопированы в `$HERMES_HOME/skills/productivity/<имя>/` и доступны без клона | `skills_list` показывает имена; `grep -m1 '^version'` совпадает с каноном |
| **Правило в памяти** | Гермес помнит, что канон существует, и сам сверяется с ним перед ответом по процессу | в новом чате: «какие скиллы есть в репозитории процесса?» — должен ответить по `INDEX.md`, а не «не знаю» |
| **Синхронизация** | клон и установленные скиллы не расходятся с каноном (pull-only, без автопуша) | `git -C <клон> log -1` = последний коммит канона; версии скиллов совпадают |

Установка скиллов из репозитория (по одному, а не «всё подряд»):

```bash
REPO=<клон-канона>
for d in "$REPO"/skills/*/ "$REPO"/step-*/skill*/; do
  name=$(basename "$(dirname "$d")"); [ "$name" = "skills" ] && name=$(basename "$d")
  [ -f "$d/SKILL.md" ] || continue
  grep -q "^name:" "$d/SKILL.md" || continue
  mkdir -p "$HERMES_HOME/skills/productivity/$name"
  cp -r "$d/." "$HERMES_HOME/skills/productivity/$name/"
done
```

Правило в память (одна запись, а не абзац):

> Канон процесса — `iiko-product-process/iiko-product-process`. Перед ответом по процессу свериться
> с `INDEX.md` и README шага, скиллы брать оттуда, артефакты — в `tasks/` на ветке `personal`.

Синхронизация — **только в одну сторону, из канона в контейнер**: `git fetch` +
`git merge --ff-only`, затем копирование изменившихся скиллов по манифесту (sha1 + версия).
Автоматический пуш из контейнера в общий репозиторий не настраивается никогда: изменения уходят
только через PR человеком.

**Минимальная проверка «привязка есть»:** начать новый чат и попросить «покажи, какие скиллы есть
в репозитории процесса и какой из них брать для Story». Если Гермес отвечает по канону без
напоминаний — привязка работает; если начинает угадывать — не хватает уровня 1 или 2.

## Регулярный сбор новинок: среда и пятница

Разовая настройка забывается — поэтому проверка новых скиллов и наработок ставится на расписание:
**каждую среду и пятницу**. Задача собирает то, что появилось в контейнере, и отправляет в **свой
форк**; в общий репозиторий ничего не уходит и PR не создаётся.

Скрипт лежит рядом со скиллом: `scripts/weekly-fork-sync.sh`. Что он делает:

1. берёт скиллы, которые появились или менялись **с прошлого запуска** (по отметке времени
   `$HERMES_HOME/.weekly-fork-sync-last`) — а не всё, что установлено;
2. отбирает только процессные: имя по шаблону (`iiko-…`, `pb-…`, `spec-writing`, `task-workspace`,
   `share-to-common` и т. п.) или тег `iiko` в frontmatter — иначе в форк уехали бы посторонние
   скиллы вроде `pdf`, `arxiv`, `xlsx`;
3. те, которых ещё нет в клоне, копирует в `<клон>/skills/_inbox/<имя>/` — отдельная папка, чтобы не
   ломать структуру шагов и не править `INDEX.md` автоматически;
4. коммитит и пушит **только в свой форк** (`origin`, ветка `personal`);
5. если новых нет — молчит (пустой вывод = нет уведомления от cron).

Первый запуск ничего не отправляет: он только ставит отметку времени (baseline) — иначе в форк
уехало бы всё, что уже установлено. Сбросить отметку вручную: `--reset-state`.

Что он **не** делает: не создаёт PR, не пушит в общий репозиторий, не перезаписывает существующие
скиллы, не коммитит при грязной рабочей копии (сообщит и выйдет).

Проверить вручную перед постановкой в cron:

```bash
# показать, что будет отправлено, ничего не меняя
bash "$HERMES_HOME/skills/productivity/git-onboarding/scripts/weekly-fork-sync.sh" \
  --repo "$HOME/iiko-product-process" --branch personal --dry-run

# первый запуск (или после долгого перерыва) — только поставить baseline
bash "$HERMES_HOME/skills/productivity/git-onboarding/scripts/weekly-fork-sync.sh" \
  --repo "$HOME/iiko-product-process" --reset-state
```

Создание cron-задачи (Гермес делает это сам по просьбе сотрудника):

| Параметр | Значение |
|---|---|
| Расписание | `0 10 * * 3,5` — среда и пятница, 10:00 по местному времени |
| Скрипт | `<HERMES_HOME>/skills/productivity/git-onboarding/scripts/weekly-fork-sync.sh` |
| Аргументы | `--repo <клон> --branch personal` |
| Режим | `no_agent` — скрипт сам формирует текст, модель не нужна |

## Типовые проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| `404` на репозиторий | приглашение в организацию не принято | принять письмо или попросить приглашение заново |
| `403 Write access to repository not granted` | push в канон (у сотрудника read) или токен без `repo` | пушить в свой форк, проверить скоупы токена |
| `Push rejected (fetch first)` | в каноне появились новые коммиты | `git fetch upstream && git rebase upstream/main` |
| `fatal: Need to specify how to reconcile divergent branches` | локальная ветка разошлась с форком | `git pull --rebase` или явный `git merge` |
| форк не создаётся | уже есть репозиторий с таким именем | переименовать свой старый репозиторий, затем форкнуть |
| `Cannot assign … permission of read` | попытка выдать read в репозитории личного аккаунта | read возможен только в организации |
| «в `personal` видны все папки» | в форке `personal` — это канон + артефакты, а не только `tasks/` | это норма: шаблон задач смотрите в `tasks/`, скиллы — в `main` |

## Чего не делать

- не пушить в `main` канона (прав нет, и это не случайность);
- не коммитить артефакты задач в `main` — они живут на `personal`;
- не хранить токены в репозитории и не вставлять их в URL remote, который попадёт в историю;
- не клонировать чужие форки «посмотреть» — для этого есть PR и доступ админа;
- не пересказывать сотруднику весь репозиторий: короткая сводка по шагам + предложение начать.
