# Git onboarding — подключение сотрудника к репозиторию процесса

Скилл ведёт сотрудника от нуля до рабочего состояния: доступ к организации, форк, клон,
identity, правила для Гермеса, MCP и первый понятный список «что здесь можно делать».
Задача — чтобы человек не разбирался в git и не спрашивал «а где это лежит».

**Когда использовать:** первый рабочий день с репозиторием, новый ноутбук/контейнер,
«подключи меня к общей папке», «что тут вообще есть».
**Когда не использовать:** рутинные правки уже подключённого репозитория (`share-to-common`,
`mirror-skill-to-repo`) и вопросы про конкретный шаг процесса.

## Шаг 0. Замер до начала

Скрипт лежит рядом со скиллом, зависимостей нет:

```bash
python3 skills/git-onboarding/scripts/check_onboarding.py --repo .
```

Печатает `ok` / `warn` / `БЛОКЕР` по каждому пункту и возвращает 1, если есть блокеры:
git, ключ, токен, доступ к канону, `origin`/`upstream`, ветка `personal`, правила агента.
Токен не показывает. Без клона — запускать без `--repo`.

## Шаг 1. Организация и доступ

- Организация: **https://github.com/iiko-product-process**
- Канон процесса: **https://github.com/iiko-product-process/iiko-product-process** (приватный)
- У сотрудника роль **read**: читать можно всё, писать в `main` нельзя; изменения — PR из форка.
- `main` — общий слой (скиллы шагов, `INDEX.md`, правила), `personal` — личные артефакты задач.

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: token $GITHUB_TOKEN" \
  https://api.github.com/repos/iiko-product-process/iiko-product-process   # ожидаем 200
```

Как читать ответ:

| Код | Что это значит |
|---|---|
| 200 | доступ есть, идём дальше |
| 401 | токен неверный, протух или не экспортирован |
| 403 | токен без скоупов `repo` / `read:org` |
| 404 | приглашение не принято **или** запрос без токена к приватному репозиторию |

`404` с рабочим токеном при пустом списке приглашений — это не поломка токена, а отсутствие
членства: приглашение с ролью `read` выдаёт админ организации. Разбор по шагам (членство,
приглашения, скоупы) — `references/troubleshooting.md`.

## Шаг 2. Форк, клон, identity

Форк — личная копия, канон она не меняет. Форк приватного репозитория тоже приватный.

1. Канон → кнопка **Fork** → владелец — свой аккаунт → **Create fork**. В форке сразу обе ветки.
2. Клон по SSH: так токен не попадает ни в URL, ни в историю. Нет SSH-ключа — `ssh-keygen -t ed25519`,
   публичный ключ в GitHub → Settings → SSH and GPG keys, проверить `ssh -T git@github.com`.

```bash
git clone git@github.com:<ты>/iiko-product-process.git
cd iiko-product-process
git remote add upstream git@github.com:iiko-product-process/iiko-product-process.git
git config user.name  "<Имя Фамилия>"      # без этого первый коммит падает
git config user.email "<рабочая почта>"
git fetch upstream
git remote -v                              # origin — форк, upstream — канон
```

HTTPS-вариант вместо SSH: `git clone https://github.com/<ты>/iiko-product-process.git` плюс
credential helper; токен в URL не вставлять никогда.

Проверить, что форк виден (пусто в ответе — форка нет):

```bash
curl -s -H "Authorization: token $GITHUB_TOKEN" \
  'https://api.github.com/user/repos?per_page=100&affiliation=owner' | grep -o '"full_name": "[^"]*iiko-product-process"'
```

## Шаг 3. Ветки и первый цикл работы

| Ветка | Что в ней | Кто пишет |
|---|---|---|
| `main` канона | скиллы шагов, `INDEX.md`, `README.md`, `CONTRIBUTING.md` | админ через PR |
| `main` форка | копия канона, обновляется `git pull upstream main` | сотрудник |
| `personal` | `tasks/_шаблон` и папки задач `tasks/<слаг>/` | сотрудник, в канон не уходит |
| `feature/*` | предложение в общий слой | сотрудник → PR → мердж админом |

```bash
git checkout personal                     # личное пространство; ветка уже есть в форке
cp -r tasks/_шаблон tasks/моя-задача      # новая задача из шаблона
git add tasks/моя-задача && git commit -m "Задача: ..." && git push origin personal
```

Предложение в канон:

```bash
git checkout main && git pull upstream main        # свежий main, не недельной давности
git checkout -b feature/мой-скилл
git add -A && git commit -m "Скилл <имя> (шаг N)"
git push -u origin feature/мой-скилл               # дальше Compare & pull request → base main
```

Канон уехал вперёд, пока шла работа:

```bash
git fetch upstream && git rebase upstream/main
git push --force-with-lease origin feature/мой-скилл   # только своя feature-ветка
```

`--force-with-lease`, не `--force`. Ветку `personal` не PR-им никогда. Один PR — одна идея;
новый скилл без строки в `INDEX.md` и без поднятого `version:` не мёржится.

## Шаг 4. Изучить репозиторий (и не гадать)

Порядок чтения — от общего к частному; Гермес проходит его сам и пересказывает коротко.

| Что | Зачем |
|---|---|
| `README.md` | шаги процесса, кто что делает, как начать |
| `.hermes.md` | правила для Гермеса в этой папке (подхватываются автоматически) |
| `INDEX.md` | реестр скиллов: имя, шаг, путь — единственный источник «что вообще есть» |
| `CONTRIBUTING.md` | форк → ветка → PR → squash-мердж |
| `step-N-*/README.md` | что делает шаг, что лежит в папке, когда какой скилл брать |
| `skills/*/SKILL.md` | сквозные скиллы: папка задачи, шаринг, зеркалирование, онбординг |

```bash
git ls-tree -r --name-only upstream/main | wc -l          # сколько файлов
git show upstream/main:INDEX.md | head -40                # реестр скиллов
git show upstream/main:README.md | sed -n '1,60p'         # что за процесс
```

**Чек-лист «я понял репозиторий»** — подтвердить вслух или в чате:

- [ ] какие шаги есть (1–7) и что делает каждый;
- [ ] где скиллы (`main`) и где артефакты задач (`personal`) — это разные ветки;
- [ ] как предложить изменение (`feature/*` → PR → мердж админом);
- [ ] `personal` в канон не уходит;
- [ ] какой скилл брать под конкретную задачу (таблицы «когда брать» в README шага).

## Шаг 5. Правила для Гермеса

У каждого сотрудника Гермес должен **сначала смотреть в репозиторий, а потом отвечать**. Иначе он
импровизирует там, где уже есть скилл, шаблон или формат.

В этом репозитории `.hermes.md` уже лежит в корне и приезжает с клоном: свои правила дописывать в
него нельзя, это общий файл. Второй `.hermes.md` рядом заводить бессмысленно — Hermes грузит
**один** источник за сессию (приоритет `.hermes.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules`),
поэтому дубль молча выключит командные правила.

Если скилл применяется к репозиторию **без** `.hermes.md` — создать файл из
`references/hermes-md-template.md` и убрать его из-под коммита:

```bash
printf '.hermes.md\n' >> .git/info/exclude
git status --short          # файла быть не должно
```

## Шаг 6. MCP — по одному, по мере надобности

| MCP | Что даёт | Без него |
|---|---|---|
| **Atlassian (Jira + Confluence)** | Epic/Story, статусы, комментарии, публикация PRD | задачи и спеки оформляются вручную |
| **Matomo** | уники, устройства, воронки, почасовые срезы | анализ данных шага 1 только по выгрузкам |
| **Pyrus** | обращения, реестры, формы | нет источника реальных сбоев |

Порядок для каждого: токен → переменная окружения → проверка одним запросом → виден ли
инструмент Гермесу. Токены — вне репозитория.

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $JIRA_TOKEN" \
  "https://jira.iiko.ru/rest/api/2/myself"          # 200 — токен живой
```

Нет токена — записать в список «что попросить у админа» и не блокировать онбординг.

## Шаг 7. С чего начать и что здесь есть

Два входа, оба рабочие: **А** — сначала инфраструктура (MCP, доступы, правила), **Б** — сразу
задача. В любом случае первый шаг — папка задачи (`task-workspace`, ветка `personal`).

Сводку «что здесь есть» собрать из `INDEX.md` и README шагов и вывести **по шагам**, а не списком
из 22 строк:

| Шаг | Что делает | Ключевые скиллы |
|---|---|---|
| 1. Проблема | валидация, формулировка, данные, рынок, интервью | problem-validation, problem-formulation, data-analysis, interview-guide |
| 2. Гипотезы | формулировка, ICE, приоритизация | iiko-hypotheses |
| 3. Story | Epic/Story в Jira PB | pb-task-writer |
| 4. Дизайн | прототипы на ДС, тексты | ux-writing-iiko, iiko-design-system, iiko-ds-components |
| 5. Спека | PRD по стандарту | spec-writing |
| 6. Разработка | статусы, актуализация описаний | jira-task-digest, requirement-actualization |
| 7. Пилот | папка создана, скиллов пока нет | — |
| Сквозные | папка задачи, шаринг, зеркалирование, онбординг | task-workspace, share-to-common, mirror-skill-to-repo, git-onboarding |

Список сверять с `INDEX.md`: скилла нет — так и сказать, а не подставить похожий по названию.
`INDEX.md` недоступен — обходить `step-*/README.md` и `skills/*/SKILL.md`.

Закончить вопросом «с чего начнём — подключим MCP или берём задачу?» и конкретным шагом.

## Финальный чек-лист

- [ ] `check_onboarding.py` без блокеров
- [ ] `GET /repos/iiko-product-process/iiko-product-process` → 200
- [ ] форк создан и приватный, `git remote -v` = `origin` + `upstream`, `git fetch upstream` проходит
- [ ] `user.name` / `user.email` заданы, первый коммит не падает
- [ ] ветка `personal` на месте, шаблон задачи скопирован
- [ ] правила агента: канонный `.hermes.md` на месте, второй не заведён
- [ ] `INDEX.md` прочитан, сводка «что здесь есть» выдана
- [ ] MCP: подключено / отложено с записанным списком
- [ ] сотрудник понимает: `main` — общее, `personal` — личное, PR — через `feature/*`

## Чего не делать

- не пушить в `main` канона (прав нет, и это не случайность) и не PR-ить `personal`;
- не коммитить артефакты задач в `main` — они живут на `personal`;
- не хранить токены в репозитории и не вставлять их в URL remote, который попадёт в историю;
- не заводить свой `.hermes.md` рядом с канонным;
- не клонировать чужие форки «посмотреть» — для этого есть PR и доступ админа;
- не пересказывать сотруднику весь репозиторий: короткая сводка по шагам + предложение начать;
- не выдавать отсутствующий скилл за существующий.
