# Итоги встречи из транскрипта → план действий → заметка

Триггеры: «проанализируй расшифровку / собери итоги встречи», вложенный `.docx`/`.txt`/`.md` из авто-ASR,
«опиши план действий, который обсуждали в конце», следом «создай заметку и положи в мой репозиторий».
Пользователь — продакт/аналитик iiko (веб-приложение), встречи про дизайн, аналитику, процессы.

## Шаги

1. **Прочитать транскрипт целиком.** `read_file` сам извлекает текст `.docx` — конвертеры не нужны.
   Файлы на 700+ строк приходят с `truncated: true`: дочитывай вторым вызовом с `offset`. Не анализируй по первой половине.
   Первым делом вытащи **шапку файла** — `<имя>-<ГГГГММДД_HHMMSS>-Расшифровка|Запись собрания`, дату и длительность
   (`N мин N с`): по ней вложение сопоставляется со встречей (шаг 7), а не по имени файла.
   Если `read_file` объявил `.docx` «binary» / файл не находится по имени (NFD-нормализация macOS) —
   рабочие приёмы в `references/notes-vault-delivery.md`.
2. **Восстановить искажённые ASR-термины** по контексту (см. `references/asr-term-glossary.md`) и **явно оговорить это в ответе**:
   одной строкой «расшифровка автоматическая, термины восстановлены по контексту: «гид» = гит-репозиторий, …».
   Без такой сноски пользователь считает ошибки распознавания твоими.
3. **Собрать итоги по структуре** из `templates/itogi-vstrechi.md`:
   шапка (дата, время, длительность, участники + кто ведущий, источник) →
   контекст и цель → «что уже есть у участников» (таблица кто→что) → **Решения** →
   **План на этот спринт** по людям → **Чек-лист ответственных** → организационное →
   порядок этапов → связи-вики-ссылки.
   Секция «в конце встречи» (распределение ролей и времени) — ядро запроса: вытаскивай её отдельным разделом,
   а не растворяй в общем тексте.
4. **Отдать результат текстом в чат** (структурированный markdown, не пересказ процесса работы)
   и файлом `$HERMES_HOME/Итоги_встречи_<тема>_<ГГГГ-ММ-ДД>.md` — в имени файла обязательно дата.
5. **Дождаться правок и применить их дословно.** Пользователь присылает блок «Правки» с готовыми формулировками:
   вставляй их как есть, не переписывай своими словами, не «улучшай» структуру, которую он задал.
   Обнови файл целиком (`write_file`, не патч по кусочкам) и покажи в чате только изменённые разделы.
6. **По запросу «создай заметку в мой репозиторий»** — положить итоги в vault: `references/notes-vault-delivery.md`
   (путь `$HERMES_HOME/ARTIFACTS`, frontmatter `kind: встреча` → `Встречи/<topic>/`, скрипты раскладки и индексации).
   Заметка получает ту же структуру + чек-лист ответственных с владельцами и сроками.
7. **Несколько вложений сразу / фрагмент + полная запись одной встречи.** Сопоставляй файлы со встречами по шапке
   (дата + длительность), а не по номеру в имени: нумерация выгрузок из Teams бывает обратной хронологии
   («(3)» — более ранняя встреча, чем «(2)»). Если пришёл короткий обрывок (десятки секунд) и следом полная запись
   той же встречи — **не создавай вторую заметку**, перепиши существующую целиком (`write_file`), добавив в шапку
   обе ссылки на `raw/…` и пометку, что первый файл был обрывком. Разные встречи → разные заметки (по дате).
8. **Длинные расшифровки (40+ мин, 40–50 тыс. знаков) — параллельные сабагенты + обязательная сверка.**
   Контракт на выжимку, рецепт проверки и грабли — `references/delegating-long-transcripts.md`.
   Ключевое: сабагент возвращает markdown **в ответе** (не пишет файлы сам), а перед сохранением ты **грепаешь
   исходную расшифровку** по именам/числам/терминам из его выжимки. Итоги встреч остаются твоей ответственностью:
   выдуманный термин в заметке всплывёт как факт.

## Pitfalls

- **Сомнительные термины сабагента сверяй с расшифровкой, а не принимай на веру.** Реальный случай: в выжимке
  появилось «ЕГИС/ЭГОИС», а в тексте было «э г а и с» / «егэса» / «эгоизд» → это ЕГАИС. Чужую реконструкцию
  либо подтверждай по исходнику, либо возвращай пометку `[?]` — «красивое» название хуже честного пропуска.
- **Не перераспределяй задачи между участниками** по своей логике. Пункт принадлежит тому, кто о нём говорил и
  кто взял его в работу. Это самая частая правка пользователя: проверка гипотезы и работа с гайдами ушли Андрею,
  хотя по смыслу «просились» Максиму/Полине.
- Формулировки «можно оставить на потом», «на последних этапах», «отдельный трек» — это часть плана, а не мусор.
  Такие пометки теряются при пересказе и потом всплывают как недоговорённости.
- Сохраняй количественные оценки (2–3 ч/нед, ~6–9 ч на спринте) и итоговые формулировки («Итог: …»).
- Не объединяй разделы «Решения» и «План»: решения — что договорились, план — кто и что делает.
- При пересборке заметки не пересоздавай её в другой папке/под другим slug — иначе в vault останется дубль.
- Если встреча породила изменения в уже сохранённом артефакте (файл в чате + заметка в vault) — правь оба, не оставляй расхождение.
- Никаких выдуманных деталей: если что-то в транскрипте неразборчиво («тайски», «антисуда доктрин»), не додумывай смысл —
  оставь как есть или помечай «уточнить».

## Связанные навыки

- `notes-inbox` (user-owned) — общий приём заметок в vault: frontmatter, категории, конвертация вложений. Он источник истины
  по раскладке; здесь — только специфика итогов встреч и проверенные детали механики репозитория.
- `teams-meeting-pipeline` — про автоматический пайплайн Microsoft Teams (Graph-подписки), не про ручной разбор расшифровки.

## Файлы навыка

- `references/asr-term-glossary.md` — таблица «что в расшифровке → что на самом деле» (гид→git, фильма→Figma, эгоизд→ЕГАИС, …).
- `references/notes-vault-delivery.md` — доставка в `$HERMES_HOME/ARTIFACTS`: раскладка, скрипты, NFD-имена, извлечение docx.
- `references/delegating-long-transcripts.md` — контракт для сабагентов на длинных расшифровках + рецепт сверки их выжимок.
- `references/iiko-team-roster.md` — кто есть кто на встречах (спикеры, подрядчики, заказчики) и какие встречи повторяются.
- `templates/itogi-vstrechi.md` — структура итогов встречи для чата и для заметки.
