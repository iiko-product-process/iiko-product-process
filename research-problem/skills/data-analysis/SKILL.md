# Действие 2: анализ данных (шаг 1)

Второе из четырёх действий шага 1 (навигатор — скилл `problem-validation`). Задача — дополнить проблему данными: подтвердить/уточнить её числами или показать, что данных нет и что нужно собрать.

## Принцип

Сначала **план** («что проверяем и зачем»), потом запросы к источникам. План строится **от проблемы**: какая метрика или срез лучше покажет её наличие (вместо «что здесь плохо работает?» — «какая метрика покажет проблему?»).

**Источники предлагаются, а не выдаются списком.** Сначала спроси пользователя, что у него уже есть для изучения (данные, выгрузки, доступы), и предложи подключить недостающее — например, Matomo к его аккаунту по его токену. Чего нет — не настаивай: зафиксируй, что данных нет, и двигайся дальше.

## Источники

| Что можно изучить | Что даёт | Как с этим работать |
|---|---|---|
| **Matomo** | уники, устройства, воронки, сегменты, глубина прокрутки | предложить подключить к аккаунту пользователя по его токену: мост `matomo-mcp-setup`, дальше — запросы по скиллу `matomo-web-analytics` |
| Опросы CSI/NPS (открытый текст) | причины «почему» | спросить, есть ли выгрузка или доступ; есть — разбираем, нет — не настаивать |
| Обращения в поддержку | реальные сценарии сбоев | Pyrus (MCP) + скилл `pyrus-api-direct`: выгрузка по теме проблемы |
| Технические данные (скорость загрузки, время ответа) | техническое подтверждение | в большинстве случаев источник — Matomo; могут быть и другие данные — уточнить у продакта |
| Дашборды Киры (продуктовая аналитика) | продуктовые срезы | попросить доступ, если он есть; если нет — не обращать внимания |
| Разметка событий и воронки | проверка, что нужные события собираются | через Matomo; свериться со схемой разметки |
| Заметки и расшифровки встреч | качественные подтверждения | скилл `notes-search`: цитаты с датой и тайм-кодом |

## Порядок

1. Спроси пользователя, **что есть** для изучения по этой проблеме: какие данные, выгрузки и доступы уже под рукой.
2. Предложи подключить недостающее (Matomo — по токену пользователя) и собери список проверок: метрика → зачем → где смотрим.
3. Прогони запросы (MCP/скиллы), сохрани срезы.
4. Сегментируй: проблема может быть только у новых пользователей, конкретных тарифов, городов и т.п.
5. Результат — в карточку проблемы, раздел **«4. Данные: что проверяли и что нашли»**: таблица `Метрика | Значение | Источник | Дата | Статус (проверено / нужно проверить)`.
6. Строка в `журнал.md` задачи.

## Жёсткие правила

- Числа — только из источников; каждый факт со ссылкой на систему/выгрузку и датой.
- Чего нет — помечай «нужно проверить» (и предложи, где взять); выдумывать данные нельзя.
- Один срез — одна строка в таблице; не дублировать.

## Промпт-рамка (для поиска в данных)

```
Контекст: [продукт, раздел, сегмент].
Проблема: [формулировка].
Проверяем: [список метрик/срезов].
Ограничения: только [Matomo / Pyrus / …]; каждая цифра — с датой и источником.
Формат: таблица «метрика | значение | источник | дата».
```

## Связанные скиллы

`matomo-web-analytics` · `pyrus-api-direct` · `notes-search` · координатор — `problem-validation`.
