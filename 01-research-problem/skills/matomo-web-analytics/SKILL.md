# Matomo Web Analytics

Instrumenting and querying Matomo (self-hosted / on-premise web analytics). Covers the JS tracker, event-based funnels, Custom Dimensions, Content Tracking, the Reporting API, and the premium Funnels plugin.

## When to use

- Designing/adding tracking instrumentation (events, custom dimensions, content groups, user ID) for a web app or SPA.
- Building funnels — overall or per-item (per-product, per-section, per-app).
- Querying/exporting reports via the Matomo Reporting API.
- Any "can Matomo do X natively?" question — answer from docs, not memory.
- Админ-задачи инстанса: транзакционная почта (SMTP, сброс пароля, инвайты), пользователи и их права, email-отчёты, плагины, OAuth/SSO → `references/matomo-admin-and-email.md`.
- Tag Manager: «зачем MTM, если трекинг уже кодом», «что можно поправить без релиза фронта», поля тега Matomo (customUrl, customDimensions sticky, goal/event; **поля User ID нет** → Custom HTML `setUserId`), ограничения и ловушки внедрения → `references/tag-manager-mtm.md`.
- Подключение Hermes к Matomo на другой машине / передача доступа коллеге, недельная cron-джоба по разделам → отдельный скилл **`matomo-mcp-setup`** (stdio-мост + `--selftest`, дерево разделов `pages_tree.py`, шаблон промпта джобы, API-кулинарная книга).
- «Таблица разделов/страниц с локализацией» (URL ↔ отображаемое название) → `references/section-localization.md`.
- «Редкие пользователи: зачем заходят, почему уходят, где подцепить» (удержание W1→W2, lift по модулям) → `references/rare-users-and-retention.md`.
- «Кто заходит с мобильного, а кто с компа», «на каком устройстве проверять гипотезу об обрыве», «% пользователей с устройства по сегментам» → `references/device-breakdowns.md`.

## Core concepts

- **Event** = 4 fields: Category (required), Action (required), Name (optional, recommended), Value (optional, MUST be numeric). JS: `_paq.push(['trackEvent', category, action, name, value])`. Case-sensitive (`Video` ≠ `video`); names live forever — use a fixed enum, never ad-hoc strings.
- **Events report hierarchy**: Category → Action → Name drill-down. This is the free way to get an overall funnel (per Action) AND per-item counts (per Name) without exports.
- **Metric caveat**: in the Events report, Visits are counted per event action — one visit with 3 events is counted in each step. For funnels always use **nb_uniq_visitors**, never nb_visits.
- **Custom Dimensions**: scopes Visit (last value in visit wins) and Action (attached per pageview/event). 5–15 per scope depending on version; deactivate, don't delete. JS: `_paq.push(['setCustomDimension', id, value])`; HTTP param `dimensionN`. Action-scope CDs support **URL Extractions** (regex, exactly one capture group) — auto-populate from URL with zero JS changes; explicit setCustomDimension is more robust when routes vary.
- **Content Tracking**: impressions / interactions / interaction rate keyed by Content Name/Piece. Use for "shown vs clicked" on content blocks/cards; events are the better tool for funnels.
- **User ID**: `uid` HTTP param / `setUserId` — enforces identity, enables `userId` segment, makes funnel uniqueness cross-device.

## Recommended pattern: event-based funnel (free)

1. Category = fixed product area (e.g. `Marketplace`).
2. Action = fixed enum of funnel steps (kebab-case, never renamed).
3. Name = **stable item identifier** (slug/catalog key — NOT the display name; display names change and break history).
4. Value = optional numeric (price, count).
5. Add an Action-scope Custom Dimension (e.g. `AppId`) set before each event and before trackPageView on item pages → segment ANY report by item, combine with other segments (restaurant, date, userId).
6. Overall funnel in UI: Reports → Events, rows = steps. Per-item: drill into an Action row (Name subtable) or apply a segment.
7. Export per-item funnel: `method=Events.getAction&secondaryDimension=eventName&flat=1` → rows "action × name" with nb_events / nb_uniq_visitors / sum_event_value. Methods: `Events.getCategory/getAction/getName`; secondaryDimension ∈ {eventAction, eventName, eventCategory}.
8. Funnel math caveat: reports give step counts, not per-visitor step ORDER. Step N→N+1 conversion ≈ uniq visitors(N+1) / uniq visitors(N) — a fair approximation for B2B flows with rare repeat conversions. Strict sequences (skips, backfills, required steps) need the Funnels plugin.

## Premium Funnels plugin

- Paid (InnoCraft EULA, 30-day trial, Matomo 5.x). Unlimited funnels/steps; steps match URL/path/title **or Event Category/Name/Action** (equals/contains/starts/ends). Standalone since 5.1.0 (no goal required). Configure & fetch via HTTP Reporting API. Segments apply to funnel reports, including funnel-step segments.
- Per-item funnels: one shared funnel + segment "Event Name = item", or per-item funnels created via API.
- Same event instrumentation serves both free and premium paths — upgrading requires no re-tagging.

## Pitfalls

- **Задержка появления данных в отчётах (замер на iiko-инстансе 2026-09, Matomo 5.11):** два слоя. (1) Сырые данные — **1–5 с**: Журнал посещений, «В реальном времени», `Live.getCounters`/`Live.getLastVisitsDetails` читают `log_*` сразу после `matomo.php` (замер: `lastActionDateTime` = текущая минута). (2) Агрегаты отчётов (в т.ч. **События**) — пересчёт архива по запросу, и только если архив старше `time_before_today_archive_considered_outdated` = **900 с (15 мин)** в дефолте Matomo 5.x (`config/global.ini.php`; week/month/year/range = `-1` → падают на то же значение; в UI это General Settings). Наблюдённая картина: архив посчитан ~14:56 → 14:57–15:11 цифры заморожены (сырой трафик шёл, ~70 визитов/мин) → 15:11–15:12 пересчёт (последний час в архиве — текущий). Практический ответ «сколько ждать»: **до ~15 мин** для сегодняшних данных; если в инстансе включена только cron-архивация (`browser_archiving_disabled_enforce=1`), обновление строго по крону (типично 1 час), и тогда дольше. Инструмент замера: `cd $HERMES_HOME/matomo_weekly && python3 check_archive_freshness.py [минут] [интервал_с]` (печатает моменты пересчёта архива vs сырой слой).
- **Сегмент ≠ «свежий обход»:** запрос с `&segment=` пересчитывает архив независимо от порога — если цифры с сегментом «свежее» бессегментных, это не баг данных, а разница путей архивации.
- Old doc URLs 404 → use `matomo.org/guide/` (see Docs map).
- Don't rely on the URL alone for item identity: URL analysis breaks on route changes and can't segment events. Event Name + CD is the robust combo.
- Double-firing: guard dev StrictMode / double-clicks (disable buttons, single handler); acceptance criteria usually require zero duplicate tracking requests.
- SPA: call trackPageView on every route change (history listener); set a unique readable `document.title` before tracking so Pages reports are usable.
- Test-stand exclusion (dev/demo chains) is a site-config/segment/proxy concern — separate from instrumentation.
- **Token hardening**: some deployments reject `token_auth` in the URL or headers ("Unable to authenticate… required to be sent as a POST parameter") — retry with the token as a POST form param before concluding the token is invalid.
- **Uniques vanish on aggregate periods**: `period=range` and Devices/Resolution/VisitTime rollups often return NO `nb_uniq_visitors` (or null), while `period=week` DOES return `nb_uniq_visitors` + `nb_users`. For weekly unique counts use `period=week` with the week-start date; daily uniques via `period=day`.
- **`period=day` multi-date responses** come back as a LIST (rows with `label=date`) OR a DICT keyed by date with empty days as `[]`/`{}` — parse both, skip empty days (a day with zero data may be missing entirely).
- Daily uniques summed over a week exceed the weekly unique-visitor count — expected (the same visitor counts in each day); the week's unique comes only from the week/range aggregate.
- **Share-of-device/resolution comparisons across differently-complete weeks are confounded**: weekdays are desktop-heavier than weekends in B2B, so a week missing Mon–Wed (tracking rollout) looks artificially "more mobile". Compare shares only over IDENTICAL day-ranges in both weeks (`period=range`, same weekdays — e.g. Fri–Sun in each week), never whole-week vs partial-week shares. Worked recipe: `references/reporting-api-quirks.md` (Tracking-start section).
- Before interpreting hourly/"working day" reports, verify the site timezone via `SitesManager.getSiteFromId` → `timezone` field (iiko prod: Europe/Moscow → hourly data already MSK).
- **Aggregate-hourly hides where the sag actually is — drill day × hour.** A week-level hourly profile showed a flat −4…−9% in *every* hour (reads as "nothing specific"), while the same report split per weekday (`period=day` per day, or an `hourly_by_day` payload) showed one whole weekday sagging −11…−21% in *every working hour*, another partly, and nothing >−10% on Thu–Sun. Diagnose with day×hour rows, not the hourly profile; and make sure the prose matches the per-day drop markers a dashboard renders (those chips are day×hour, so a headline "no hours drop >10%" can contradict the chart next to it). **Уточнение (прогон 2026-09-28):** расхождение даёт порог по объёму, которого у чипов НЕТ — аналитик отсекает мелочь (напр. часы <300 визитов), а `gen_dips_by_day` рисует всё с Δ ≤ −10%, поэтому в выводе проскочило «в рабочие часы просадок нет», тогда как в приложенном файле лежали чипы `Чт 03:00 −28%` и `Ср 02:00 −13%`. Порядок: собрать дашборд → прочитать `<!--BLOCK:dips-->` из готового HTML → перечислить в сообщении ровно эти часы (+ оговорка про объёмы/нерабочее время) → только потом формулировать «просадок нет».
- **Ступенька ≠ тренд: недельную дельту модуля проверяйте по дням, прежде чем объяснять.** Рабочий кейс 2026-09-21 (iiko prod): недельные «till-shifts −16,8%» и «forecast +80,1%» — это один шаг 15.09 (till-shifts 8 233 → 7 065 визитов/день, forecast 1 354 → 2 566), причём в тот же день шагнули ещё inventory, lite-stock, configuration, «Справочники», «Планы подготовки», workflow-config, marketplace, abc-xyz. Синхронный одноразовый сдвиг по многим модулям = релиз/раскатка/изменение разметки — подавать как гипотезу и просить сверить выкатку, а не как рост или уход аудитории. Разбор — `scripts/detect_module_steps.py` (сравнивает Вт–Вс, чтобы понедельник после отчётного дня не раздувал дельту).
- **Статические блоки дашборда и JS-вид расходятся — проверяйте оба.** Текст инсайтов и чипы просадок вшиты в HTML (нужны для предпросмотра без JS), но страничный JS перезаписывает `#dip-chips` представлением выбранного дня: в браузере видно один день (по умолчанию Пн), хотя в файле лежат все семь. Не делать вывод «чипы потерялись» по `outerHTML`/snapshot — читать сам файл (region `<!--BLOCK:dips-->`) либо `document.querySelectorAll('.insight li').length` для инсайтов.
- **`DevicesDetection.getType` не отдаёт `nb_uniq_visitors`** (ни range, ни month — только nb_visits/nb_actions), поэтому «% пользователей с устройства» из него не считается: доли по разделам — по визитам, по пользователям — только через Live `showColumns="userId,deviceType"` + `user → Counter(device)`. И `filter_limit=-1` + `period=range` + сегмент на 300 uid даёт **HTTP 500** (падает на 5-й пачке) — массовый съём только `period=day` + `filter_limit=1000` + `filter_offset`. Рецепт и цифры (iiko: редкие 87,6% комп vs регулярные 66,5%/32,8% моб) — `references/device-breakdowns.md`. **Для обрывов доля визитов не годится:** нужны `abandoned_share_%` (из каких устройств состояли обрывы) и `abandoned_%` внутри устройства. iiko 01–13.10.2026: инвентаризация — 53,1% обрывов мобильные, 55,4% против 39,9% на компе; закупки — 88,3% обрывов на компе, 22,1% против 2,7% на мобильном; документы — 85% на компе, но доли равны (60,7/59,9). Не писать «мобильный хуже» по доле визитов — только по cross-tab.
- **Ranked subtables are truncated even at `filter_limit=-1`**: `Resolution.getResolution` / `DevicesDetection.getType` on iiko weekly returned exactly 15 rows summing ~72% of site visits. Compute shares over the returned sum (and say "топ-15"), never over `totals.visits`.
- **Route renames and per-visit-hit divergence are tracking-quality signals, not usage trends.** A section vanishing while a new one appears the same period is a rename (iiko: `/employees` → `/user-account`, 5 237 → 6 212 visits) — report it as needing an alias so history stays comparable. Likewise a module whose hits/visit jumps between weeks (`/inventory` 5.33 → 2.25) usually means frontend `trackPageView` behavior changed; flag it for the module team instead of reading it as a usage surge. **Продолжение (iiko, прогон 2026-09-28):** у `/inventory` ряд hits/visit 5,33 → 6,86 → 4,47 — выброс откатился даже ниже прежней нормы, а `/navigator` падает монотонно третью неделю (3,36 → 3,02 → 2,78). Одинаковый симптом «просмотры падают» означает разметку в первом случае и сценарий раздела во втором — различать по форме ряда, а ряд проверять запросами к СТАРЫМ периодам (`scripts/verify_page_trend.py`), потому что `data.json` держит только W1/W2 и «унаследованный» ряд из прошлого `insights.json` иначе остаётся неподтверждённым. И когда падает site-wide `actions`, раскладывать дельту по страницам в абсолюте: в том прогоне `/inventory` дала −38 719 из −106 121 (36% всего падения), топ-15 — 60%, т.е. «действия упали −7,2%» было нормализацией одного модуля, а не уходом аудитории.
- Page-titles QA via `Actions.getPageTitles`: module-level shared `document.title` collapses many routes into one row (e.g. "Purchase" with tens of thousands of hits), and pages without any title show as "Page Name not defined" — both are tracking-quality signals worth reporting to the product side. See `references/reporting-api-quirks.md` for worked iiko recipes (POST-only auth, week-vs-range uniques, tracking-start partial weeks, and a local stdio MCP bridge when a remote MCP endpoint's auth is incompatible with MCP transport).
- **SPA-раздел «склеен в один index.html»**: если все экраны раздела пишутся как `/<module>/index.html`, это хэш-роутинг — фрагмент `#…` срезан при ingest (у сайта `keep_url_fragment: 0`). Report-side это НЕ лечится: данных об экранах в базе нет (проверять titles/events/content-groups, прежде чем обещать постраничный отчёт). Фиксы: `setCustomUrl` нормализованным путём из конфигурации роутера (динамические сегменты схлопывать, иначе кардинальность) либо per-site `keep_url_fragment=1` (только статичные хэш-роуты). Диагностика + сниппеты: `references/spa-hash-routing.md`.
- **"By page" vs "by module" — и почему `flat=1` НЕ даёт разбивку по ресторанам (перепроверено 2026-09-21)**: `Actions.getPageUrls` и с `flat=1`, и без него возвращают **строки уровня пути**: за день 185 строк, за неделю 106–109 (не сотни), и Σ визитов/хитов по строкам у flat и non-flat **совпадает до единицы** (проверка: 75 092 визита/208 870 хитов за 16.09 в обоих режимах). То есть `flat=1` НЕ добавляет измерение «поддомен ресторана» — прежний вывод «~200 строк = host×module» был ошибкой чтения (200 строк — это столько путей с трафиком). Различие только в форме: non-flat — дерево (верхний уровень = модуль, `label` без `/`, есть `idsubdatatable`), flat — плоский список тех же путей (`label` = `/navigator/index.html`). Для «по разделам» берите non-flat.
- **Поле `url` строки — ОДИН примерный хост, а метрики строки — сумма по ВСЕМ ресторанам.** В строке `/navigator/index.html` за 16.09 было `url=https://sedelice-co.iikoweb.ru/navigator/index.html`, `nb_visits=18 534`; при этом сегмент `pageUrl=@/navigator` за тот же день = 17 317 визитов (это тот самый путь по всем поддоменам), а сегмент по хосту `pageUrl=@sedelice-co.iikoweb.ru` = всего 511 визитов. Вывод: атрибутировать трафик хосту из строк `getPageUrls` нельзя (18 534 приписано ресторану, у которого 511), и «сложить nb_hits по url» = получить вымышленные цифры по ресторану. Разбивка `label` — это всегда ПУТЬ, даже при `flat=1` и за диапазон.
- **Реальные цифры по хосту — только сегментом**: `segment=pageUrl=@<host>` (+ `VisitsSummary.get`/`Actions.*`). Перечислить хосты через `getPageUrls` невозможно: в поле `url` за день видно лишь ~59 хостов (по одному примеру на путь). Для положительного вывода («с хоста X есть трафик») сегмент обязателен, для отрицательного («тестовых доменов нет») `getPageUrls` не доказательство.
- **Список хостов по разделу и пары «поддомен × uid» — только из сырого слоя (Live), не из агрегатов.** Перепроверено 05.10.2026 (iiko, `/internal-couriers`): из поля `url` строк `Actions.getPageUrls` вышло «5 хостов», а `Live.getLastVisitsDetails` по дням (`segment=pageUrl=@<раздел>`, `showColumns="userId,visitServerDate,visitLocalTime,actions,actionDetails"`, `filter_limit=-1`, день=3,5 МБ/3 с) нашёл **129 хостов, 307 uid, 322 пары (host,uid)** за 30 дней — и 60+ хостов уже в одном дне. Per-host сегменты (`pageUrl=@<раздел>;pageUrl=@<host>`) дают точные цифры, но стоят ~60 с на запрос — только для точечной сверки (hatimaki: 847 сегментом против 814 в выгрузке, Δ≈4% из-за межхостовых визитов). Инвентарь идентификаторов авторизованного пользователя (числовой `userId`, `visitorId`=sha1(userId)[:16], `visitIp`, CD1 Store ID в каждом действии `dimension1`; отсутствуют CRM/ФИО/роли/названия), рецепт выгрузки и рабочие цифры — `references/userid-and-host-export.md` + `scripts/export_section_host_uid.py`.
- **Сравнение недель/дней, когда внутри одной из них переключили базу идентичности: брать только одинаковые дни на новой базе и обязательно через `period=range`.** Прогон 12.10.2026 (iiko prod): W1 = 05–11.10 (вся новая база), W2 = 28.09–04.10 **смешанная** — 28–30.09 старый счётчик, 01.10 ~11:00 МСК включение `user_id` + склейки, 02–04.10 новая база. Агрегаты дают «−77% уников, −53% визитов, +4,8% действий, авторизованных −0,02%», а сопоставимые Пт–Вс — «уники −6,1%, визиты −2,9%, действия −1,0%». Визуально ровно как «падение трафика», физически — смена базы. Приём: `Actions.getPageUrls`/`VisitsSummary.get` с `period=range&date=2026-10-02,2026-10-04` против `2026-10-09,2026-10-11`; контроль — половина дня после перелома против того же дня другой недели (01.10 12:00–23:00 против 08.10 12:00–23:00 = −7,6%, тогда как утро 01.10 = −71%). Недельные средние (`действий/визит 18,55 против 8,30`, `время 1246 против 738 с`) внутри смешанной недели — артефакт; на сопоставимых днях они совпадают (20,2 против 19,8; 1 280 против 1 282 с). В регулярном отчёте это закрывается `mark_comparable_days.py` в `$HERMES_HOME/matomo_weekly/` (пишет `meta.comparable_weekdays`, чипы просадок строятся только по сопоставимым дням).
- **Недельная дельта визитов почти всегда составная — раскладывать на ядро / приток / отток, иначе вывод «вырос трафик» может быть про смену состава.** Приём (прогон 26.10.2026: визиты +3,2%, уники +4,4%): `UserId.getUsers` с `period=range&filter_limit=-1` за обе недели → два словаря `{uid: nb_visits}`, пересечение = ядро. Итог: 6 255 общих uid (73% от W2) дали 79 757 против 78 603 визитов (+1,5%), одновизитные 2 624 против 2 420 (+8,4%), только-W1 2 745 uid / 6 327 визитов, только-W2 2 345 / 4 747 — и ядро +1 154 + приток 6 327 − отток 4 747 = +2 734 при фактических +2 700. **Всегда проверяй, что разложение сходится с фактической дельтой** (расхождение >2% = перепутаны диапазоны или период). Читать так: ядро ±2% ⇒ те, кто работает, работают столько же, а вся дельта в притоке/оттоке; ядро и одновизитные в РАЗНЫЕ стороны ⇒ смена состава аудитории (см. кейс 19.10.2026: ядро −0,7% при униках −9,9%), в одну ⇒ рост. Готовый скрипт — `scripts/weekly_cohort_delta.py` (заодно печатает `timezone` сайта).
- **Наличие `nb_uniq_visitors` по страницам НЕ признак «старая/новая база» — оно плавает между неделями в любую сторону.** 26.10.2026 в одном ответе `fetch_matomo.py` у W1 (19–25.10) уникальные по страницам были, а у W2 (12–18.10) — `null`, хотя обе недели уже на новой разметке. Поэтому: (а) не делать вывод «сменилась база» по наличию колонки, (б) сравнивать страницы/разделы по `nb_visits`, (в) в тексте отчёта оговаривать «доли считаны по визитам».
- **Non-flat дерево `Actions.getPageUrls` = агрегат по разделу — единственный способ сравнить разделы недель с разной разметкой путей.** Верхний уровень (`navigator`, `till-shifts`, `inventory`) суммирует все подроуты, поэтому сравним с прежними «склеенными» метками (`/navigator/index.html`). Кейс 12.10.2026: на сопоставимых Пт–Вс все разделы в пределах ±12% (till-shifts +8,1%, external-menu +4,4%, navigator −6,6%, Σ верхнего уровня −5,4%), кроме `inventory` −30,2%. Разбор по экранам решает трактовку: просадка равномерна по ВСЕМ экранам модуля (list −29,0%, count/:id/zones −32,3%, zones/:id −27,1%, настройки −32…−36%) при росте глубины визита (просмотров/визит 5,31 → 5,87) = приходит меньше людей, а не «сломался экран». Обратная картина (падение одного экрана при ровных соседях) = разметка/релиз конкретного экрана. **Сумма по разделу (перепроверено 26.10.2026): удобнее `flat=1&filter_limit=-1` + суммирование строк по префиксу `/section`, а НЕ ручной обход дерева.** В `expanded=1` `nb_visits` родителя уже равен сумме детей, а `label` детей идут БЕЗ ведущего слэша (`inventory` → `count` → `:id` → `zones`) плюс рядом живут строки-двойники с другим типом матча (`/list` = точный URL одного поддомена против `list` = префикс по всем хостам) — наивный flatten даёт двойной счёт и «0 визитов» по разделу, если искать `startswith('/inventory')`. Рабочий результат того прогона (flat=1, суммы по префиксу): navigator 65 211, till-shifts 25 269, call-center 22 230, external-menu 20 800, dashboard 17 796, purchase 14 701, inventory 12 613.
- **Compound-сегменты (`a;b`) — ~60 с каждый**: массовые циклы по десяткам хостов на них не строить (упирается в таймаут, а пользователь считает это зависанием — кейс «10 минут уже думаешь!!» был именно сверкой сегментами). Для точных per-user цифр внутри сегмента брать `nb_visits`/`nb_actions` строки `UserId.getUsers` (сегменты он принимает: 309 строк против 15 103 без), но не `sum_daily_nb_users` — эта метрика считается шире сегмента.

- **Segments via MCP `matomo_raw` can silently not apply**: an `extra: {flat:1, segment:"pageUrl=@/nomenclature"}` call returned rows from ALL modules (unfiltered), while the same query as a direct POST (fetch_matomo.py api()-pattern) worked. Rule: if a segmented report looks too broad or a flat result contains foreign modules, don't trust it — switch to direct POST and cross-check one day against the daily dashboard. For production numbers go straight to direct POST.
- **UserCountry (страны)**: `nb_uniq_visitors` exists only per-day (`period=day`); `period=week`/`period=range` return `sum_daily_nb_uniq_visitors` (sum of daily uniques, double-counts multi-day visitors) instead. Country = GeoIP by IP; «Unknown»/`xx` = geo lookup failed (check proxies/internal IPs, don't dismiss). Module segment must be `pageUrl=@/<module>` (contains) — the non-flat row's own `pageUrl=^https://analytics.iiko.ru/<module>` does NOT cover restaurant subdomains where the module actually lives. Worked recipe + prototype layout: `references/user-country-reports.md`.
- **`label` в `Actions.getPageUrls` — всегда ПУТЬ (`/navigator/index.html`), хост там не искать** (даже при `flat=1` и за диапазон). Поиск `.test` / `localhost` / доменов по `label` всегда даёт ложный вывод «тестовых доменов нет» — на эти грабли уже наступили в отчёте пользователю. Хост виден только как пример в поле `url` строки — и это ОДИН хост на путь, метрики строки относятся ко всем ресторанам (см. выше): складывать `nb_hits` по `url` нельзя. Хост-специфичные цифры — только сегментом `pageUrl=@<host>`.
- **«Данные не приходят» ≠ фильтр Matomo**: прежде чем утверждать это, проверить серверную фильтрацию — `SitesManager.getSiteFromId` → `exclude_unknown_urls` (0 = по домену НЕ отсекает, значит любой хост попадёт в базу и «если стенд шлёт сюда — его видно») и `SitesManager.getSiteUrlsFromId` (список URL сайта; у iiko там только сам Matomo-домен). Плюс `[Tracker] exclude_requests` живёт только в конфиге сервера — по API не читается, но может молча выкидывать запросы (напр. `e_c==…`).
- **Скриншот/домен из чужого стенда не доказывает состояние прод-инстанса**: в prod-Matomo iiko нет ни одного хоста `*.iikoweb.test` (ни по `url`, ни сегментом `pageUrl=@.test`) — визит с `nscpjn.iikoweb.test` снят с другого инстанса Matomo. Внутренние тест-стенды в prod приходят как `*.iiko.iwr.lan`, dev-машины — как `localhost:4200` / `vm-*:4200` / `192.168.x.x:4200`, демо-стенды — как `*-demo*.iikoweb.ru`, `*testov*`, `*demorms*`.
- **Почта и UI-админка токеном недоступны**: суперюзерский токен на ЛЮБОЙ не-API запрос → HTTP 500 «Embedding widgets with super-user token authentication is not allowed» (`core/API/Request.php::checkTokenAuthIsNotLimited` бросает `Widgetize_TooHighAccessLevel` до проверки всех allow-флагов — GET/POST неважно). SMTP (`[mail]` в `config.ini.php` / General Settings → Email settings), self-service сброс пароля, Diagnostics, список плагинов — только человек с паролем в UI или файл на сервере. Не обещать «настрою почту через API». Токеном доступны отчёты и пользователи (`inviteUser` / `resendInvite` / `generateInviteLink` / `updateUser(login, password)`). Детали + OAuth-ландшафт: `references/matomo-admin-and-email.md`.
- **`mail()` запрещён на хосте ⇒ вся транзакционная почта мертва**: Matomo 5.x шлёт через PHPMailer 7 из `core/Mail/Transport.php`; при пустом `[mail] transport` используется PHP `mail()` (ошибка «Невозможно запустить функцию mail()» при сбросе пароля). SMTP-транспорт его не требует — но включается только в UI/конфиге.
- **«Через сколько событие/визит с прода появится в Matomo?» — отвечать двухслойно, а не одной цифрой.** Сырой слой (Журнал посещений, «В реальном времени», Live API) — секунды; а вот все отчёты (События, Действия, любые агрегаты) читают **архив**, который пересчитывается по порогу/крону, поэтому свежее событие появляется в отчёте не сразу. Замерено на iiko: архив «за сегодня» стоял ≥10 мин без обновления при живом сыром трафике (~70 визитов/мин) — пересчёт НЕ на каждый запрос; дефолт Matomo 5.x `time_before_today_archive_considered_outdated=900` (15 мин, перекрывается в UI → General Settings). Периодичность пересчёта **не угадывать** — измерять. Режимы архивации (`browser_archiving_disabled_enforce`, range-периоды), замеры, UI-рецепт проверки и квирк ключей `Live.getCounters`: `references/report-freshness-and-archiving.md` + `scripts/check_archive_freshness.py`.
- **Ежедневный дайджест (`daily.json`) — доли считать от `totals.visits`, не от Σ визитов по разделам.** Из-за кросс-доменной агрегации (сегмент по модулю) Σ visits по 59 разделам ≈ вдвое больше итога дня, а Σ уников больше итога дня. Проверять также полноту дня (`Σ hourly.visits == totals.visits`) и сравнивать не только с прошлым днём, но и с **тем же днём прошлой недели** — иначе разовая просадка читается как тренд. Базовые цифры дня сравнения достаются даже если его прогон упал (`## Error: Request timed out`): они лежат в строке «К прошлому дню (ДД.ММ, Хх): уники X → Y» **следующего** отчёта — `grep -n "ДД.ММ" $HERMES_HOME/cron/output/d1d15d50171d/*.md`. `actions/visit` не читать как «объём работы»: раскладывать на (действия/уника) и (визиты/уника) — падение при неизменном «на уника» означает больше коротких возвратов. **`hits` — уже агрегат модуля с подстраницами, это готовый «вес действий»** (16.10.2026: `call-center` 73 074 hits против 24 339 у собственной строки `/call-center`; `purchase` 38 003 против 25 621 у `/purchase/order-list-v2`) — hits соседних строк не складывать, иначе раздел посчитан дважды. Σ hits по всем строкам ≈ `totals.actions` (16.10: 253 917 против 257 660, Δ≈250 не атрибутировано), так что hits/actions = доля дня, а hits/uniq = «действий на человека»; именно так видно, что весь прирост действий дня дал один модуль (call-center 314 на чел. против 245 днём раньше при общем +10,6%). Число строк в `daily.json` плавает 60–72 (72 при 15.10, 65 при 16.10) — печатать фактическое «Все N страниц», а не «~59» из старого описания скилла. Пайплайн, схему `daily.json` и формат сообщения см. `references/daily-digest-cron.md`, разбор — `scripts/daily_digest_stats.py`.
- **Уники/визиты вдвое вниз при плоских `nb_users` и `nb_actions` = смена базы идентичности, а не потеря трафика.** Кейс 01.10.2026 (iiko prod): `daily.json` дал уники 21 323 → 11 248 (−47%) и визиты 44 054 → 22 788 (−48%), тогда как `nb_users` 4 660 → 4 573 (−1,9%), `nb_actions` 223 274 → 220 246 (−1,4%), а к тому же дню недели (24.09, Чт) действия даже +10,3%. Локализация сегментами: визиты без uid 28 786 → 8 933 (−69%), действия с uid 118 048 → 191 174 (+62%) — склейка сессий при раскатке uid (`enable_userid_overwrites_visitorid`): один человек на телефоне и десктопе = один visitorId. Правило: сравнивать дни по `nb_users` и `nb_actions`, окно «к прошлому дню» в сообщении подавать с явной оговоркой; побочные артефакты (действия/уника 10,5 → 19,6; «визит удлинился»; ночная доля 5,3% → 12,9%; D 60% → 63%) — следствие упавшего знаменателя, а не поведение. Детектор — `scripts/detect_identity_step.py`, разбор — `references/identity-change-detection.md`.
- **`daily.json.hourly` — разбивка по СЕРВЕРНОМУ часу** (`VisitTime.getVisitInformationPerServerTime`), а не по браузерному времени посетителя. Базис проверять через `SitesManager.getSiteFromId` → `timezone` (iiko: Europe/Moscow ⇒ сервер и сайт в МСК, часы в отчёте = МСК). `VisitTime.getVisitInformationPerLocalTime` даёт другую картинку (кейс 01.10.2026: час 0 — 599 против 728, час 14 — 1 183 против 1 010) — для дайджеста его брать нельзя, часы разъедутся с прошлыми отчётами. И не читать `segment` строк `PerServerTime` (`visitStartServerHour==(N+21)%24`) как сдвиг часов: таблица уже в времени сайта.
- **`uniq`/`visits`/`hits` бывают `null` у мелких модулей** (01.10.2026: recipe-manage, kiosk-management, payment-gateways, purchase-mobile, error) — любой скрипт разбора обязан нормализовать None → 0 до сортировки, иначе `TypeError: bad operand type for unary -: 'NoneType'`; `scripts/daily_digest_stats.py` это чинит с 02.10.2026.
- **Один раздел может лежать в таблице двумя строками** (`user-profile` 1 857 уник. и `/user-profile` 887 уник., 01.10.2026) — подавать как «нужен алиас, иначе рвётся история раздела», не складывать молча.
- **«Есть ли в Matomo данные по разделу X?» — искать по ключевым словам сразу в трёх отчётах:** `Actions.getPageUrls` (flat=1, `label`+`url`), `Actions.getPageTitles`, `Events.getCategory/getAction/getName` — регекспом по названию раздела и его англо/русским вариантам. Кейс 08.10.2026: «Accounts & Transactions» нашёлся как `/directories/accounts-transactions/accounts` (839 визитов/30 дн.) + `transactions/:accountId` (136), заголовок «Счета и проводки» (119 визитов), **отслеживается только с 01.10.2026** (до выката подроутов экраны сливались в `/directories/index.html`, а title проставлялся лишь у 11 визитов за сентябрь). В ответе обязательно указывать дату старта данных: «нет истории до <дата>» — иначе пользователь сравнивает WoW там, где сравнимого периода нет. Событий в разделе нет — если нужны действия внутри (создал счёт, провёл транзакцию), это отдельный запрос на разметку.

## Аудит «приходят ли данные» (события / цели / тест-стенды)

Класс задач «проверь, что X приходит в Matomo», «доработку выкатили — тестовые данные больше не идут?», «с каких доменов есть события?». Как отдавать результат этому пользователю: **вердикт первой строкой**, затем таблица с цифрами и датами (за какой период, сколько), затем UI-рецепт (путь по меню + сегмент — спрашивает именно «как проверить в ЛК»), затем команда/скрипт для перепроверки. Проверять фактами из API, а не по памяти; оговорки («исчезло, но это может быть просто прекращение использования») писать явно. Любые файлы/вложения к таким ответам называть **с датой периода данных в имени (ISO ГГГГ-ММ-ДД)** — прямое требование пользователя (2026-09), относится ко всем присылаемым отчётам и файлам. **Таблицы и сводки показывать целиком** — не обрезать до топ-N молча; если сокращаешь, явно помечай «показаны применимые/топ, полная версия в файле» (пользователь спросил «почему только 10 строк — их правда больше нет?» после сокращённой сводки, 2026-10).

1. **События**: `Events.getCategory / getAction / getName` (диагностика — `matomo-api-quirks.md` → «События (Events) — аудит»); скрипты в `$HERMES_HOME/matomo_weekly/`: `check_events.py [дней] [подстрока]` и `check_events_by_host.py --days 7 <хост> …` (сегмент `pageUrl=@<хост>`).
2. **Тест-стенды / «доработка помогла?»**: `check_test_traffic.py [idSite] [дней_от] [дней_до]` — все хосты с признаками теста/dev (`localhost:42xx`, `127.0.0.1`, `192.168.*`, `10.*`, `vm-*`, `*.iwr.lan`, `*-demo*`, `*test*`, `:порт`) с «первый/последний раз» и разбивкой по дням: сразу видно, перестал ли источник приходить. Для чужого инстанса — `check_stand_traffic.py <base_url> <token> <подстрока_хоста>`.
3. **События по хостам** ищутся сегментом `pageUrl=@<хост>` (событие привязано к URL страницы) — то же самое делает пользователь в UI: Behaviour → Events → сегмент (измерение **Page URL** → contains). Несколько хостов: запятая = OR, `;` = AND, негативные операторы `!@` / `!~`.
4. **Цели**: цели не ретроактивны и большинство типов создаются без разметки фронта — разбор, типы триггеров и что можно завести «из ЛК» — `references/goals-vs-events.md`.
5. **«Почему метрики расходятся»** (уникальные посетители ≠ пользователи, vизиты ≠ уники, разные числа за один период в двух блоках ЛК): разбирать строго по порядку — (а) какая это метрика (цитата определений из `API.getMetadata`), (б) какой период в шапке (day/week/range + `sum_daily_*`), (в) покрытие `uid` на фронте. Определения, пруф `sha1(userId)[:16]`, квантификация визитов без uid, профиль «анонимных» сессий, питфолл «смешанных visitorId» и локализация незаходящего `uid` в DevTools — `references/userid-coverage-diagnostics.md`.
