# Цепочки → проблемы → сегменты пользователей по путям

Продолжение `module-workflow-pairs.md` и `user-paths-analysis.md`: как из цепочек экранов дойти до
брошенных процессов и до широких сегментов пользователей. Проверено на iiko 01–13.10.2026.

## Цепочки из N экранов (топ-200)

1. Журнал: выборка пользователей (напр. 1 500 редких + 1 000 регулярных, роботы исключены) → `Live.getLastVisitsDetails`
   по дням, сегменты ≤300 id, `filter_limit=-1`, `showColumns="userId,actionDetails"`. 35 574 визита ≈ 4 мин.
   Хранить нормализованные экраны в JSONL (`{"u": uid, "s": [[screen, actions], …]}`).
2. Нормализация: подряд идущие повторы одного экрана склеить со счётчиком; `:id` уже схлопнуты фронтом.
3. Цепочка = три последовательных экрана визита (повторы подряд убраны). **Два счётчика обязательны:**
   - `visits_with` — в скольких визитах встречается (для доли = visits_with / всего визитов);
   - `occurrences` — сколько всего вхождений (цикл повторяется внутри визита).
   Доля от `occurrences` даёт **>100%** (частый баг: покупки «список→карточка→список» = 11 377 вхождений при 11 200 визитах).
4. JSONL-сериализация цепочек: писать `[[s1,s2,s3], visits_with, occurrences]` — НЕ `for k in counter.most_common()` (k там — кортеж (key,count), `list(k)` ломает структуру).

## Группировка по разделам (цепочка повторяется в группах)

Пользователь просит «сгруппировать цепочки по разделам». Правило: цепочка попадает **во все разделы,
которые затрагивает** (первый экран, второй, третий — каждый даёт членство в своей группе), поэтому
между группами строки повторяются. Для каждой группы дополнительно считать «действия внутри раздела» —
подпоследовательность под-роутов именно этого раздела (без имени раздела), чтобы показать, чем там занимаются.

## Метрика «успешно vs оборвано» (прокси брошенности)

- **Успешно** = визит закончился на списке/главной/корне раздела (вернулся к рабочему списку → операция завершена).
- **Оборвано** = визит закончился на глубоком рабочем экране (карточка, редактор, подсчёт) → операцию прервали, не вернувшись.
- **Оборвано на 100 успешных** = abandoned / completed — шкала серьёзности.
- HUB-экран = корень модуля (1 сегмент) ИЛИ последний сегмент в списке ключей списка: `list, home, main, index,
  order-list, order-list-v2, external-menu, documents, accounts, stock, transactions`.
- **Ловушка «табло»:** для разделов, где рабочий экран и есть конечная точка, метрика НЕПРИМЕНИМА — там 98% «обрывов»
  это норма. Список iiko: till-shifts, dashboard, cpu, delivery-map, internal-couriers, web-event-log, abc-xyz,
  customer-screen, loyaltysystem, app-licensing, site-constructor, schema-editor, prep-plans, configuration,
  employees, forecast, user-profile, directories. Их показывать в отдельной группе «—», а в сводке — только «✓»-разделы.
- iiko 13.10.2026 (применимые): колл-центр 89,6% успешно (здоров), закупки 86,8%, номенклатура 99,9%,
  склад 84,8%, интеграции 76,8%; плохие — документы 39,2% (60,8% оборвано, 155 обрывов на 100 успешных),
  инвентаризация 52,9% (47,1%), внешнее меню 28,4% (71,6% — но это «короткая правка и выход», см. ниже).
- Интерпретация «оборвано» различать: высокая доля обрыва может значить «короткая операция без возврата» (внешнее меню,
  настройки), а не брошенный процесс; «брошенный» подтверждается обрывом на КОНКРЕТНОМ глубоком экране
  (документы — `/incoming_invoice/:id` 230, инвентаризация — зоны подсчёта 818).

## Сегменты пользователей по путям

- **Метка по журналу**: сегмент = контур, где у пользователя больше всего действий (`argmax` по сумме действий на модуль,
  сгруппированных по карте «модуль → сегмент»). «Только вход и профиль» — фоллбэк, если действий в рабочих модулях нет.
- **Правило для ВСЕЙ базы** (не только выборки): по матрице `user × module` (действия из `matrix.json`) взять сегмент-argmax.
  Совпадение правила с журналом — 81% (2 035/2 500): пригодно для распределения всех аккаунтов, но оговорку про точность писать.
- Карта «модуль → сегмент» (iiko): операционка — call-center / purchase* / till-shifts* / inventory / lite-stock /
  documents* / cpu / eprod / prep-plans / orders* / delivery-map / internal-couriers; настройка-витрина — configuration /
  integration / employees / user-account / workflow-config / directories / external-menu / nomenclature / price-list /
  menu-quick / customer-screen / loyaltysystem / site-constructor / marketplace / webkds / schema-editor; аналитика —
  dashboard / forecast / abc-xyz / web-event-log. navigator/auth/home/user-profile/config/error — «только вход».
- Результат 13.10.2026 (11 628 аккаунтов): настройки и администрирование 30,6%, меню и цены 25,9%, аналитика 12%,
  кассы и смены 8,3%, только вход и профиль 7,5%, склад 6,5%, далее витрина/закупки/колл-центр/документы/доставка/ЦПУ.
- Артефакты: `segments_summary.json`, `segments_users_full.csv` (все аккаунты), `segments_users_sample.csv` (метка по журналу),
  `chain_groups.json` (группы циклов), `dropoff_rates.json`.

## Выдача пользователю

- **Таблицы показывать ЦЕЛИКОМ, не обрезать до топ-N.** Пользователь явно спросил «почему только 10 строк — их правда больше нет?»
  после сокращённой сводки. Правило: либо все строки в чате, либо явно сказать «полная таблица (N строк) в файле — показать все?»
  и приложить файл. Сокращать допустимо только с явной пометкой «показаны применимые/топ, полная версия в файле».
- Файлы — CSV «;» UTF-8 BOM + MD для чтения; в имени дата конца периода.
