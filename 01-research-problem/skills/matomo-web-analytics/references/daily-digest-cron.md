# Ежедневный дайджест Matomo (cron, вчерашний день)

Пайплайн, который крутится каждый день в 06:00 UTC (09:00 МСК) и отдаёт в Telegram компактный отчёт за **вчера**.
Рабочая папка: **$HERMES_HOME/matomo_weekly/**; скилл-обёртка — `matomo-daily-report` (user-owned, автономно не правится).

## Прогон

```bash
cd $HERMES_HOME/matomo_weekly
python3 fetch_matomo_daily.py        # → daily.json (60–72 модуля; число строк плавает: 72 при 15.10.2026, 65 при 16.10.2026)
python3 build_daily_dashboard.py     # → daily_dashboard.html (KPI, часы, устройства, полная таблица)
cp daily_dashboard.html reports/matomo_daily_$(date -d yesterday +%F).html   # имя = дата ДАННЫХ
python3 <skill_dir>/scripts/daily_digest_stats.py $HERMES_HOME/matomo_weekly/daily.json
```

Отправлять в сообщении **датированную копию** (`reports/matomo_daily_<дата данных>.html`), не `daily_dashboard.html`.
Файлы и вложения — всегда с датой данных в имени (ISO ГГГГ-ММ-ДД): прямое требование пользователя.

**Копию сверять хешем, а не размером.** `build_daily_dashboard.py` печатает «daily_dashboard.html: N байт», и это N — длина строки в символах, а не размер на диске (кириллица в UTF-8 = 2 байта): 13.10.2026 в логе было 21 954, а файл на диске 22 742. Расхождение не значит, что копия устарела. Проверка:

```bash
md5sum daily_dashboard.html reports/matomo_daily_<дата>.html   # хеши обязаны совпасть
```


## Схема daily.json

`{date, weekday, totals{uniq,visits,actions,bounce}, devices_total[{label,pct}],
 hourly[{hour,visits,uniq}], pages[{module,uniq,visits,hits,has_sub,devices[{label,pct}]}], note}`

Поля host/path/url в daily.json НЕТ — агрегация по `p.module` сегментом, кросс-доменно. Поэтому:
Σ uniq/visits по pages больше итогов дня (один пользователь = несколько разделов).

`hits` — тоже агрегат модуля **вместе с подстраницами** (16.10.2026: `call-center` 73 074 против 24 339 у собственной строки `/call-center`), поэтому hits соседних строк не складывать. Зато Σ hits по всем строкам ≈ `totals.actions` (16.10: 253 917 против 257 660, Δ≈250 не атрибутировано) → `hits/totals.actions` = доля дня, `hits/uniq` = «действий на человека». Это самый быстрый способ объяснить скачок `actions`: 16.10 действия +10,6% к 15.10 дал один call-center (314 на чел. против 245).

Строки с `"uniq": null` (dev/мусор по 1 визиту: order, payment-gateways, franchise, delivery-heatmap, recipe-manage) обязаны отфильтровываться перед любой сортировкой по uniq — иначе `TypeError: bad operand type for unary -: 'NoneType'`.

## Проверки перед публикацией цифр

- `Σ hourly.visits == totals.visits` → день полный. Не сходится — писать в отчёте, что день неполный (не выдавать цифры как финальные).
- Доля топ-разделов («navigator + purchase — 72% визитов дня») считается **от `totals.visits`**, а не от Σ визитов по страницам. От Σ получится ~39% — цифра верная арифметически, но ломает преемственность с прошлыми отчётами и читается как падение.
- Глубина: `actions/uniq` (напр. 12,6) и `actions/visit` (5,9); визитов на уника 2,15.
- **Падение `actions/visit` само по себе НЕ значит «стало меньше работы»** — раскладывать `actions/visit = (actions/uniq) / (visits/uniq)`. Кейс 26.09 (сб): actions/uniq 10,84 против 10,86 в пятницу — объём на человека не изменился, а visits/uniq вырос 2,13 → 2,26, поэтому на визит пришлось 4,80 вместо 5,11. Верная формулировка — «больше коротких возвратов», а не «просевшая работа»; без разложения получается ложный вывод.
- **Число модулей с трафиком зависит от дня недели** (пт 62 → сб 50): в выходной часть разделов просто не открывают. Подавать как факт дня («12 разделов не открывали»), а не как аномалию или потерю трафика.
- **Shares устройств день-к-дню (пт↔сб) сравнивать нельзя** — в выходной профиль переворачивается: сб 26.09 дала M 50% / D 47% против D 58% / M 39% в пятницу. Драйвер — операционные роли (till-shifts M 78%, dashboard M 67% при v/u 2,64 и 2,06), тогда как десктопные кабинеты в выходной почти не работают (call-center D 93%, external-menu D 94%, configuration D 87%). Сравнивать только с тем же днём недели и явно называть сдвиг выходным.
- Пик/минимум часа — по `hourly.visits`; вечернее окно 18:00–23:00 считать долей суток.

## «Дверь» приложения и подстраницы модулей (для инсайтов)

Цифры входа даются **сегментом по подпути**, а не строкой `getPageUrls` (её `label` — только первый сегмент):

```python
# VisitsSummary.get, segment=pageUrl=@/navigator/auth/login
/navigator/auth/login   uniq=2715  visits=5416  actions=152404   # 13.10.2026 = 95% уников navigator
/navigator/home         uniq=2241  visits=4136
/navigator (модуль)     uniq=2853  visits=5840
```

Разбивка внутри модуля: `Actions.getPageUrls` + `segment=pageUrl=@/<module>` + `flat=1` + `showColumns=nb_uniq_visitors,nb_visits,nb_hits` — без `showColumns` ответ в разы толще (десятки полей времени на строку), а с ним помещается в контекст.
Готово: `python3 -u <skill_dir>/scripts/door_probe.py 2026-10-13 navigator`.

## Прошлый день для сравнения

Последний файл `$HERMES_HOME/cron/output/d1d15d50171d/*.md` (job_id дневного джоба).
Имя файла = дата **запуска**; данные внутри = запуск − 1 день. Файл начинается с промпта и полного текста скилла (~60 строк) — готовый отчёт ищи после строки `## Response`, не читай с начала.

Дополнительно брать файл **семидневной давности** (тот же день недели): сравнение «Пт к Пт» отделяет разовую просадку от тренда. В отчёте давать оба сравнения — день-к-дню и неделю-к-неделе.

**Если прогон нужного дня упал — цифры всё равно достаются.** В `$HERMES_HOME/cron/output/d1d15d50171d/` встречаются файлы с `## Error` вместо `## Response` (прогон 2026-09-20 за Сб 19.09: `RuntimeError: Request timed out` — секции ответа в файле нет вовсе). Цифры пропущенного дня лежат в **следующем** отчёте строкой «К прошлому дню (19.09, Сб): уники 13 318 → 12 976, визиты 30 108 → 29 495». Поиск: `grep -n "19.09" $HERMES_HOME/cron/output/d1d15d50171d/*.md`. Перед использованием файла проверять, что в нём есть `## Response` (иначе читаешь только промпт и `## Error`). Так WoW-сравнение (13 318 → 13 257 уников, −0,5%) собирается, даже когда отчёт за базовый день не вышел.

## Cron-специфика

- `execute_code` в cron-профиле недоступен (approvals.cron_mode блокирует произвольный Python) — анализ делать временным скриптом: `write_file $HERMES_HOME/matomo_weekly/_stats.py` → `terminal: python3 _stats.py` → удалить файл. Готовый разбор — `scripts/daily_digest_stats.py` (не переписывать заново).
- «Вчера» считается по UTC — при запуске в 06:00 UTC это ровно предыдущий календарный день по МСК.
- В данных есть служебные/dev-строки: `Page URL not defined`, `/index`, `/nomenclature`, `ru-RU`, модули с 1–3 униками (app-trial, eprod, orders, kiosk-management…). В таблице оставлять, в выводах отмечать как dev-заходы.
- **`dev=true` — эвристика, а не гарантия: проверяй, что строки вообще есть.** Флаг ставится только если рядом с почти пустой строкой сегмент собирает ≥50 визитов (`fetch_matomo_daily.py::main`). 13.10.2026 строки `auth` в верхнем уровне не было вовсе → список dev пуст, хотя localhost-строки (`order`, `payment-gateways`, `/index`, `/order-list-v2`) в таблице были. Не писать в отчёт «dev-строки помечены»/«строка `auth` искажает цифры», когда список пуст — перечислять фактические localhost-строки с их 0–1 уником.

## Формат сообщения (принятый у пользователя)

Шапка «📊 Matomo iiko · вчера, ДД.ММ (Дн)» → **Резюме** (уники · визиты · действия · отказы, устройства D/M/P/T, пик/минимум часа) → **Топ разделов** (5–8 строк `• module — N уник., M виз. · D x% / M y%`) → **Сравнение** (день-к-дню и неделя-к-неделе) → **Инсайты** (3–5 фраз: глубина, что просело/удержалось, возвратность визит/уника, мобильные vs десктопные разделы, концентрация) → строка «Все N страниц — в прототипе» + `MEDIA:<путь к датированной копии>` → примечание о полноте дня.

Смысловые блоки разделять **пустой строкой**; пользователь смотрит с телефона в предпросмотре Telegram — текст должен читаться без JS.

Рабочий вариант компоновки (отдан 27.09 за 26.09): оба сравнения — двумя строками прямо в блоке «Резюме» (день-к-дню и WoW), «День по часам» — отдельным блоком между «Топ разделов» и «Инсайтами» (пик/минимум, плато, доли вечернего и ночного окна, сверка Σ часов с итогом). Инсайты — 4–5 абзацев: сначала самый «продуктовый» вывод дня (смена профиля устройств, глубина, концентрация), затем возвратность по разделам, затем хвост и техшум.
