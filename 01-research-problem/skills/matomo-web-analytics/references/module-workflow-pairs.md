# Связки модулей (рабочие процессы) и профиль «зачем заходят» по классам пользователей

Класс задач: «какие разделы фактически один процесс», «где проверять связки вроде колл-центр + карта доставок»,
«хочу понять, как разделить регулярных и редких по разделам». Проверено на iiko prod, 01–13.10.2026.
Скрипты прогона: `$HERMES_HOME/scripts/workflows_step1_pairs.py`, `workflows_step2_class.py`,
`workflows_step3_report.py`, `routes_ru.py`, словарь `ru_names.py`.

## 1. Что исключать из связок (правка пользователя)

- `/navigator` — **главная страница, основная точка входа**; связки с ней тривиальны, в анализ не брать.
- `/user-profile` — транзитный экран (открывают по пути): попадает в половину пар и делает их неинформативными.
  Такие пары выносить в справочный блок, а не в гипотезы.
- Технические: `auth`, `error`, `no-access`, `config`.

## 2. Ключевой питфолл: составной сегмент по pageUrl не работает

`segment=pageUrl=@/call-center;pageUrl=@/delivery-map` → **0 визитов**, хотя по отдельности 11 912 и 3 095.
Причина: два условия по одной размерности применяются к ОДНОМУ действию, а не к разным действиям одного визита.
Не подбирать синтаксис — использовать обход.

**Обход:** `Actions.getPageUrls&period=range&date=<R>&segment=pageUrl=@/<A>&flat=1&filter_limit=-1&showColumns=label,nb_visits`
возвращает ВСЕ страницы визитов, где был модуль A. Строки модуля B = визиты, где встречались оба.
Один вызов на модуль A (~5–35 с) покрывает все пары сразу (31 модуль ≈ 10 минут).
База P(B|A) — из `VisitsSummary.get&segment=pageUrl=@/<A>` (это надёжнее и считается за ~1 с).

## 3. Два уровня связи дают разные выводы — смотреть оба

| Уровень | Как считать | Что показывает |
|---|---|---|
| Пользовательский | пересечение uid из `UserId.getUsers&segment=pageUrl=@/<module>`; lift = факт/ожидание | одни и те же люди ходят в оба модуля (в т.ч. в разные дни) |
| Визитный | обход из п.2; P(B\\|A), P(A\\|B), lift визитов | встречаются ли в одной сессии |

Пример (iiko): **call-center + delivery-map** — 104 общих пользователя, lift 14.3 на уровне людей, но лишь
**11.7% визитов с картой содержат колл-центр** (362 визита с обоими). Вывод: процесс один (оператор смотрит,
где курьер, чтобы ответить гостю), но растянут по сессиям (визит рвётся на 30 мин простоя).
Для аналитики такие процессы считать по «дням пользователя»; для продукта — аргумент связывать разделы в интерфейсе.

## 5. Профиль «зачем заходят»: главный модуль визита × класс пользователей

Метод: для каждого визита определить главный модуль (максимум действий по модулям в визите), агрегировать
по классам (постоянные / редкие / автоматы), нормировать на 1000 визитов класса; индекс = редкие ÷ регулярные.
Выборка 1 000 редких + 400 регулярных (случайная, seed) даёт устойчивую картину по всем разделам.

Результат iiko (на 1000 визитов группы):

| Раздел | Редкие | Регулярные | Индекс |
|---|---:|---:|---:|
| Колл-центр | 3.0 | 104.6 | 0.03 |
| Закупки | 9.3 | 140.2 | 0.07 |
| Кассовые смены | 31.9 | 141.0 | 0.23 |
| Карта доставок | 0.3 | 12.6 | 0.03 |
| Внешнее меню | 192.3 | 66.5 | 2.89 |
| Настройки | 35.3 | 14.7 | 2.40 |
| Интеграции | 27.3 | 8.7 | 3.14 |
| Экраны гостя | 20.3 | 3.9 | 5.19 |
| Маркетплейс / схема зала / WEB-KDS | 2.7–3.0 | 0.1–0.2 | 14–24 |

Профиль: **регулярные = операционка** (колл-центр, закупки, смены, карта доставок, курьеры, ЦПУ),
**редкие = администрирование и витрина** (настройки, интеграции, меню/номенклатура, лояльность, сайт, киоски).
Проверка гипотезы «регулярные не ходят в настройки/интеграции»: подтверждается в ослабленном виде — у них это
десятые доли процента (8.7 и 14.7 на 1000), но и вывод «это разделы редких» верен: у редких 27.3 и 35.3.
