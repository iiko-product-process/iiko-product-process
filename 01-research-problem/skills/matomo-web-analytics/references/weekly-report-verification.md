# Проверка недельного отчёта перед отправкой (runbook)

Относится к классу «регулярный отчёт по Matomo в чат» (еженедельный/ежедневный пайплайн
`$HERMES_HOME/matomo_weekly/`, cron пн 09:00 МСК). Сам пайплайн и его файлы — в
`references/iiko-instance-access.md`; здесь — приёмы, которые ловят ошибки в отчёте.

## 1. `fetch_matomo.py` не укладывается в foreground-таймаут

Скрипт делает ~10 запросов к API и на iiko-инстансе идёт **дольше 180 с** — терминал убивает
его по таймауту (exit 124), и это выглядит как «не работает», хотя данные тянутся нормально.
Запускать сразу в фоне и дожидаться:

```
terminal(command="cd $HERMES_HOME/matomo_weekly && python3 fetch_matomo.py > /tmp/fetch_matomo.log 2>&1; echo EXIT=$?", background=true)
process(action="wait", session_id="...", timeout=180)   # лимит wait клампится к 180 с; при недоборе — повторить
```

Признак успеха в логе: `data.json сохранён`, две недели (w1/w2), непустые totals.
Тот же приём — для любого прогона, который может уйти за 3 минуты.

## 2. Унаследованные цифры проверять ДО того, как они попадут в отчёт

Правило пользователя: утверждения проверять по фактическим данным. Выводы прошлого прогона
лежат в `insights.json`, и соблазн переписать ряд «5,33 → 6,86 → 4,47» как факт. Но `data.json`
содержит только W1 и W2 — более старый период в текущем прогоне НЕ виден, значит утверждение
о ряде из 3+ недель не подтверждено ничем.

Проверка (сработавший приём):

```
python3 <skills>/research/matomo-web-analytics/scripts/verify_page_trend.py /navigator /inventory --weeks 3
```

Рабочий кейс 2026-09-28 (iiko prod) — ряд подтвердился, и это изменило трактовку отчёта:

| период | `/inventory` hits/visit | `/navigator` hits/visit |
|---|---|---|
| 07–13.09 | 5,33 | 3,36 |
| 14–20.09 | 6,86 (выброс) | 3,02 |
| 21–27.09 | 4,47 | 2,78 |

`/inventory` — разовая аномалия, откатившаяся даже ниже прежней нормы (5,33). `/navigator` —
монотонный тренд третью неделю. Трактовки разные: первое = проблема разметки, второе = реальное
изменение сценария раздела. Без проверки оба выглядели бы одинаково «просмотры упали».

## 3. Сверять текст отчёта с фактическими чипами вложенного HTML

`gen_dips_by_day` в `build_dashboard.py` строит чипы просадок **без порога по объёму** — только
Δ ≤ −10% между W1 и W2 по часу дня. Аналитик же обычно отсекает мелочь порогом (≥300 визитов),
и тогда фраза «в рабочие часы просадок нет» расходится с чипами, которые пользователь видит
в приложенном файле. На этом уже спотыкались (ночные чипы `Чт 03:00 −28%`, `Ср 02:00 −13%`
в отчёте 2026-09-28 всплыли только после чтения собранного HTML).

Порядок: собрать дашборд → прочитать `<!--BLOCK:dips-->` из `dashboard.html` → перечислить в
выводе **ровно те** часы, что там есть, и добавить оговорку про малые объёмы/нерабочее время.
Не пересчитывать «по-своему» и не утверждать отсутствие просадок раньше этой сверки.
(Статичные блоки и JS-вид расходятся — см. одноимённый pitfall в SKILL.md.)

## 4. Падение site-wide метрики раскладывать по вкладу одной страницы

Когда итоговые «действия» падают при растущих визитах, арифметика решает трактовку: посчитать
абсолютные дельты `nb_hits` по топ-страницам и их долю в общей дельте. Кейс 2026-09-28:

- действия по сайту: 1 370 493 против 1 476 614 = **−106 121**;
- топ-15 страниц: **−63 931** (60% падения);
- `/inventory` одна: **−38 719** (36% всего падения по сайту).

Вывод в отчёт: падение «действий» — не уход аудитории, а нормализация просмотров одного модуля.
Без этого разложения отчёт читается как «пользователи стали работать хуже».

## 5. Вложение и имя файла

Даже если текст cron-задания просит вложить `dashboard.html`, прикреплять **датированную копию**
`reports/matomo_weekly_<воскресенье W1>.html` — у пользователя правило «дата отчёта в имени
присылаемого файла». `dashboard.html` остаётся каноническим рабочим файлом (его правят руками),
в ответе его указывать отдельно. После пересборки дашборда копию пересоздавать и сверять `cmp`,
иначе вложение разойдётся с текстом.

## 6. Неделя выросла — раскладывать так же, как падение

Плюс в агрегатах не отменяет проверки состава: прогон 26.10.2026 дал «визиты +3,2%, уники +4,4%,
действия +1,3%» на двух неделях одной базы (19–25.10 против 12–18.10), но глубины просели
(действий на визит 18,46 против 18,82, −1,9%), то есть прирост пришёл людьми, а не интенсивностью.

```
cd $HERMES_HOME/matomo_weekly && python3 -u <skills>/research/matomo-web-analytics/scripts/weekly_cohort_delta.py \
    2026-10-19,2026-10-25 2026-10-12,2026-10-18
```

Итог: 6 255 общих uid (73% от W2) дали 79 757 против 78 603 визитов (+1,5%), одновизитные
2 624 против 2 420 (+8,4%), только-W1 2 745 uid / 6 327 визитов, только-W2 2 345 / 4 747 —
и разложение (+1 154 +6 327 −4 747 = +2 734) сошлось с фактическими +2 700. Формулировка в отчёте:
«растут и ядро, и разовые» (в отличие от 19.10.2026, где ядро −0,7% при униках −9,9% = разовые заходы).

Полезные зацепки этого прогона: единственные минусы по разделам — `call-center` −2,5%,
`till-shifts` −1,8%; самый сильный рост — `inventory` +17,5% равномерно по всем экранам
(отыграл прошлую −30,2%, значит это был реальный спад и он закончился, а не смена разметки);
доля десктопа +0,97 пп к смартфону (−1,00 пп) при плоских разрешениях мобильных.



Прогон 12.10.2026 (iiko prod): W1 = 05–11.10 (вся новая база, первая полная неделя), W2 = 28.09–04.10
смешанная (28–30.09 старый счётчик, 01.10 ~11:00 МСК переключение, 02–04.10 новая база). Агрегатные
«−77,3% уников и −53,1% визитов при +4,8% действий» — про смену базы, а не про трафик.

Порядок (сработавший):
1. `python3 -u $HERMES_HOME/skills/research/matomo-web-analytics/scripts/detect_identity_step.py 14` → день перелома.
2. Сопоставимые дни W2 (целиком на новой базе) против тех же дней W1 через `period=range`:
   `VisitsSummary.get`/`DevicesDetection.getType`/`Resolution.getResolution`/`VisitsSummary` + `userId`
   и `Actions.getPageUrls` (non-flat — агрегат по разделу) за `2026-10-02,2026-10-04` и `2026-10-09,2026-10-11`.
   Дало: уники −6,1%, визиты −2,9%, действия −1,0%; глубины совпадают (20,2 против 19,8 действия/визит,
   отказы 21% в обеих неделях) — прошлонедельное «визит стал крупнее» было артефактом.
3. Контроль: 01.10 12:00–23:00 (новая база) против 08.10 12:00–23:00 = −7,6%, а утро 01.10 = −71,3%.
4. `python3 mark_comparable_days.py --break 2026-10-01 --days "Пт,Сб,Вс"` (после `fetch_matomo.py`,
   до `build_dashboard.py`) → `meta.comparable_weekdays`; чипы просадок в дашборде строятся только
   по сопоставимым дням, остальные подписаны «сравнение не показано» (и статика, и JS `renderHour`).
5. Перед отправкой прочитать `<!--BLOCK:dips-->` из собранного HTML и перечислить в сообщении ровно
   те часы (с объёмами), что там есть.

Тогда же подтвердилось: смена меток путей (`/navigator/index.html` 66 056 → 305, пришли подроуты,
flat-строк 442 против ~106), поэтому «страница пропала» = смена метки, а не нули; разделы сравнивать
только по non-flat дереву. Единственный сильный выброс раздела — `inventory` −30,2% равномерно по
всем экранам (проверять у команды, а не писать «экран сломался»).

## 8. Одноразовые пробы

`execute_code` в cron-профиле заблокирован. Анализ делается временными скриптами: писать
`$HERMES_HOME/matomo_weekly/probeN.py` через write_file (длинные inline-однострочники терминал
блокирует), запускать `python3 probeN.py`, по завершении удалять — рабочая папка пользователя,
мусор в ней не нужен.
