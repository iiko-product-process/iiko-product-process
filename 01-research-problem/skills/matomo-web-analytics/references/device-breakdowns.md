# Устройства: разрез по пользователям, классам и сегментам

Задача: «кто заходит с мобильного, а кто с компа» — чтобы понять, где рвутся процессы и на каком устройстве проверять гипотезы.
Проверено на iiko prod (idSite=1), окно 01–13.10.2026.

## Три разреза — три метода

**1. Доля устройства по РАЗДЕЛУ (визиты) — дёшево.**
`DevicesDetection.getType` + `segment=pageUrl=@/<module>`, `period=range`. 18 разделов ≈ 11 с.
Возвращает `nb_visits` / `nb_actions` по типам: `Desktop-приложение`, `Смартфон`, `Фаблет`, `Планшет`, прочее по нулям.

**2. Доля устройства по ПОЛЬЗОВАТЕЛЮ/классу/сегменту — только через Live.**
`DevicesDetection.getType` **не отдаёт `nb_uniq_visitors`** ни на range, ни на month (в ответе только nb_visits/nb_actions),
поэтому «% пользователей» из него не получить. Устройство есть на уровне визита в Live:
`showColumns="userId,deviceType"` (без `actionDetails` — payload маленький), затем `user → Counter(device)`.
Выборка 2 500 пользователей / 35 617 визитов: ~100 с.

Схема съёма (обязательно `period=day` + пагинация):

```python
for day in DAYS:                      # 01..13
    for batch in chunks(users, 300):  # сегмент userId==a,userId==b,...
        offset = 0
        while True:
            rows = api(method="Live.getLastVisitsDetails", period="day", date=day,
                       segment=seg, filter_limit=1000, filter_offset=offset,
                       showColumns="userId,deviceType")
            ... ; offset += len(rows)
            if len(rows) < 1000: break
```

**Питфолл:** `filter_limit=-1` + `period=range` + сегмент на 300 uid → **HTTP 500 Internal Server Error**
(падает на 5-й пачке из 9). Лечится переходом на `period=day` + `filter_limit=1000` + `filter_offset`.

## Нормализация типов

- `Desktop-приложение` → desktop
- `Смартфон` + `Фаблет` → mobile (фаблеты = телефоны, отдельной группой не показывать)
- `Планшет` → tablet

По пользователю считать два числа: **главное устройство** (доминирующее по числу визитов) и **«заходят с мобильного хоть раз»**
(≥1 мобильного визита) — второе важнее для гипотез: человек может работать и там и там.

## Устройства × обрывы: третий разрез (проверено 29.10.2026)

Доля устройства по разделу ещё не отвечает на вопрос «где проверять обрыв». Нужны **три** числа:

1. `visits_share_%` — доля устройства среди всех визитов раздела;
2. `abandoned_share_%` — доля устройства среди **оборванных** визитов;
3. `abandoned_%` — доля обрыва **внутри** устройства.

Скрипт: `$HERMES_HOME/scripts/device_dropoff.py` → `segments/device_dropoff.json`. Он тянет
`Live.getLastVisitsDetails` с `showColumns="userId,deviceType,actionDetails"` по тем же батчам 300 uid /
дню / `filter_limit=1000`, определяет последний экран визита и делит на hub/deep.

| Раздел | Комп % визитов | Моб % визитов | Доля обрывов: комп | Доля обрывов: моб | Обрыв % комп | Обрыв % моб |
|---|---:|---:|---:|---:|---:|---:|
| Инвентаризация | 63,8 | 34,6 | 45,6 | **53,1** | 39,9 | **55,4** |
| Закупки | 56,1 | 42,0 | **88,3** | 8,8 | **22,1** | 2,7 |
| Документы | 80,1 | 17,4 | **85,0** | 12,4 | 60,7 | 59,9 |
| Внешнее меню | 94,6 | 4,9 | **95,8** | 3,8 | 71,6 | 72,1 |
| Колл-центр | 93,3 | 5,4 | **97,0** | 3,0 | 10,7 | 7,9 |

Читать так:

- **Инвентаризация** — единственный крупный процесс, где мобильный реально хуже и по доле обрывов,
  и по доле обрыва внутри устройства. Проверять на телефоне.
- **Закупки** — 42% визитов с мобильного, но 88,3% обрывов на компе; доля обрыва там ниже (2,7% против 22,1%).
  Проверять на обоих, начинать с компьютера. Прежняя рекомендация «закупки — два устройства» была слишком грубой.
- **Документы** — 85% обрывов на компе, но доля обрыва почти равна (60,7 / 59,9): проблема в форме,
  а не в адаптивности. Проверять на компе.
- **Меню, интеграции, колл-центр** — обрывы почти целиком на компе; это не мобильная проблема.
- **Кассы, дашборд, ЦПУ, настройки** — «табло»: метрика обрыва не применяется; 100% — ложный сигнал.

### Нормализация — обязательна

`device_dropoff.py` должен использовать **тот же** `norm()`, что и `seg_step1_pull.py`:
`strip query/hash`, `rstrip("/")`, схлопывать подряд идущие одинаковые экраны. Иначе последний экран
классифицируется иначе и обрывы расходятся: у инвентаризации получалось **51,9% вместо 47,1%**
(1 142 vs 1 038 обрывов). После прогона сверять суммы `exits` по разделам с `dropoff_rates.json`
(расхождение — единицы визитов без экранов).

## Как это читать в отчёте

- **Где проверять гипотезу об обрыве** — по `abandoned_share_%` и `abandoned_%` (раздел «Устройства × обрывы»),
  а не по доле визитов: инвентаризация — мобильный; закупки — комп (мобильный проверить вторым);
  документы — комп; меню и колл-центр — комп; кассы и дашборд — мобильные, но это «табло».
- «Табло»-разделы (till-shifts, dashboard) мобильные — это телефон в руке, а не рабочее место; обрывы там не читать как потери.
- Не смешивать метрики: доли по разделам считаны по ВИЗИТАМ, по классам/сегментам — по ПОЛЬЗОВАТЕЛЯМ (выборка 2 500).
  В тексте отчёта это оговаривать.
