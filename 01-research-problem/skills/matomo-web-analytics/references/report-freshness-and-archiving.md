# Задержка появления данных в отчётах Matomo: сырой слой vs архив

Класс вопроса: «через сколько событие/визит с прода появится в Matomo?», «почему в отчёте ещё нет сегодняшних данных», «есть ли задержка и какая».

## Модель (важно отвечать двухслойно)

1. **Сырой слой — секунды.** Трекер `matomo.php` пишет визит/действие/событие в таблицы `log_*` синхронно. Его читают: «Посетители → Журнал посещений» (Visits Log), «Посетители → В реальном времени», Live API (`Live.getCounters`, `Live.getLastVisitsDetails`). Задержка = только сеть/клиент.
2. **Слой отчётов — архив.** Все отчёты (Действия, События, Страницы, Устройства, любые агрегаты) в UI и через Reporting API читают **archive-таблицы**, которые пересчитываются отдельно: по запросу (browser archiving — только если архив старше порога) либо кроном `core:archive`. Пока архив не пересчитан, отчёт отдаёт старые цифры, даже если сырые данные уже пришли.

## Пороги и режимы (Matomo 5.x, `config/global.ini.php`, сверено с 5.x-dev)

- `time_before_today_archive_considered_outdated = 900` — «сегодня» пересчитывается не чаще, чем раз в 15 мин; **перекрывается в UI → General Settings** (там значение может быть другим, файл `config.ini.php` по API не читается).
- `time_before_week_/month_/year_/range_archive_considered_outdated = -1` — наследуют значение «сегодня» (если `enable_general_settings_admin=0`), иначе берут из UI.
- `browser_archiving_disabled_enforce = 0` по умолчанию ⇒ запрос может триггерить архивацию; при `1` отчёты обновляются **только** в момент крона (обычно ежечасно, у части инсталляций 5–15 мин).
- `archiving_range_force_on_browser_request = 1` — произвольные диапазоны дат форсируются по запросу даже при отключённой браузерной архивации; крон `core:archive` произвольные range-периоды не считает.
- Следствия для «вчера/неделя/месяц»: данные прошлых дней уже посчитаны, но агрегат недели/месяца может отставать до своего порога (неделя ~15 мин, месяц ~1 ч при дефолтах).

## Замер на инстансе analytics.iiko.services (5.11.0, tz Europe/Moscow, idSite=1, 2026-09-17, ~70 визитов/мин)

- Сырой слой: `Live.getLastVisitsDetails` → `lastActionDateTime` = текущая минута (задержка секунды).
- Архив «за сегодня» (`VisitsSummary.get`, `period=day&date=today`): 14:53:58 МСК — 20 723 визита → **14:56:29 — 21 451** (пересчёт произошёл) → до 15:07 не менялся, т.е. **≥11 мин без обновления**, притом что сырой трафик шёл. Значит пересчёт НЕ на каждый запрос; интервал между обновлениями ≥10 мин (точная периодичность не выяснена — мерить скриптом, а не заявлять).
- `VisitTime.getVisitInformationPerServerTime` (архив, почасовка) отставал на тот же шаг: последний час в архиве — предыдущий, с частичным заполнением.
- Вывод для пользователя: **событие в отчёте «События» появляется в пределах ~5–15 минут**, а не сразу; в Журнале посещений — сразу.

## Что добавляет задержку сверх архива

- Крон-архивация вместо браузерной (`browser_archiving_disabled_enforce=1`) — ждать до запуска крона.
- Клиентская склейка: если фронт батчит трекинг или шлёт события через свой backend (не напрямую `matomo.php`), задержка возникает ещё до Matomo.
- Кэш страницы отчёта в браузере при обновлении вкладки.

## Как отвечать и как проверять

1. Вердикт первой строкой, затем два слоя (сырые — секунды; отчёты — до ~15 мин), затем цифры замера с датой.
2. UI-рецепт: «Посетители → Журнал посещений»/«В реальном времени» — сырое сразу; «Поведение → События» + сегмент по измерению *Page URL* → contains `<хост>`.
3. Фронт: DevTools → Network → запрос `matomo.php` с `e_c`/`e_a`/`e_n` в момент действия. Запроса нет — виновата не задержка, а разметка.
4. Если события нет и через 20–30 мин — это не задержка отображения, а потеря данных (не тот idSite/URL, отсечение трекером `[Tracker] exclude_requests`, dev-сборка).
5. Периодичность пересчёта (5/15/60 мин) **не угадывать** — измерить: `cd $HERMES_HOME/matomo_weekly && python3 check_archive_freshness.py [минут] [интервал_сек]`.

## Квирк API, на который легко наступить

`Live.getCounters` с `lastMinutes=N` возвращает **список из одного объекта с ключами `visits`, `actions`, `visitors`, `visitsConverted`** — НЕ `nb_visits`/`nb_events`. Чтение `nb_visits` даёт `None` и ложный вывод «Live API не работает». Ключи `nb_*` — у отчётных методов (`VisitsSummary`, `Events`), не у Live-счётчиков за окно.
