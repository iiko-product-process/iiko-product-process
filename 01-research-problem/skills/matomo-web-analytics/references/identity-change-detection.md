# Смена базы идентичности vs потеря трафика (Matomo / iiko)

Задача класса: в ежедневном/недельном отчёте метрики вдруг падают в разы. Первый вопрос —
это уход аудитории или смена правил учёта. Ниже рабочий протокол различения с подтверждённым кейсом.

## Сигнатура (проверено на iiko prod, 2026-10-01)

| метрика | 30.09 (Ср) | 01.10 (Чт) | Δ |
|---|---|---|---|
| `nb_uniq_visitors` | 21 323 | 11 248 | **−47,2%** |
| `nb_visits` | 44 054 | 22 788 | **−48,3%** |
| `nb_users` | 4 660 | 4 573 | −1,9% |
| `nb_actions` | 223 274 | 220 246 | −1,4% |

Тот же день недели до сдвига (24.09, Чт): уники 18 382, визиты 39 086, действия 199 657 —
т.е. к нему действия **+10,3%**, а уники −38,8%. Объём работы не упал, упала «уникальность».

**Правило: уники/визиты вдвое вниз при плоских `nb_users` и `nb_actions` = сменилась база
идентичности.** Не подавать как падение трафика и не объяснять сценарием/релизом продукта.

## Локализация сегментами (обязательный шаг — иначе причина гадательна)

`VisitsSummary.get` + `segment=userId!=` (с uid) и `segment=userId==` (без uid):

|  | 30.09 | 01.10 |
|---|---|---|
| без uid: uniq / visits / actions | 15 092 / 28 786 / 105 226 | 6 254 / **8 933** / 29 072 |
| с uid: uniq / visits / actions | 6 522 / 15 268 / 118 048 | 5 042 / 13 855 / **191 174** |

`actions` с uid + без uid = итог дня (105 226+118 048 = 223 274 ✓) — сегменты корректны.
Сдвиг сидит в сегменте БЕЗ uid (−69% визитов), тогда как действия с uid выросли +62%.
Читается как склейка сессий при раскатке uid (`enable_userid_overwrites_visitorid`):
один человек на телефоне и на десктопе = один visitorId, короткие повторные визиты слиплись.

## Что это меняет в отчёте

- Сравнивать дни по `nb_users` и `nb_actions`; окно «к прошлому дню» давать с явной
  оговоркой о смене базы (кейс: «уники −47%, но пользователей −1,9% и действий −1,4%»).
- Побочные артефакты, которые нельзя читать как поведение: `actions/uniq` скачет
  (10,5 → 19,6), `visits/uniq` растёт («визит удлинился»), доля ночных часов растёт
  (5,3% → 12,9%) — знаменатель упал, а часовая форма перекосилась в пользу утра,
  потому что схлопнулись дневные короткие возвраты. Для выводов по часам брать день
  после стабилизации базы.
- Устройства тоже смещаются (D 60% → 63%): mobile-сессии слипались чаще.

## Как проверить, а не поверить

```bash
cd $HERMES_HOME/matomo_weekly && python3 -u $HERMES_HOME/skills/research/matomo-web-analytics/scripts/detect_identity_step.py 14
```

Печатает по дням users/uniq/visits/actions с дельтами и помечает дни-кандидаты
(`◀ СМЕНА БАЗЫ ИДЕНТИЧНОСТИ?`), затем разложение двух последних дней по uid.
`-u` обязателен (иначе буферизация); запускать через `terminal` — `execute_code` в cron-профиле заблокирован.

Разовый ручной вариант (короткие команды, гейт-фильтр не любит длинные склейки):

```python
fm.api("VisitsSummary.get", "2026-10-01",
       {"showColumns": "nb_uniq_visitors,nb_users,nb_visits,nb_actions"})
fm.api("VisitsSummary.get", "2026-10-01", {"segment": "userId=="})
```

## Сопутствующие квирки того же прогона

- **`uniq=null` у мелочи**: 01.10.2026 — recipe-manage, kiosk-management, payment-gateways,
  purchase-mobile, error. Любой скрипт разбора обязан нормализовать None → 0 до сортировки.
- **Раздвоение пути раздела**: в таблице одновременно `user-profile` (1 857 уник.) и
  `/user-profile` (887 уник.) — похоже на дубль пути; сообщать как «нужен алиас, иначе
  рвётся история раздела», а не складывать молча.
