# Формат выдачи аналитических отчётов (предпочтения пользователя, проверено 2026-10)

Правила для класса задач «анализ путей / связей / сегментов в Matomo» при отдаче результата этому пользователю.
Собраны из явных коррекций в прогоне 01–16.10.2026.

## Один файл, а не рассыпь

- Пользователь просил «собрать один отчёт», когда накопилось много отдельных файлов («слишком много файлов, хочу получить один, чтобы определиться куда идём дальше»). После серии из 10+ файлов — **консолидировать в один MD-отчёт** (сводка → метод → данные → гипотезы → бэклог → ограничения), а сырые CSVs/JSON отдать отдельным архивом по запросу («скинь исходные данные»).
- Отдельные выносы («схемы путей отдельным файлом», «отчёт по домену X») делаются ТОЛЬКО когда пользователь явно просит вынести; иначе всё идёт в один документ.

## Схемы — Mermaid, не ручной SVG

- Пользователь прямо отверг самодельные SVG-диаграммы («это плохо выглядит, сделай в mermaid»). Для схем путей/связей — **`flowchart` в Mermaid** (```mermaid-блоками в MD), рендерится в GitHub/Obsidian/Typora.
- **Тёмная тема**: у Mermaid текст узла берётся из темы вьюера — в тёмной становится белым и сливается со светлой заливкой. Фикс — принудительный тёмный текст на светлых узлах:
  ```
  %%{init: {"theme":"base", "themeVariables": {"primaryTextColor":"#14181f", "lineColor":"#475467", "edgeLabelBackground":"#ffffff"}}}%%
  ```
  (одна директива в начале файла) + у каждого узла `style N fill:#eef2ff,stroke:#3b5bdb,color:#14181f`.

## Любой HTML/SVG-файл — читаем в обеих темах

- Пользователь на тёмной теме: «серый текст слился с белой карточкой». Любой HTML-артефакт делай с `:root`-переменными + `@media (prefers-color-scheme: dark)` (фон, карточка, текст, muted, SVG через `style="fill:var(--…)"`). Muted-текст в светлой теме затемнять до ~#344054, не #667085.

## Устройства — обязательный разрез отчёта по путям

- Пользователь просит не «ещё одну метрику», а ответ «кто с мобильного, кто с компа, где ошибка в брошенных процессах
  и с какого устройства проверять гипотезу». Поэтому в каждом отчёте по путям/сегментам:
  - общий разрез визитов (комп / моб / планшет);
  - **редкие vs регулярные**: главное устройство + «хоть раз с мобильного»;
  - **в таблице сегментов** — колонки `Комп %`, `Моб %`, `Планшет %`, `Хоть раз с моб. %` (по выборке,
    рядом с полными пользователями базы);
  - **по разделам** — доля устройств + обрывы: `abandoned_share_%` (из каких устройств состояли обрывы) и
    `abandoned_%` внутри устройства;
  - **в каждой гипотезе** — строка «Проверять на устройстве» с обоснованием из cross-tab, а не из доли визитов.
- Не подписывать «проверять на двух устройствах» по одной only-визитной доле: если 88% обрывов на компе,
  основная проверка — комп, мобильный — вторичная. Инвентаризация — обратный случай (мобильный хуже).
- В XLSX — отдельные листы `Устройства_общее`, `Устройства_группы`, `Устройства_сегменты`,
  `Устройства_разделы`, `Устройства_обрывы`; в HTML — отдельная вкладка «Устройства».
- Всегда подписывать базу: общий разрез — все визиты; сегменты/группы — выборка пользователей;
  «главное устройство» — по числу визитов, а не роль.

## «Оборвано» — прокси, а не факт

- Метрика «оборвано» = визит закончился на рабочем/глубоком экране, не вернувшись к списку. Пользователь дважды допытывался, что это значит. Один и тот же «сделал и ушёл с экрана» — ТРИ разных случая: (1) бросил, (2) сделал и закрыл (успех, ложно считается обрывом), (3) пауза >30 мин → сессия развалилась (артефакт). Различить их по текущим данным нельзя — нужны событие «сохранено/проведено» + id объекта. **Всегда писать это оговоркой**, не подавать «% обрывов» как факт потерь.

## Цифры на схемах и в тексте

- К каждой схеме/процессу добавлять «сколько пользователей» (охват union по матрице + связка-ядро intersection) — пользователь явно просил («добавь информацию, сколько пользователей используют эти пути»).
- Гипотезы — содержательные и data-backed, без «воды» («не хочу видеть много бесполезного текста»).
