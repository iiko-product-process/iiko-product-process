# Анализ непрерывности сессии: разлогины и возврат на экран

Как ответить на вопросы «сколько пользователей после разлогина возвращаются туда, где работали»,
«какой процент попадает на главную» и «где сессия рвёт сценарий, а где пользователь просто ушёл».
Не путать с общим анализом путей: здесь единица — событие логина и его `prev`/`next` экран.

## Когда использовать

- Нужно оценить проблему «после повторного входа выбрасывает на главную».
- Нужно отделить начальный вход в визит от разлогина посреди рабочего сценария.
- Нужно выбрать, на каких экранах чинить возврат после логина и на каком устройстве проверять.

## Определения

- **Событие логина** — вхождение экрана `/navigator/auth/login` в последовательность визита.
- **Разлогин с рабочего экрана** — у события есть `prev` (экран до логина, не логин) и `next` (экран после).
  Начальный вход в визит (`prev` нет) — не разлогин.
- **Вернулся на тот же экран** — `next == prev`.
- **Вернулся в тот же раздел** — первый сегмент URL `next` совпадает с `prev`; это слабее, чем тот же экран.
- **Попал на главную** — `next == /navigator/home`.
- **Пользователь с разлогином** — у него есть ≥1 событие с `prev`; для «рабочих экранов» исключай `prev = home`.

## Метод

1. Возьми нормализованные последовательности визитов (query/hash/`index.html`/trailing slash убраны,
   подряд идущие повторы схлопнуты). Один нормализатор на все расчёты.
2. Для каждого вхождения логина сохрани `(user, prev, next)`.
3. Считай **две воронки**:
   - **по событиям**: `next` → home / тот же экран / тот же раздел, другой экран / другой раздел;
   - **по пользователям**: первый такой разлогин → home; «ни разу не вернулся на тот же экран»;
     «ни разу не вернулся в тот же раздел».
4. Исключай `prev = /navigator/home` из анализа «рабочих экранов»: иначе home одновременно считается
   и «главной», и «тем же экраном» и завышает обе метрики.
5. Строй таблицу по экранам-источникам: логины, на главную, на тот же экран, в тот же раздел/другой экран,
   в другой раздел. Сортируй по числу логинов; подписывай знаменатель.
6. Устройство накладывай отдельно (доли устройств на экране-источнике), не смешивая с долей возврата:
   устройство объясняет, где проверять, но не заменяет анализ `prev`/`next`.

## Что нельзя путать

- **Агрегированные переходы ≠ события журнала.** В iiko агрегат дал 2 642 перехода на логин,
  а полный журнал выборки — 13 478 событий. Для пользовательских процентов — только журнал.
- **Начальный вход ≠ разлогин.** Если у логина нет `prev`, это старт визита; такие события не входят
  в «разлогин с рабочего экрана».
- **Первый разлогин ≠ все разлогины.** «55% при первом разлогине попали на главную» и «76,9% ни разу
  не вернулись» могут быть одновременно верны: у пользователя несколько логинов.
- **Тот же раздел ≠ тот же экран.** В закупках карточка → список — это возврат в раздел (44%),
  но не в карточку (0,5%); для UX-проблемы важен именно экран.
- **Высокая доля главной сама по себе не проблема**, если до логина пользователь был на главной.
  Смотри на не-главные источники и на долю «вернулся на тот же экран».
- **Не приписывай причину.** Логин в конце визита может быть истёкшей сессией, ручным выходом
  или редиректом; без событий/логов это сигнал, а не доказательство.

## Формат выдачи

1. Контекст: сколько пользователей с логином, сколько с разлогином, сколько с `next`.
2. Две строки итогов: «по событиям» и «по пользователям» — с явными знаменателями.
3. Таблица по экранам-источникам (топ-10–12) с разбивкой home / same screen / same section / other.
4. Вывод: какие экраны чинить первыми и что считать «возвратом» (экран или раздел).
5. Опционально — device overlay и ссылка на `device-segmentation`.

## Скрипт

`scripts/login_return_stats.py` — читает JSONL визитов `{u, s}`, считает событийную и пользовательскую
воронки, печатает итог или JSON:

```bash
python scripts/login_return_stats.py visits.jsonl \
  --login /navigator/auth/login --home /navigator/home
```
