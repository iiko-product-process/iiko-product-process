# Еженедельный Matomo-отчёт iiko (пн, 09:00 МСК)

Запускается cron-джобой каждый понедельник. Рабочая папка: **$HERMES_HOME/matomo_weekly/** (README.md там же).
Скрипты пишут на python3 (heredoc/terminal); **execute_code в cron заблокирован**, запись — только в $HERMES_HOME.

## Шаги

1. **Проверь доступ**: `$HERMES_HOME/matomo_weekly/config.json` должен существовать (base_url + site_id).
   Токен лежит в `$HERMES_HOME/.env` (MATOMO_TOKEN_AUTH) — скрипт fetch_matomo.py читает его сам (env → файл .env → config.json).
   Если config.json нет — ответь пользователю (RU): доступы Matomo не настроены (см. README.md); ничего больше не делай.
2. **Выгрузка**: `cd $HERMES_HOME/matomo_weekly && python3 fetch_matomo.py`
   - Проверь stdout: недели (w1 = последняя полная Пн–Вс, w2 — предыдущая), totals не пустые.
   - Если `days` ≠ 14 или totals пустые/«__error__» — перепроверь config (base_url/token/site_id),
     при повторной ошибке честно сообщи в чат и завершись.
3. **Датированная копия для отправки**: имя файла = дата конца периода данных W1 (воскресенье, ISO ГГГГ-ММ-ДД):
   `D=$(date -d yesterday +%F); cp dashboard.html reports/matomo_weekly_$D.html` (если dashboard.html существует).
   В сообщение прикрепляй reports/matomo_weekly_$D.html; dashboard.html остаётся каноническим рабочим файлом (его правит пользователь).
4. **Инсайты**: прочитай `data.json` и напиши `insights.json` (список объектов `{title, text, bullets[]}`),
   3–6 выводов на русском. Правила:
   - КАЖДЫЙ вывод = факт с цифрами (W1 vs W2, Δ%) + интерпретация + что стоит посмотреть/сделать.
   - Покрыть: уникальные пользователи и визиты (неделя к неделе), день-к-дню (какой будний день просел/вырос),
     устройства и разрешения (сдвиги долей), просадки по часам рабочего дня (сверь часовой пояс отчёта Matomo!).
   - Ничего не выдумывать: нет данных — так и скажи (например «почасовые уникальные Matomo не отдаёт — считаем визиты»).
   - Не писать «вода»; если изменений нет — сказать «без значимых изменений» и указать самые близкие к порогу.
5. **Сборка**: `python3 build_dashboard.py` (обновляет только data/insights-блоки в dashboard.html; правки пользователя в HTML сохраняются).
6. **Финальный ответ** (доставляется в чат): краткое аналитическое заключение:
   - Шапка: «📊 Matomo: неделя к неделе (W1 … – …, W2 … – …)» + 1 строка-резюме.
   - 4–7 маркированных пунктов-инсайтов (цифры + вывод), отдельно «просадки по часам» при наличии.
   - **Форматирование сообщения: между инсайтами — ПУСТАЯ СТРОКА (двойной перенос `\n\n`),**
     каждый инсайт — заголовок + текст + буллеты с новой строки; НЕ склеивать в сплошной текст.
   - Путь к прототипу + строка `MEDIA:$HERMES_HOME/matomo_weekly/reports/matomo_weekly_<ГГГГ-ММ-ДД>.html` (файл уйдёт вложением в Telegram; <ГГГГ-ММ-ДД> — воскресенье W1 из шага 3).
   - Если вложения не поддерживаются — просто путь.

## Pitfalls

- **Уники падают сильнее визитов ⇒ сначала проверь состав аудитории, а не «потерю трафика».**
  Приём (проверен 19.10.2026: уники −9,9%, визиты −2,1%): когортная сверка через
  `UserId.getUsers` с `period=range`, `date=ГГГГ-ММ-ДД,ГГГГ-ММ-ДД`, `filter_limit=-1` →
  два словаря `{uid: nb_visits}`, пересечение по неделям. Дало: 6 269 общих пользователей
  (73% W1) с 77 953 против 78 464 визитов (−0,7%) и «одновизитных» 2 420 против 2 802 (−13,6%)
  — т.е. минус только в разовых заходах первой недели после запуска.
  В `period=range` Matomo этого инстанса **не отдаёт** `nb_uniq_visitors` (только визиты/действия),
  а `api()` из `fetch_matomo_daily` жёстко ставит `period=day` — для range-проверок писать свой
  вызов `urllib` с `period=range` (см. `_wk_range_probe.py` в рабочей папке).
- **Деньги/действия от внешних переходов**: `Referrers.getReferrerType/getWebsites` работают
  (98% — direct). У ntp.msn.com / away.vk.ru бывает 3–7 тыс. действий за один визит
  (бот/превью): ~1,5% визитов дают до 5% действий — упоминать как QA-находку, не как трафик.
- Часовой пояс Matomo: по умолчанию серверный; «рабочий день» интерпретируй по факту пиков на графике, а не по МСК вслепую.
- Ежедневные уники в сумме > недельного уника — нормально (один пользователь в разные дни считается в каждом дне); недельный уник бери из totals.
- Устройства/разрешения могут быть с `nb_uniq_visitors: null` — тогда используй `nb_visits` и оговори.
- Каналы данных могут отсутствовать (плагин выключен) — метод вернёт пусто; в выводе отметь.
- Редактируемость: dashboard.html правится пользователем вручную; НЕ пересобирай с `--fresh` без нужды (сотрёт его правки).
  Проверка, что правки целы: `python3`-скриптом вырезать регионы `data-block`, `insights-block` и все `<div class="insight">…` и сравнить с копией `reports/matomo_weekly_<прошлая дата>.html` — отличаться должны только KPI-числа в статике.
- **Смена разметки (user_id + склейка подроутов) с 01.10.2026**: уники/визиты обратно несопоставимы с неделями до перехода. Признаки: визиты и уники падают в 2–3 раза, а действия и авторизованные (`nb_users`) растут; среднее время на сайте скачет вверх, отказы вниз; у «старой» недели `nb_uniq_visitors` по страницам = `null`, у «новой» — есть. Не писать «падение трафика».
  Приём для честного сравнения: найти внутри W1 день перелома (по часам — обрыв внутри дня) и посчитать **сопоставимый подпериод** (например Пн–Ср до перехода) против тех же дней W2 — только он даёт настоящую динамику.
- **Топ-15 страниц не выровнены между неделями**: `fetch_matomo.py` сортирует W1 по `nb_uniq_visitors` (когда Matomo его отдаёт), а W2 — по `nb_visits`. Пропажа раздела в списке W1 не значит нули — это порог отбора; проверяй по `data.json`/сегментному запросу, прежде чем писать «страница перестала использоваться».
- **Переключение базы внутри W2 ⇒ сравнивать только дни новой базы, остальное в дашборде пометить.**
  Прогон 12.10.2026: W1 = 05–11.10 (вся новая база), W2 = 28.09–04.10 **смешанная** (28–30.09 старый
  счётчик, 01.10 ~11:00 МСК переключение, 02–04.10 новая база). Агрегаты выглядят как «−77% уников,
  −53% визитов», а действий +4,8% — читать их как трафик нельзя. Порядок:
  1) найти день перелома: `python3 -u $HERMES_HOME/skills/research/matomo-web-analytics/scripts/detect_identity_step.py 14`;
  2) взять только дни W2, целиком лежащие на новой базе (тут Пт–Вс), сравнить их с теми же днями W1
     (`VisitsSummary.get`/`Actions.getPageUrls` с `period=range`, date=`2026-10-02,2026-10-04`);
  3) пометить это в `data.json`, чтобы блок просадок в дашборде не показывал шум «−60% везде»:
     `python3 mark_comparable_days.py --break 2026-10-01 --days "Пт,Сб,Вс"` (запускать после
     `fetch_matomo.py`, до `build_dashboard.py`; `--clear` снимает пометку).
     `build_dashboard.py:gen_dips_by_day` и JS `renderHour` читают `meta.comparable_weekdays`:
     чипы строятся только по сопоставимым дням, остальные дни подписаны «сравнение не показано».
     Следующий прогон (W2 = 05–11.10, уже новая база) идёт как обычно — ключа в свежем `data.json` нет.
  4) контрольная сверка «внутри недели»: половина дня после перелома против того же дня W1
     (01.10 12:00–23:00 против 08.10 12:00–23:00 = −7,6%), а утро 01.10 даёт −71% — то есть шаг
     действительно в базе учёта, а не в трафике.
- **«Вклад одного раздела в рост сайта» считать только в ОДНИХ единицах.** Сумма по разделу из `flat=1` (Σ `nb_visits` по префиксу, напр. inventory 18 528) — это визиты ПО СТРАНИЦАМ раздела, они больше числа визитов сайта и не вычитаются из него. Чтобы сказать «сколько дал раздел», берите `VisitsSummary.get` с сегментом `pageUrl=@/<раздел>` за те же недели (визиты, затронувшие раздел: 9 206 против 6 401) и вычитайте их из `totals.visits` обеих недель: 81 589 против 79 739 = +2,3% вместо +5,4%. Формулировка «раздел дал +5 915 при общем +4 655» — ошибка единиц (проверено 02.11.2026: числа выглядели убедительно и были неверны).
- **Шаг раздела с первого дня недели — не «раскатка в понедельник» по умолчанию.** 02.11.2026 inventory вырос +46,9% (18 528 против 12 613) и держался всю неделю, включая выходные (Сб 1 236 против 537, Вс 1 243 против 805), при том что ряд до этого рос три недели (10 341 → 10 730 → 12 613). Признаки реального роста, а не разметки: рост пользователей раздела +32,4% (1 753 против 1 324), все экраны +36…52%, `hits/visit` ниже, а не выше. Причина (конец месяца/раскатка/обучение) по API не устанавливается — отдавать как кандидата на подтверждение команде.
- **Новая разметка приносит экраны вместо `/xxx/index.html` — старые метки не сравнивать.** В W1
  (05–11.10) flat-строк 442 против ~106, а `/navigator/index.html` упал с 66 056 до 305 визитов, потому
  что пришли подроуты (`/navigator/auth/login` 36 398, `/navigator/home` 28 099). «Раздел пропал из
  списка» = смена метки, не нули. Сравнение по экранам строить начиная с первой полной недели новой базы.
- **Единственное сильное отклонение раздела на сопоставимых днях — проверять по экранам.** Прогон
  12.10.2026: `inventory` −30,2% (4 919 → 3 435 визита, Пт–Вс), причём падение равномерно по всем
  экранам раздела (list −29,0%, count/:id/zones −32,3%, zones/:id −27,1%, настройки −32…−36%) —
  это «приходит меньше людей», а не «сломался один экран»; равномерная просадка целого модуля
  подаётся как кандидат на реальный спад/неполную разметку с просьбой к команде подтвердить.
- Каналы/источники в `data.json` могут отсутствовать целиком (плагин выключен) — прямо отмечай в выводах, что причину сдвигов по источникам проверить нельзя.
