# Анализ путей и сегментов пользователей в Matomo

Как понять, как разные пользователи используют продукт: собрать визиты по user id, реконструировать пути,
найти закономерности (маршруты, пары модулей, сегменты пользователей). Проверено на iiko web (idSite=1).

## Когда использовать

- Вопросы вида «как используют продукт разные пользователи», «куда ходят из раздела X», «есть ли пользователи, которые используют несколько частей продукта регулярно».
- Сегментация пользователей по составу используемых модулей/экранов.
- Конвейер: выборка → сбор журнала визитов → нормализация → матрицы/маршруты → сегменты → отчёт.

## Ключевые ловушки (проверено)

1. **Визит ≠ рабочий день.** Сессия рвётся через 30 минут простоя, в полночь и при перезагрузке SPA. Один рабочий день = 2–6 визитов. Для связей между модулями нужна склейка в **«день пользователя»** (uid + дата, разрыв > 4 ч = отдельный блок).
2. **Автоматизированные аккаунты портят картину.** На проде есть аккаунты с 24/7-активностью и повторами одной цепочки 90%+ визитов (мониторинг/автологин), а также пинг-визиты с 1 действием. Их надо выделять и исключать из анализа людей. Критерии (≥2): визитов/активный день > 20; активность в ≥ 18 часах суток; ≥ 50% визитов — повтор одной и той же цепочки; ≥ 30% визитов с 1 действием; почти нулевой разброс длительности.
3. **uid на 100% только с 01.10.2026** (после выката фикса). Раньше — 30–65% анонимных, для сегментации не годится.
4. **Экраны нормализовать**: `/module/index.html` → `/module/`, `:id` уже схлопнуты фронтом; убирать query/фрагменты; подряд идущие повторы одного экрана схлопывать со счётчиком действий.
5. **Матрица «пользователь × модуль» дешевле, чем полный журнал**: `UserId.getUsers` с сегментом `pageUrl=@/<module>` даёт список пользователей модуля за 1 вызов (~5–10 с).
6. **Сегмент из списка uid**: `userId==a,userId==b,…` — проверено до 300 id (4 261 символ) в одном сегменте.

## Пайплайн (скрипты в $HERMES_HOME/scripts/)

1. **Ростер**: `UserId.getUsers` period=range filter_limit=-1 → все uid с визитами/действиями; CSV `roster_<дата>.csv`.
2. **Модули**: `Actions.getPageUrls` flat=1 filter_limit=-1 → агрегация по первому сегменту пути → `modules.json`.
3. **Активность по дням**: `UserId.getUsers` по каждому дню → `day_users.json` → «сколько дней из N активен» (стабильность).
4. **Матрица user × module**: по каждому модулю `UserId.getUsers&segment=pageUrl=@/<module>` → `user_module_matrix.json`, затем `user_module_counts.csv` и `user_module_pairs.csv` (пары модулей + lift = общие/(ожидаемые)).
5. **Пути по визитам**: `Live.getLastVisitsDetails` по дням с `showColumns="userId,visitServerDate,visitLocalTime,visitDuration,actions,actionDetails"`, сегмент по списку uid → нормализованные цепочки экранов с числом действий → `sample_visits_paths.json`, агрегат `user_id;screen;actions`.
6. Дальше (полный прогон): матрица переходов экран→экран, топ n-грамм, сегменты по числу модулей и стабильности, отчёт.

Готовые скрипты пилота: `pilot_step1.py` (ростер/модули/дни), `pilot_step2_matrix.py` (матрица, пары, распределение мультимодульности), `pilot_step3_paths.py` (пути по визитам), `pilot_step4_summary.py`, `pilot_step5_bots.py` (признаки автоматизации).

## Метрики и приёмы анализа

- **Мультимодульность**: распределение пользователей по числу используемых модулей (1 / 2–3 / 4+). Пилот 01–07.10.2026: 14% — 1 модуль, 42% — 2–3, 30% — 4–7, 13% — 8+ (среди 22 топ-модулей).
- **Пары модулей**: общие пользователи + lift; lift ≫ 1 = реальная связка (напр. external-menu + integration, lift 2.5).
- **Переходы**: `Transitions.getTransitionsForPageUrl` (до/после страницы, топ-10) — быстро и по сегменту; полные цепочки — только своим разбором журнала.
- **Точки входа/выхода**: `Actions.getEntryPageUrls` / `getExitPageUrls` + сегмент группы.
- **Действия на экран**: из журнала (счётчик действий на экран в визите) или `Actions.getPageUrls` (nb_hits/nb_visits).

## Объёмы и стоимость (оценка)

- Неделя по всем пользователям: ~9,7 тыс. uid, ~86 тыс. визитов, 1,5 млн действий.
- Матрица по 22 модулям: ~2 минуты (22 запроса).
- Полный журнал по выборке 100–150 uid за 2 недели: десятки тысяч визитов, сбор в фоне 15–20 минут; хранить в JSONL/SQLite, нарезки после — секунды.
- Массовые сегментные запросы отвечают 5–60 с; ставить таймауты ≥120 с, тяжёлое — в фон.

## Редкие пользователи и удержание (проверенный сценарий)

Ключевой продуктовый вопрос — «зачем заходят редкие, почему уходят и где их подцепить». Рабочая схема:

1. **Определить редких** двумя срезами: по классу (визитов < 10 за период → 71% базы на iiko, ≈16% трафика) и по активности (1–2 дня из 13 → 51%).
2. **Удержание по модулям (точки подцепки)**: период делим на две недели W1/W2; для каждого модуля строим отдельные матрицы по неделям (`UserId.getUsers&segment=pageUrl=@/<module>&period=range&date=<неделя>`); считаем долю редких W1, вернувшихся в W2. База возврата — общая доля вернувшихся редких; lift = модуль/база. На iiko 2026-10: база 42.6%; крючки — call-center (64%), documents (58%), external-menu (57%), till-shifts (52%); тупики — user-account (30%), user-profile (39%), navigator (41%).
3. **Поведение редких по журналу**: выборка 300–500 редких (рандом, seed) + 100–150 регулярных для сравнения; тянем `Live.getLastVisitsDetails` только по дням активности (сегменты ≤300 id) — это в разы дешевле, чем весь период.
4. **Что считать**: «зачем пришёл» = модуль с максимумом действий в визите; первый/последний экран визита; набор модулей за визит (однозадачность); медианы действий и длительности; доля визитов с 1 действием; первые переходы.
5. **Приток новых**: пользователи, которых не было в W1, но которые появились в W2 — по модулям → «входные двери» для новых аккаунтов.
6. Скрипты-образцы: `rare_step1_hooks.py`, `rare_step2_behavior.py`, `rare_step3_report.py` в $HERMES_HOME/scripts/.

## Формат выдачи

CSV (Excel-совместимый, «;», UTF-8 BOM) + JSON для повторных нарезок + краткая сводка с выводами.
В имени файла — дата конца периода.
