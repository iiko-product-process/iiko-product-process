# PB Story — шаблон задачи (Product Backlog, Law2)

> **Пример для всех команд, не эталонный.** Формат PB-стори команды «iiko Project Law 2», снятый с реальных задач: ориентир и образец, а не обязательный стандарт шага. Отличие от правил шага 3 (скилл `pb-task-writer`): здесь создание задачи описано через REST-API; в скилле — Atlassian MCP.

Каноническая структура PB-стори команды «iiko Project Law 2».
Выведена из реальных стори PB-7863/7864/7865/7866 (TitanPos), PB-7816 (денежный ящик), PB-7539 (ФПО), PB-7484/7485. Актуализировано: добавлены «Зависимости», «Out of Scope», «Важная информация вне формата».

## Порядок работы над стори (обязательный)

> Приоритет `scoreWSJF` — это ICEG гипотезы шага 2 (`I × C × E × G`), и в конце описания пишется
> короткое обоснование (2–3 строки). Подробно — `skill/SKILL.md`, раздел «Приоритет scoreWSJF».

1. **Пойми срез эпика**, который закрывает стори (см. «Состав доработок» родительского эпика).
2. **Обязательный опрос PO** — если есть пробелы.
3. **Напиши описание** (подтип: функциональная или ресёч).
4. **Создай стори** с Epic Link на родителя.
5. Для функциональной стори, задающей конкретный экран/функционал, — приложи/создай макет (обычно макет делается на уровне эпика).

## Два подтипа стори

### 1. Функциональная стори (доработка)

Цель → Steps / Given-When-Then → Критерии приёмки → (Зависимости / Out of Scope / Важная инфо — по ситуации).

### 2. Ресёч-стори (исследование / spike)

Цель → **Вопросы для исследования** → Критерии приёмки = «письменный вывод по каждому вопросу».

**Маркировка ресёча.** Префикс `[Ресёч]` в начале summary ИЛИ лейбл `research`.

## Текстовый шаблон (копипаст, функциональная стори)

```
h3. Цель

{одна конкретная задача стори: что должно начать/перестать происходить}.

h3. Given (предусловия)

* {предусловие: настройка, страна, состояние}.
* {предусловие 2}.

h3. When (действия)

* {действие кассира/системы 1}.
* {действие 2}.

h3. Then (результаты)

* {ожидаемый результат 1, включая конкретные поля/значения}.
* {ожидаемый результат 2}.

h3. Критерии приёмки

* {измеримый критерий 1}.
* {измеримый критерий 2}.
* {место доработки (плагин/ядро) — по итогам ресёча PB-XXXX, если ещё не определено}.

h3. Зависимости

| Команда / функционал | Серв (да/нет) | Кому обратиться (PO / тимлид) |
| {команда} | да/нет | {имя} |

h3. Out of Scope

* {что сознательно вне стори}.
```

### Ресёч-стори — блок «Вопросы для исследования»

```
h3. Цель

{что именно надо выяснить и зачем — решение какой развилки зависит от ответа}.

h3. Вопросы для исследования

# {вопрос 1 — про механизм/признак/поле}.
# {вопрос 2 — доходит ли сигнал, доступно ли поле через API}.
# {вопрос 3 — место доработки: только плагин или нужен проброс из ядра}.

h3. Критерии приёмки

* Есть письменный вывод по каждому вопросу.
* Зафиксировано место доработки: плагин / ядро / оба.
* Зафиксировано, один корень у симптомов или несколько.
```

## Важная информация вне формата

Если есть инфо, не укладывающаяся в секции выше (решения, оговорки, ссылки на обсуждения), — отдельный блок в конце стори:

```
h3. Важная информация вне формата

* {инфо, не влезающая в шаблон}.
```

## Обязательный опрос при создании

Перед написанием текста стори — обязательный шаг. Если есть пробелы (границы стори, предусловие, конкретное поле/значение, место доработки, приоритет), НЕ додумывай — задай PO вопросы.

Правила (те же, что у эпика):
- **По одному вопросу за раз** через `clarify`.
- **Multiple choice, 2–4 варианта** + «свой вариант».
- После ответа — следующий вопрос, затем применить ответы.

## Логика и покрытие

- **Стори = один срез эпика**, одна законченная ценность или одно исследование. Не смешивать доработку и ресёч.
- **AC измеримы и привязаны к артефакту**: конкретное поле, строка отчёта, номер заказа из Pyrus. «Работает корректно» — не AC.
- **Given/When/Then несут конкретику**, которую RMS не переоткрывает.
- **Покрытие**: каждый AC эпика прослеживается до ≥1 стори.
- **Зависимости**: если стори затрагивает чужую команду/серверный контур — фиксировать в таблице.
