# PB Epic — шаблон задачи (Product Backlog, Law2)

> **Пример для всех команд, не эталонный.** Формат PB-эпиков команды «iiko Project Law 2», снятый с реальных задач: ориентир и образец, а не обязательный стандарт шага. Отличия от правил шага 3 (скилл `pb-task-writer`): здесь макет — обязательный пункт работы, а создание задачи описано через REST-API; в скилле — макет по запросу и Atlassian MCP.

Каноническая структура PB-эпика команды «iiko Project Law 2» (компонент `iikoProjectLaw2`).
Выведена из реальных эпиков PB-7862, PB-7704, PB-7779, PB-7472, PB-6935, PB-7905. Актуализировано: добавлены «Зависимости», «Метрики», «Out of Scope», «Важная информация вне формата» и шаг «Структура на согласование».

## Порядок работы над эпиком (обязательный)

1. **Собери входные данные** (НПА, Pyrus, макет/скриншоты от партнёра, существующие PB/RMS, результаты ресёч).
2. **Обязательный опрос PO** — см. «Обязательный опрос при создании» ниже.
3. **Покажи структуру на согласование** — до создания выведи план: имя эпика + список стори (название + 1 строка «что покрывает»). Создавай задачи только после согласия PO.
4. **Напиши описание** по секциям ниже (обязательные — жирным).
5. **Создай эпик** в Jira (field map ниже) + стори (Epic Link).
6. **Создай HTML-макет** функционала, если готовый макет не приложен.

## Структура описания (секции)

**Жирным — обязательные**; остальные — по ситуации. Порядок фиксирован.

1. **User Story** (если эпик клиентский: «Как X, я хочу Y, чтобы Z»)
2. **Бизнес-контекст / юридическое основание** — НПА и нормативные ссылки + зачем
3. Текущее поведение (AS-IS)
4. Проблема / Цель (+ бизнес-эффект TO-BE)
5. **Состав доработок** — явный перечень прилинкованных стори (декомпозиция)
6. Источники / связанные задачи
7. **ТРИЗ-анализ** — противоречие / ИКР / приёмы / ресурсы
8. **Acceptance Criteria** — Given/When/Then
9. **Зависимости** — таблица: команды, серв, к кому обратиться (см. ниже)
10. Метрики — измеримые метрики успеха
11. Out of Scope — что сознательно вне эпика
12. Этапность (только если реально есть этапы)
13. **Важная информация вне формата** — отдельный блок в конце (если есть инфо, не влезающая в шаблон)

> «Срез конкурентов», «Область применения» — по ситуации (обычно только в discovery/локализационных эпиках).
> «Пользовательский путь», «Блок-схема», «Сценарии прототипа» — артефакты UX/discovery, НЕ секции эпика; при необходимости выносятся в ресёч-стори или в HTML-макет.

## Текстовый шаблон (копипаст)

```
h1. {Страна. Краткое имя эпика}

h2. User Story

Как {роль} в {страна/сегмент},
я хочу {возможность},
чтобы {ценность}.

h2. Бизнес-контекст / юридическое основание

* {НПА с реквизитами: закон, статья, пункт, дата вступления} — что требует.
* {Последствия несоблюдения: штраф, статья КоАП, блокировка продаж}.
* {Партнёрский запрос: Pyrus #idNNN, плагин, версия}.

h2. Текущее поведение

* {как работает сейчас, по пунктам}.

h2. Проблема / Цель

* {чего не хватает / что не так}.
* {цель доработки}.
* {бизнес-эффект TO-BE: что даёт, сколько теряем без неё}.

h2. Состав доработок

# {стори 1} (PB-XXXX) — что покрывает.
# {стори 2} (PB-XXXX) — что покрывает.
# Ресёч: место доработки (плагин/ядро) — PB-XXXX.

h2. Источники / связанные задачи

* [Pyrus #idNNN|https://pyrus.com/t#idNNN]
* [PB-XXXX|https://jira.iiko.ru/browse/PB-XXXX] — {что}
* [RMS-XXXX|https://jira.iiko.ru/browse/RMS-XXXX] — {что}

h2. ТРИЗ-анализ

* Противоречие: {техническое/физическое противоречие, которое снимает решение}.
* ИКР: {идеальный конечный результат}.
* Приёмы: {номера и названия приёмов из 40}.
* Ресурсы (уже есть): {готовые поля/справочники/механизмы}.

h2. Acceptance Criteria

Given {условие}
When {действие}
Then
 * {ожидаемое поведение 1}
 * {ожидаемое поведение 2}

h2. Зависимости

| Команда / функционал | Серв (да/нет) | Кому обратиться (PO / тимлид) |

| {команда 2} | да/нет | {имя} |

* {от чего зависит и на что влияет — если не видно из таблицы}.

h2. Метрики

* {измеримая метрика успеха 1}.
* {измеримая метрика успеха 2}.

h2. Out of Scope

* {что сознательно НЕ входит в эпик}.

h2. Этапность

# Этап 2. {что}.
```

## Обязательный опрос при создании

Перед написанием текста эпика — обязательный шаг. Если в задаче есть пробелы (неясен объём, место доработки, страна/сегмент, приоритет, дефолт, юридическая трактовка), НЕ заполняй их сам — задай PO уточняющие вопросы.

Правила:
- **По одному вопросу за раз** через `clarify`. Никогда не батчить.
- **Multiple choice, 2–4 конкретных варианта** + «свой вариант». Не открытый вопрос, если можно дать варианты.
- После ответа — следующий вопрос, затем применить ответы в текст.

Типичные точки опроса: страна/сегмент; место доработки (вынести ресёч-стори?); приоритет; дефолтное поведение; границы скоупа.

## Структура на согласование (новый шаг)

После опроса PO и до создания задач — выведи план декомпозиции и дождись согласия:

```
Создам:
Эпик: {summary}
Стори внутри:
- {story 1 summary} — {что покрывает}
- {story 2 summary} — {что покрывает}
```

Создавай задачи только после «да». Для тривиальных случаев (1 стори без развилок) шаг можно объединить с опросом. Это не излишний шаг: предотвращает пересоздание/перелинковку при неверной декомпозиции.

## Обязательный макет

После написания эпика — обязательно создать HTML-макет функционала, если готовый макет не был приложен сразу.

Правила:
- Макет = интерактивный HTML-прототип по `claude-design` (2–3 варианта — `sketch`). Один самодостаточный `.html` с инлайн CSS/JS.
- Покрывает основной сценарий из AC: ключевые экраны, состояния (дефолт / ошибка / пусто), кнопки/попапы.
- Сохранить в `/opt/data/mockups/<PB-XXXX>-<slug>/index.html` и отдать путь в чат.
- Если готовый макет приложен — не создавать, в эпик добавить ссылку/вложение.

## Логика и покрытие

- **Эпик = ценность, а не техника.** Бизнес/юр-основание в начале, AC уровня «что видит клиент» в конце.
- **Декомпозиция — строго через Epic Link** (`customfield_11441` у стори = ключ эпика).
- **Каждый AC эпика прослеживается до ≥1 стори**; каждая стори вливается в AC эпика.
- **ТРИЗ обязателен** (правило Vladislav'а).
- **Зависимости обязательны**: любая доработка, затрагивающая чужую команду/серверный контур, фиксируется в таблице с указанием к кому обратиться.
