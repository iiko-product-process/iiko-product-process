## ЭПИК

**Summary:** Шапка iikoweb: контекстный пульт раздела

**Бизнес-контекст / проблема.**
Шапка iiko web сегодня — «полоса настроек», а не пульт раздела: жёсткий бордер отрезает её от контента, связь «ресторан/период → данные страницы» не читается. Продуктовые команды копируют шапку из соседнего раздела — часто некорректно или просто занимая место. При прокрутке длинных таблиц и отчётов контекст (ресторан, период) уходит за экран, и пользователь работает с данными, не видя среза.

**AS-IS.**
1. Шапка — отдельная полоса с жёстким бордером, визуально не связана с разделом.
2. Три группы элементов: выбор ресторана, выбор периода, поиск + кнопки личного кабинета.
3. Нет мультивыбора ресторанов — сравнить точки можно только переключением по одной.
4. Контрол периода без пресетов и группировки, без индикатора пересчёта.
5. При скролле контекст теряется; состав шапки у каждого раздела свой (копии).

**TO-BE / цель.**
Шапка — контекстный пульт текущего раздела на общей с контентом поверхности: показывает только нужное разделу, сразу перерисовывает данные при смене среза, остаётся видимой при прокрутке, состав элементов настраивается, а не копируется.

**Состав доработок (декомпозиция на стори):**

| # | Стори | Что покрывает |
|---|---|---|
| 1 | Поверхность: свести шапку и контент в один блок | убрать жёсткий бордер, общий фон/карточная поверхность, мягкая тень при липкости |
| 2 | Мультивыбор ресторанов | чекбоксы, «Все рестораны», поиск, счётчик при ≥2, группировка по городам/сети, «Применить»/«Отмена»; одиночный режим там, где мультивыбор невозможен (например, инвентаризация на точке) — и это видно по элементу |
| 3 | Новый контрол периода | пресеты Сегодня/Вчера/7 дней/30 дней/Квартал, свой диапазон, группировка по дням/неделям/месяцам, индикатор «пересчитывается», мгновенная перерисовка данных |
| 4 | Липкая компактная полоса при скролле | счётчик ресторанов + период кратко + 1–2 быстрых действия раздела; период не исчезает; ничего не перекрывается |

**Критерии приёмки (эпик).**
- Дано: пользователь в разделе с длинным отчётом. Когда: меняет ресторан или период. Тогда: данные раздела перерисовываются, срез остаётся видимым при прокрутке ≥1 экрана.
- Дано: шапка и контент. Когда: пользователь смотрит на страницу. Тогда: они читаются как один блок (нет «отрезанной полосы»).
- Дано: скролл длинной таблицы. Когда: шапка конденсируется. Тогда: ничего не перекрывается, страница не «дёргается» (CLS ≤ 0,1).

**Метрики / критерии успеха** (из гипотез списка):
- доля отчётных сессий с ≥2 выбранными ресторанами: 0% (функции нет) → ≥10%;
- время установки периода: baseline уточнить → ≤5 с; доля периодов из пресетов → ≥70%;
- доля сессий с прокруткой ≥1 экрана и последующей сменой среза: baseline уточнить → −30%;
- число разделов с неканоничной (скопированной) шапкой → 0;
- мобильные: время до первого изменения среза −30%, отказы 27,5% → −20% (ограничение — мобильная шапка в отдельной стори, если решим);
- CLS ≤ 0,1.

**Зависимости:** ⬜ нужно уточнить — состав участников (дизайн/фронт), разметка событий в Matomo (события шапки и разделов), решение по дизайн-системе (молекулы «шапка»/сайтбар из встречи 15.09).

**Out of Scope (предложение):**
- тумблер «Сравнить с предыдущим периодом» — сначала исследование (h11);
- «большая шапка, уменьшающаяся при скролле» — исследование (h8);
- мобильная/планшетная шапка — отдельная стори (h9), если не войдёт в первую волну;
- кухонный экран планшета повара — другая задача, не путать.

**ТРИЗ-блок (авто):**
- Противоречие: шапка должна вмещать всё управление срезом (ресторан, период, поиск, действия) — и при этом не занимать место у данных и не отвлекать.
- ИКР: шапка показывает ровно тот минимум, который нужен текущему разделу и срезу, а при прокрутке сжимается до контекста среза.
- Приёмы: сегментация (состав по разделам), динамичность (переход «развёрнутая → липкая»), предварительное действие (пресеты периода), универсальность (один компонент с параметрами вместо копий).
- Ресурсы: дизайн-система (молекулы), существующие данные раздела о нужном срезе, экранное время пользователя.

**Источники:** PB-7655; дейли дизайнеров 15.09 и 17.09; встреча по дизайн-системе 14.09; список гипотез «Шапка iiko web» (12 шт.).
**⚡ Разногласие:** в PB-7655 приоритет «3 — Nice to have», на дейли 17.09 шапка названа приоритетом (после релиза ЕГАИС).

## СТОРИ 1 — Поверхность: шапка и контент — один блок

**Тип:** функциональная. **Epic Link:** {эпик} — ставится при создании.
**Цель:** убрать визуальную оторванность шапки от раздела, чтобы ресторан и период читались как часть текущего раздела.
**AS-IS:** шапка отделена жёстким бордером; элементы выглядят как самостоятельная полоса настроек.
**TO-BE:** единая поверхность: общий фон, вместо бордера — мягкая тень/подложка; в липком состоянии — аккуратная тень без скачка макета.
**Критерии приёмки:**
- Дано: любой раздел с шапкой. Когда: страница открыта. Тогда: шапка и контент визуально одно целое (нет жёсткой линии-разделителя).
- Дано: прокрутка. Когда: шапка становится липкой. Тогда: тень появляется без смещения контента.
**Зависимости:** дизайн-система (поверхности/тени), фронт.
**Метрики:** доля сессий, где срез меняют в первые 30 с после входа в раздел: baseline уточнить → +20%.
**Out of Scope:** изменение состава элементов шапки (это стори 2–4).

## СТОРИ 2 — Мультивыбор ресторанов

**Тип:** функциональная.
**Цель:** собирать срез по сети за одну операцию, без переключения точек по одной.
**Критерии приёмки:**
- Дано: пользователь открывает выбор ресторана. Когда: ставит 2+ чекбокса. Тогда: элемент показывает счётчик («3 ресторана»), данные раздела перерисовываются после «Применить».
- Дано: поиск и группировка. Когда: вводит название или выбирает город/сеть. Тогда: список фильтруется/группируется; есть «Все рестораны» и «Отмена» (возврат к прежнему срезу).
- Дано: раздел, где мультивыбор невозможен (инвентаризация на точке). Когда: открывается шапка. Тогда: выбор одиночный и это видно по элементу.
**Зависимости:** API ресторанов, разделы-потребители (перечень уточнить).
**Метрики:** доля отчётных сессий с ≥2 ресторанами: 0% → ≥10%.
**Out of Scope:** массовые операции на мультивыборе (отдельная задача «срез точка/сеть»).

## СТОРИ 3 — Новый контрол периода

**Тип:** функциональная.
**Цель:** ставить типовой срез одним движением и сразу видеть, что данные пересчитываются.
**Критерии приёмки:**
- Дано: открыт контрол периода. Когда: пользователь выбирает пресет (Сегодня/Вчера/7/30/Квартал). Тогда: срез применяется одним действием, данные перерисовываются, показывается индикатор «пересчитывается».
- Дано: нужен нестандартный диапазон. Когда: выбирает даты вручную. Тогда: можно выбрать свой диапазон и группировку (дни/недели/месяцы).
**Зависимости:** API отчётов (перерисовка), разметка событий периода в Matomo.
**Метрики:** время установки периода: baseline уточнить → ≤5 с; доля пресетов → ≥70%.
**Out of Scope:** тумблер «Сравнить с предыдущим периодом» — до результатов исследования.

## СТОРИ 4 — Липкая компактная полоса при скролле

**Тип:** функциональная.
**Цель:** не терять срез при работе с длинными таблицами.
**Критерии приёмки:**
- Дано: длинная таблица/отчёт. Когда: пользователь прокручивает ≥1 экрана. Тогда: сверху остаётся компактная полоса со счётчиком ресторанов, периодом кратко и 1–2 действиями раздела.
- Дано: быстрые действия раздела. Когда: полоса липкая. Тогда: 1–2 главных действия (например, «Синхронизировать меню») доступны из неё.
- Дано: переход «развёрнутая → липкая». Когда: происходит. Тогда: стабильная высота, без дёрганья (CLS ≤ 0,1), ничего не перекрывается.
**Зависимости:** дизайн-система (липкие поверхности), фронт.
**Метрики:** доля сессий с прокруткой ≥1 экрана и сменой среза: baseline уточнить → −30%; CLS ≤ 0,1.
**Out of Scope:** «большая шапка, которая уменьшается» — исследование (h8).
