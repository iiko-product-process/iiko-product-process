# PB Task Writer — продуктовые требования и задача в Jira (шаг 3)

## Overview

Скилл превращает ИИ в стандартизированного интервьюера и оформителя **продуктовых требований** для продукт-оунеров (PO) iiko. Цель: PO отдаёт всю доступную информацию, скилл задаёт вопросы по пустым блокам, структурирует ответы и создаёт в Jira Epic + Stories по единому шаблону, чтобы задачи между командами выглядели одинаково. ИИ **не принимает продуктовых решений** — он опрашивает, структурирует, подсвечивает пропуски и генерирует черновики; решения принимает PO.

## When to Use

- PO просит «составь задачу», «оформи эпик/стори», «напиши PB story», «разбей эпик на стори».
- PO запускает скилл напрямую (по имени) и скармливает вход.

Не для: редактирования существующей задачи без создания новых; валидации проблемы/гипотез (шаги 1–2 процесса).

## Порядок работы (обязательный)

### Шаг 0 — Получить вход

PO скидывает всё, что есть: ссылки на задачи Jira, страницы Confluence, ссылки на макеты в Figma (сам факт наличия — Figma к Hermes не подключаем), кликабельные прототипы, текстовое описание, файлы-вложения. Прочитай доступное через Atlassian MCP (Jira/Confluence) и вложения чата. Не требуй то, чего PO не дал.

### Шаг 1 — Разобрать вход

Разложи входящую информацию по блокам шаблона (таблицы ниже). Отметь: ✅ заполнено, ⬜ пусто, ⚡ противоречие (в одном месте так, в другом иначе), 🔍 неточно/нужно уточнить. **Не выдумывай отсутствующие факты** — неизвестное помечай «нужно уточнить».

### Шаг 2 — Тип и системные поля

1. **Эпик или стори?** Если PO не сказал явно — уточни.
2. Если стори — **тип: функциональная или ресёч (исследование)?** Спрашивай явно всегда: «это доработка или нужно что-то доисследовать?». Это меняет структуру стори.
3. Если создаёшь **одиночную стори** (не в рамках декомпозиции эпика) — спроси: **«Привязать к существующей задаче?»** (эпик/стори/что угодно). Да + эпик → Epic Link; да + другая задача → связь (link); нет → без родителя.
4. **Component** и **Labels** — спрашивай **каждый раз**, по одному вопросу, простой формулировкой («Какой Component ставим в Jira?») и, если известны, с вариантами. **Component часто оставляют пустым** — всегда давай вариант «Пропустить / не заполняем». Если для этого PO уже известно значение (профиль ниже / прошлые запуски), подставь его первым вариантом, но всё равно подтверди.

### Шаг 3 — Опрос по пустым блокам

Иди по блокам в порядке: контекст → AS-IS → TO-BE → сценарии → зависимости → остальное.

Правила опроса:
- **По одному вопросу за раз** через `clarify`. Никогда не батчить.
- **Перед каждым вопросом показывай прогресс в процентах** (напр. `🔵 ~40%`), чтобы PO понимал, сколько ещё осталось. Оценка примерная — не страшно, если сдвинется.
- Каждый вопрос = **2–3 конкретных варианта** + вариант **«Пропустить — этого нет в этой задаче»**. Свободный ответ PO введёт через опцию «Other».
- Блок уровня «по ситуации» спрашивай только если видно, что он применим к задаче (напр. пользовательский путь — для UX-задач; НПА — для legal-задач).
- Быстрый путь: если PO говорит «я всё уже дал, не спрашивай» — переходи к структурированию, но в отчёте пометь незаполненные ядро-блоки.
- Отдельно всегда спроси: **«Есть ли дедлайн?»** (→ поле Jira duedate).

### Шаг 4 — Согласовать структуру (декомпозиция)

До создания задач выведи план и дождись «да»:

```
Создам:
Эпик: {summary}
Стори внутри:
- {story 1 summary} — {что покрывает}
- {story 2 summary} — {что покрывает}
```

Декомпозицию предлагает скилл, но решение — за PO. Каждая стори = одна законченная ценность (≈ один спринт), не «frontend/backend/API». Если задача явно больше спринта или содержит несколько независимых результатов — предложи разбить.

### Шаг 5 — Создать в Jira

Через Atlassian MCP (`jira_create_issue`). Проект **всегда `PB`**, если PO не попросил иного.

**Метка происхождения — обязательна.** В каждую созданную задачу (эпик и все стори) добавляется label `Hermes`.
Это единственный след того, что задача заведена с Hermes, а не руками: по нему строятся выборки «сколько задач
заводим с ИИ» и сверка с задачами, созданными вручную. С PO метка не обсуждается и не заменяется — она
добавляется всегда, вместе с остальными labels команды.

Field map (PB):
- Epic: issuetype `14`; **Epic Name** = `customfield_11443` (обязателен, иначе HTTP 400).
- Story: issuetype `15`; **Epic Link** = `customfield_11441` = ключ родительского эпика (единственная связь стори→эпик; стори без него = орфан).
- Component — значение из ответа PO (Law2 = `iikoProjectLaw2`).
- Labels — из ответа PO; для Law2 страна обязательна (`Kazakhstan`, `Belarus`, `Uzbekistan`, …) + домен + тип.
  **Плюс всегда `Hermes`** (см. «Метка происхождения») — в эпике и в каждой стори.
- Priority: `1` = Must have (юр. обязательное/блокер), `2` = Should have.
- Reporter — ставится автоматически по подключению PO. Assignee — не ставить. Duedate — если PO указал дедлайн.

Если Jira возвращает ошибку по полю (неверный id / «required») — проверь id через существующую задачу (`jira_search`/`jira_get_issue`) и поправь.

### Шаг 6 — Прототип (по запросу)

Спроси: **«Нужен HTML-прототип?»**. Если да и готового макета не было — сгенерируй один самодостаточный `.html` (inline CSS/JS) в стиле iikoWeb (ниже). Покрывает основной сценарий из критериев приёмки: ключевые экраны, состояния (дефолт/ошибка/пусто), кнопки/попапы. Отдай путь в чат + ссылку в задачу.

### Шаг 7 — Итоговый отчёт

В конце выведи сводку:
- ✅ что заполнено;
- ⚠️ что PO пропустил и почему;
- ❓ открытые вопросы (не решаются сейчас);
- ⚡ разногласия/противоречия во входе;
- 🔍 что помечено «нужно уточнить»;
- ссылки на созданный эпик и стори + прототип.

## Единая модель блоков

Легенда: 🔒 системное (спрашиваем всегда) · ❓ спросить (можно пропустить) · ➖ по ситуации.

### Epic

| Блок | Обязательность |
|---|---|
| Summary (название) | 🔒 |
| Component / Labels (вкл. страна) | 🔒 |
| Бизнес-контекст / проблема (+ НПА, если релевантно) | ❓ |
| Цель / бизнес-эффект (TO-BE) | ❓ |
| Текущее поведение (AS-IS) | ❓ |
| Состав доработок (декомпозиция → стори) | 🔒 (скилл формирует, PO согласует) |
| Критерии приёмки (Дано/Когда/Тогда) | ❓ |
| Зависимости (таблица: команда / серв / к кому обратиться) | ❓ |
| Источники / связанные задачи | ❓ |
| Регуляторные требования (НПА) | ❓ (Law2 — всегда; остальные — спросить) |
| Метрики / критерии успеха | ➖ |
| Out of Scope | ➖ |
| Область применения (страна/продукт/модуль) | ➖ |
| Этапность / план раскатки | ➖ |
| Срез конкурентов | ➖ |
| Требования FR/NFR | ➖ |

## ТРИЗ-анализ (авто)

Для эпика скилл всегда сам формирует ТРИЗ-блок: противоречие → ИКР → приёмы → ресурсы. Если данных не хватает — задай PO уточняющий вопрос с вариантами ответов, не выдумывай.

## Регуляторика (НПА)

НПА = нормативные правовые акты (законы, приказы, постановления — «регуляторика»). Юридические поля необязательны для большинства команд, но скилл о них **спрашивает** — простой формулировкой и с расшифровкой, т.к. не все знают термин: «Есть ли в задаче нормативные требования — законы/НПА (например, 171-ФЗ об обороте алкоголя), которые нужно указать?». Для Law2 блок «Бизнес-контекст / юридическое основание» обязателен всегда; для остальных — спроси один раз. Юридическую корректность проверяет специалист — скилл только структурирует и помечает «проверить юристом».

## Профиль команд (Component / Labels)

Спрашивай каждый раз, просто: «Какой Component ставим в Jira?» — с вариантами, если известны, и всегда с вариантом «Пропустить / не заполняем» (Component часто оставляют пустым). После первого ответа PO подставляй известное значение как дефолт, но всё равно подтверждай.

Известные команды (дополняется по ходу пилотов):

| Команда | Component |
|---|---|
| Law2 (iiko Project Law 2) | `iikoProjectLaw2` |

## Стиль артефактов (iikoWeb)

- Цвета: синий `#448AFF`, красный `#FF5252`, зелёный `#14B456`.
- Компоненты ДС: Select, Button, List (иконки/радио/чекбоксы слева-справа, над/подтекст), таблица с футером итогов.
- Прототип — единый стиль во всех экранах; один `.html`, без внешних зависимостей.

## Честность (критично)

- Разделяй **факты / решения команды / гипотезы / предположения**.
- Не придумывай отсутствующее. Сомневаешься — пиши «нужно уточнить», не додумывай.
- Свободные/развёрнутые ответы PO («Other») **структурируй и сократи до сути**: убери лишние слова и воду, сохранив смысл. Не переноси поток текста в задачу дословно и не добавляй отсебятины.
- После генерации всегда: «вычитай задачу после скилла» — итоговый текст PO проверяет перед согласованием.

## Common Pitfalls

1. **Создавать задачи до согласования структуры** (шаг 4). Всегда жди «да» PO — иначе пересоздание/перелинковка.
2. **Батчить вопросы** — скилл должен задавать по одному. PO теряется в простыне из 19 вопросов.
3. **Делать обязательным блок, которого нет** — напр. пользовательский путь в задаче про перевод текста. Всегда давай «Пропустить — этого нет».
4. **Выдумывать факты** — особенно НПА/номера/даты. Помечай «нужно уточнить».
5. **Забывать про ресёч-подтип** — спрашивай явно «доработка или исследование?».
6. **Забывать Component/Labels** — у каждой команды свои; спрашивай каждый раз.
7. **Генерировать Mermaid-схемы в MVP** — не делай, только спрашивай «нужна ли схема?».
8. **Смешивать доработку и ресёч в одной стори** — это разные подтипы.

## Verification Checklist

- [ ] Вход разобран по блокам; незаполненное и противоречия зафиксированы.
- [ ] Тип (эпик/стори; функциональная/ресёч) определён.
- [ ] Component и Labels спрошены у PO.
- [ ] Опрос шёл по одному вопросу, с вариантами + «пропустить».
- [ ] Декомпозиция показана PO и подтверждена до создания.
- [ ] Задачи созданы в проекте PB, стори прилинкованы к эпику (Epic Link).
- [ ] В эпике и во всех созданных стори стоит label `Hermes`.
- [ ] Прототип — только если запрошен; в стиле iikoWeb.
- [ ] Итоговый отчёт выдан: заполнено / пропущено / вопросы / разногласия / «нужно уточнить».
- [ ] Скилл ничего не выдумал; сомнительное помечено.
