## Приложение В. Чек-лист перед передачей в разработку

Используй на «Шаге 8. Ревью» и перед формированием Jira-задач (Шаг 9). Все пункты должны быть закрыты «да» или явно помечены как неприменимые (N/A) — иначе задача не готова.

### Business

- [ ] Проблема сформулирована без маркетинговых фраз
- [ ] Понятен пользователь / сегмент
- [ ] Понятен ожидаемый результат (критерий успеха)

### Functional

- [ ] Описан happy path
- [ ] Описаны значимые ошибки
- [ ] Описаны релевантные edge cases
- [ ] Есть критерии приёмки — проверяемый чек-лист (Given/When/Then — дополнительно) на каждый ключевой сценарий
- [ ] Критериев и сценариев достаточно, чтобы AQA написала автотесты

### System

- [ ] Перечислены все участвующие системы
- [ ] Описаны взаимодействия между ними
- [ ] Есть sequence diagram (если интеграции/асинхронность/несколько сервисов)
- [ ] Описаны API / события / webhooks

### Data

- [ ] Определены источники данных
- [ ] Определены обязательные поля и формат
- [ ] Описана валидация
- [ ] Учтено изменение существующих данных / миграции (если применимо)

### Technical

- [ ] Определены НФТ (только применимые: производительность, доступность, безопасность и т.д.)
- [ ] Учтены роли и права доступа
- [ ] Учтены зависимости (команды, релизы, внешние системы)
- [ ] Учтены timeout / retry / rate limits внешних интеграций

### Delivery

- [ ] Задача декомпозирована на реальные задачи (не копия разделов спеки)
- [ ] У каждой Jira-задачи есть Acceptance Criteria
- [ ] Понятны зависимости между задачами
- [ ] Нет незакрытых критических вопросов
- [ ] Feature flag / rollout / обратная совместимость — описаны, если применимо

### Стоп-правила

- Если остался вопрос, **влияющий на реализацию** — не помечай документ approved.
- Если пункт «надо уточнить» — вернись на соответствующий шаг, а не оставляй «потом».
- Не заводи Jira-задачи до явного аппрува пользователя («Создать?»).
