# Шаг 2 — «Формирование и приоритизация гипотез»

Папка шага 2 продуктового процесса iiko: инструмент, данные и описание работы.

## Что можно сделать

- **Собрать гипотезы по проблеме** — скилл `iiko-hypotheses`: формулирует по формату («Если …, тогда …, так как …», метрика baseline → target, источник данных), пишет список в `data/lists/problema-<слаг>.json`, пересобирает сводный файл и отдаёт готовый HTML — список уже в прототипе.
- **Оценить и приоритизировать** — прототип-калькулятор `prototype/ocenka-gipotez_kalkulyator.html`: карточка гипотезы, критерии I · C · E с анкерами, цели и веса, итоговый балл `I × C × E × G`; редактирование — кнопкой ✎, отметка «в работу», ключ задачи Jira — в колонке Jira.
- **Спросить Hermes прямо со страницы** (в веб-режиме) — поле «🤖 Hermes: …» → «Спросить Hermes»: агент дополняет список, страница сама перечитывает результат.
- **Создать задачи в Jira** — кнопка «Создать задачи в Jira через Hermes» по отмеченным гипотезам → задачи типа `Story` в проекте `PB`.
- **Поднять веб-режим на своём сервере** — один скрипт `install/install.sh`: правки списков сохраняются автоматически и коммитятся в репозиторий; подробности — в `install/README.md`.
- **Держать все гипотезы в одном месте** — общий список `data/lists/obshiy-spisok.json` работает как реестр: свои гипотезы + копии из списков по проблемам.

## Что должно получиться в итоге

**Приоритизированный список гипотез**, готовый к описанию и передаче в дизайн или разработку. Приоритет учитывает влияние на бизнес-метрики, сложность и риски, соответствие годовым целям компании и квартальным планам команды.

Что должно появиться по плану внедрения шага: единый шаблон гипотезы; правило «гипотеза без плана проверки не берётся в спринт»; отбор 1–3 гипотез в спринт раз в 2 недели с фиксацией решения; тип и способ проверки у каждой гипотезы; критерии оценки и скилл приоритизации; протокол проверки.

Форма результата:

- список гипотез — файл в `data/lists/` (общий `obshiy-spisok.json` или по проблеме `problema-<слаг>.json`); это источник истины;
- каждая гипотеза — формулировка, метрика, источник данных, оценки I/C/E, цели с α, отметка «в работу», ключ Jira;
- сводный `data/hypotheses.json` — все гипотезы одним файлом (собирается автоматически, руками не правится).

## Как устроен шаг

**Операции шага** (с доски процесса):

1. **Формулировка гипотез** — вход: результаты исследований Шага 1 (проблема as is / to be, сегмент, конкуренты); владелец: владелец продукта; ритм: в спринт, раз в 2 недели; выход: список гипотез.
2. **Определение критериев оценки** — вход: критерии оценки (у каждой команды были свои); владелец: команда; выход: единый набор критериев и скилл оценки.
3. **Приоритизация гипотез** — продакт; выход: приоритизированный список, сопоставленный с целями компании и команды.
4. **Выбор гипотезы для проверки** — продакт; раз в 2 недели; выход: 1–3 выбранные гипотезы.
5. **Выбор способа проверки** — продакт; выход: тип проверки (существование боли / спрос / понятность / поведение и метрики / реализуемость).
6. **Проверка гипотезы** — продакт; выход: подтверждение или опровержение + список гипотез в реализацию.

**Боли, которые закрывает шаг:** гипотезы проверяются не всегда; нет общих стандартов формулировки; не всегда делаются прототипы; не все считают эффект.

## Инструмент: калькулятор оценки гипотез

**Формула:** `Балл = I × C × E × G`, где `G = Σ (αⱼ × gⱼ)` — коэффициент цели компании. Гипотеза на приоритетную цель может обойти более «лёгкую» гипотезу на цель низкого веса: порог кроссовера `g_B / g_A > база_A / база_B`.

**Три вкладки:**

1. **Оценка гипотезы** — карточка формы: слева «Описание гипотезы» (формулировка «Если …, тогда …, так как …», метрика baseline → target, источник данных) и «Критерии оценки» (шкалы I · C · E с анкерами под информерами), справа — итоговый балл с разбором формулы и кнопки. Ниже — карточка списка гипотез.
2. **Цели и веса** — редактируемый список целей (название + коэффициент) и референс уровней с правилами заполнения.
3. **Как считается** — формула, порог кроссовера, анкеры критериев, правила и защита от накрутки.

**Работа со списком:**

- в колонке «в работу» отмечаются гипотезы, над которыми будет вестись работа;
- редактирование гипотезы — только кнопкой ✎ (клик по названию ничего не открывает);
- в колонку «Jira» вписывается ключ созданной задачи — превращается в ссылку на jira.iiko.ru;
- в строке заголовка — кнопка **«Создать задачи в Jira через Hermes»** (активна, когда что-то отмечено): собирает пакет с формулировкой, метрикой, оценкой, целью и α, и передаёт его в Hermes для создания задач в проект `PB` типом `Story`;
- внизу — работа с файлами списка: **«Открыть список…»**, **«Сохранить список»**, **«Синхронизировать с Hermes»**, экспорт CSV и печать в PDF.

## Серверный режим (правки прямо в прототипе)

Прототип умеет работать как веб-приложение: тогда списки хранятся не в браузере, а на сервере — в файлах этого репозитория, и любая правка (гипотеза, оценка, отметка «в работу», ключ Jira) сохраняется автоматически и уезжает в GitHub коммитом.

**Запуск сервиса:**

```bash
cd 02-hypotheses
python3 server/serve.py --port 8330                          # без авторизации (для локальной проверки)
python3 server/serve.py --port 8330 --auth hypo:пароль       # с HTTP Basic авторизацией
```

Что умеет сервис (только стандартная библиотека Python):

| Маршрут | Что делает |
|---|---|
| `GET /?list=<id>` | отдаёт прототип со встроенным списком |
| `GET /api/lists` | оглавление списков |
| `GET /api/lists/<id>` | список целиком |
| `PUT /api/lists/<id>` | сохранить список: пишет `data/lists/<id>.json`, пересобирает сводный файл, коммитит и пушит |
| `POST /api/lists` | создать список: `{"title": "...", "problem": "..."}` |
| `POST /api/ask` | запрос к Hermes: `{"list": "<id>", "text": "<запрос>", "mode": "ask\|task"}` → `{task}` (202), статус — `GET /api/ask/<task>`; один запрос за раз, таймаут 15 мин. `ask` — кнопка «Спросить Hermes» (дополнить список), `task` — кнопка «Создать задачу» (одна задача Jira по отмеченным гипотезам) |
| `GET /api/ask/<task>` | статус запроса: `running` / `done` / `error` / `timeout` и `message` (последняя строка ответа агента) |
| `GET /healthz` | проверка живости |

**Что видно в интерфейсе в этом режиме:** вместо файловых кнопок — боковое меню списков (открывается кнопкой-бургером в шапке: общий список и списки по проблемам, с числом гипотез и бейджами) и статус сохранения («есть изменения…» → «сохраняю…» → «сохранено ✓ 14:18»). Списки открываются по ссылке `/?list=<id>`, ссылку можно отправить продакту.

**Канал «сайт → Hermes»:** над таблицей списка есть поле «🤖 Hermes: …» и кнопка «Спросить Hermes» — продакт пишет запрос словами («добавь гипотезу про мобильную шапку»), сервис запускает агента скилла `iiko-hypotheses` в фоне, страница показывает «Hermes думает… N с» и по завершении сама перечитывает список. Итог на странице — последняя строка ответа агента, поэтому ответы заканчиваются одной строкой-выводом.

**Порт:** сервис слушает 8330 — это первый порт из диапазона, который окружение контейнера держит под прототипы (`PROTO_PORT_RANGE=8330-8339`, `/run/s6/container_environment`). Чтобы ссылку стало видно с рабочих машин, этот порт должен быть опубликован на хосте (одна строка в docker-compose: `- "8330:8330"`); после этого включаем авторизацию (`--auth`) и шарим ссылку с логином и паролем.

**Держит сервис живым:** cron-задача `hypoproto-watchdog` — поднимает сервис после перезапуска сервера и заодно коммитит правки списков, сделанные не через сервис.

## Установка на сервер сотрудника

Прототип ставится на «свой» сервер одной командой — скрипты и чек-лист лежат в `install/`:

```bash
cd 02-hypotheses
bash install/install.sh --port 8330                      # личный сервер
bash install/install.sh --port 8330 --auth iiko:пароль   # общий сервер
```

Что делает `install.sh`: проверяет зависимости (python3 ≥ 3.8, только стандартная библиотека), создаёт каталоги данных и пустой общий список, при `--auth` создаёт файл авторизации, ставит автоподъём в cron (каждые 15 минут и при загрузке), поднимает сервис, проверяет его и печатает ссылку для сотрудника. После установки — чек-лист из 6 пунктов (сохранение правки, меню списков, автоподъём, коммит в git).

Подробно: **`install/README.md`** — требования, ручная установка (в том числе пример systemd-unit), доступ снаружи и firewall, где лежат данные и как устроено «все гипотезы в одном месте», обновление, переезд на другой сервер, диагностика. Скрипты: `install/hypoproto_ensure.sh` (автоподъём, тихий, когда всё в порядке), `install/hypoproto_restart.sh` (перезапуск после правок `serve.py`).

## Проблемные карты

Перед списком гипотез по проблеме собирается карта: `data/problems/<слаг>.md` — постановка (обычно из Jira), «как сейчас», требования, цитаты встреч с датами, что не путать, открытые вопросы. Список ссылается на карту полем `list.problemNote`, в интерфейсе показывается короткая формулировка проблемы.

## Два формата списков

| Формат | Файл | Что внутри |
|---|---|---|
| **Общий список** | `data/lists/obshiy-spisok.json` | Всё, что создано или внесено продактом вручную — не привязано к одной проблеме. |
| **Список по проблеме** | `data/lists/problema-<слаг>.json` | Гипотезы по одной конкретной проблеме; в метаданных хранится формулировка проблемы. |

Сводный `data/hypotheses.json` собирает оба формата в один файл: список гипотез с пометкой, из какого списка каждая пришла.

## Связь с другими шагами

- **Вход:** из шага 1 — карточка проблемы (`data/problems/<слаг>.md`), от неё строятся гипотезы «Если …, тогда …, так как …»; данные и примеры конкурентов/бенчмарков берутся из той же карточки.
- **Выход:** приоритизированный список гипотез; отмеченные в прототипе гипотезы уходят пакетом (формулировка, метрика, оценка, цель с α) в шаг 3 — кнопка «Создать задачи в Jira через Hermes», оформление в Epic/Story делает скилл `pb-task-writer`.
- **Куда складывать артефакты:** в папку задачи `artifacts/<слаг>/02-гипотезы/` (структура — скилл `task-workspace`).

## Когда брать скилл

| Скилл | Когда использовать | Когда не использовать |
|---|---|---|
| `iiko-hypotheses` | Есть подтверждённая проблема с вариативными решениями: сформулировать гипотезы по формату, оценить I · C · E, приоритизировать, завести список и открыть его в прототипе | Проблема не подтверждена — шаг 1; решение очевидно и вариативности нет — сразу шаг 3; нужен статус разработки — шаг 6 |

## Что лежит в папке

| Путь | Что это |
|---|---|
| `prototype/ocenka-gipotez_kalkulyator.html` | **Прототип** — калькулятор оценки гипотез. Один файл, открывается двойным щелчком, данные хранит локально в браузере. |
| `data/lists/` | **Списки гипотез**: `obshiy-spisok.json` — общий список, `problema-<слаг>.json` — список по одной проблеме. Источник истины. |

| `data/problems/` | **Проблемные карты** по слагам: постановка проблемы, «как сейчас», требования, цитаты встреч, открытые вопросы. На карту ссылается список полем `list.problemNote`. |
| `data/README.md` | Формат файлов списков. |
| `skill/SKILL.md` | **Скилл для Hermes** `iiko-hypotheses`: как собирать гипотезы по формату прототипа и открывать их в нём. |
| `scripts/aggregate.py` | Пересобирает `data/hypotheses.json` из списков. |
| `scripts/sync_general.py` | Держит общий список полным: копирует в него гипотезы из списков по проблемам, не затирая правки, сделанные в интерфейсе позже источника. |
| `scripts/build_prototype.py` | Собирает HTML со встроенным списком (`build/<id>.html`, папка `build/` создаётся скриптом и в git не хранится) — открывается сразу с нужными гипотезами. |
| `scripts/export_task_list.py` | Выгружает список в markdown-дубль внутрь папки задачи (`artifacts/<слаг>/02-гипотезы/список-гипотез.md`). |
| `install/` | Установка сервиса на сервер сотрудника: `install.sh`, `hypoproto_ensure.sh` (автоподъём), `hypoproto_restart.sh`, `README.md` с чек-листом. |
| `server/serve.py` | Веб-режим: списки на сервере, правки сохраняются и коммитятся автоматически; канал «сайт → Hermes». |
