# Гипотезы Шага 2: собрать список и открыть его в прототипе

Репозиторий **iiko-product-process** — локальная копия `/opt/data/iiko-product-process` (ветка `main`), папка шага — `02-hypotheses/`.

## Когда применять

- «Продакт принёс проблему — собери гипотезы», «нужны гипотезы по проблеме …».
- «Добавь гипотезы в общий список», «внеси эти гипотезы в список».
- Пользователь прислал JSON из прототипа (кнопки «Сохранить список» / «Синхронизировать с Hermes») — надо положить его в репозиторий.
- «Открой список гипотез», «покажи, что уже есть по гипотезам», **«дай ссылку на список»**.

## Главный результат — короткое сообщение и ссылка

- Прототип открывается как веб-сервис: **`http://hermes.iiko.ru:8330/?list=<id>`** (запасной адрес — `http://10.10.8.10:8330/?list=<id>`). Порт 8330 взят из диапазона под прототипы (`PROTO_PORT_RANGE=8330-8339`), наружу он проброшен — от ИТ ничего не нужно.
- **Отдавай результат так: короткое резюме + ссылка отдельной строкой.** Длинные сообщения с вложениями десктоп-клиент пользователя иногда теряет (проверено 22.09 и 29.09) — поэтому собранный HTML присылаем файлом **только если сервис недоступен**.
- Если сервис не отвечает: `cd /opt/data/iiko-product-process/02-hypotheses && python3 server/serve.py --port 8330` (обычно его сам поднимает watchdog `/opt/data/scripts/hypoproto_ensure.sh`, cron `c5c3e550126c`, каждые 15 минут).

## Где искать контекст проблемы (делать ДО гипотез)

1. **Заметки и расшифровки встреч:** `python3 /opt/data/notes/.index/notes_search.py "<запрос>"` (скилл `notes-search`). Ищи по ключевому слову и синонимам («шапка», «навигация», «сайтбар»), отдельно — по свежим расшифровкам в `Транскрибации/`.
2. **Jira:** `jira_search` с `text ~ "<слово>" AND project = PB` — постановки, PB Design, эпики; у найденной задачи смотри `description` целиком (там требования и критерии приёмки).
3. **Проблемная карта:** собери `data/problems/<слаг>.md` — постановка, «как сейчас», требования, цитаты из встреч с датами, что НЕ путать (похожие поверхности), открытые вопросы под уточнение.
4. **Сначала покажи пользователю формулировку проблемы**, только потом гипотезы. Каждый факт — со ссылкой на источник (файл заметки, ключ Jira). Ничего не выдумывать.

## Формат гипотезы (обязательный)

1. **Формулировка** строго «Если …, тогда …, так как …» — одно предложение. Не «улучшить онбординг», а «Если …, тогда …, так как …».
2. **Метрика** — `baseline → target`. Baseline берём из данных, которые есть; если данных нет — пишем «baseline уточнить».
3. **Источник данных** — откуда возьмём метрику (дашборд, выгрузка, лог, интервью, прототип).
4. **Оценка ICE (1–10)** по анкерам:
   - **I — влияние:** 1–2 косметика; 3–4 эффект виден, но метрику цели не двигает; 5–6 сдвиг метрики цели на 1–3%; 7–8 на 3–10%; 9–10 больше 10% или разблокирует цель целиком.
   - **C — уверенность:** 10 подтверждено данными/АБ; 8 данные + интервью или бенчмарки; 6 бенчмарки и экспертиза без пользователей; 4 только экспертное мнение. **Ниже 4 (40%) — гипотеза идёт в research, а не в спринт**; C без данных не завышать выше 6.
   - **E — лёгкость:** 10 меньше 1 SP; 8 = 1–3 SP; 6 = 3–8 SP; 4 = 8–20 SP; 2 больше 20 SP или несколько команд.
5. **Цель и α:** 1–2 цели из `goals` того же файла списка; α — доля эффекта (Σα = 1). Эффект не связан ни с одной целью — массив целей пустой, применится базовый коэффициент 1.0.
6. **Итог:** `Балл = I × C × E × G`, где `G = Σ αⱼ × gⱼ`; веса `g` берём из файла, не меняем.
7. **Автор (`by`)** — обязательное поле: гипотезы, которые предлагает агент, пишем с `"by": "hermes"` (в интерфейсе — бейдж «🤖 Hermes»); гипотезы, добавленные человеком прямо в форме прототипа, получают `"by": "human"` автоматически (бейдж «✍️ вручную»). Не переставляй авторство при правках — оно про то, кто предложил гипотезу.

## Порядок работы

### A. Гипотезы по проблеме (основной сценарий)

0. **Помни про реестр:** общий список (`data/lists/obshiy-spisok.json`) — реестр всех гипотез. Гипотезы из списков по проблемам дублируются в него автоматически: `scripts/sync_general.py` вызывается из `aggregate.py`, а его запускает и сервис при каждом сохранении. Копии помечаются `srcList`/`srcListTitle` (в интерфейсе — бейдж «из «…»»), правки защищены полем `upd` (копию не затрёт, если её правили позже источника).
1. **Собери контекст** (см. раздел выше): заметки → расшифровки → Jira → проблемная карта.
2. **Покажи формулировку проблемы** пользователю (коротко: что сломано, у кого, почему важно, постановка-источник).
3. **Сформируй 5–10 гипотез.** Разные механизмы, не перепевы одного; каждая — проверяемая.
4. **Запиши файл** `data/lists/problema-<слаг>.json` (слаг латиницей: `shapka-iikoweb`, `marketplace-orders`); у каждой новой гипотезы — `"by": "hermes"`. Если файл уже есть — дописывай, не перезаписывай; id новых гипотез — `h<номер>-<смысл>` (например `h2-multivybor`). Поле `list.problemNote` указывает на проблемную карту.
5. `cd /opt/data/iiko-product-process/02-hypotheses && python3 scripts/aggregate.py` — он же синхронизирует общий список.
6. `python3 scripts/build_prototype.py data/lists/problema-<слаг>.json` — HTML для файлового режима (в `build/`, в git не хранится).
7. Коммит локально (без пуша): `git add -A && git commit -m "Шаг 2: список гипотез по проблеме …"`. Публикует администратор.
8. **Дубль в папку задачи (обязательный шаг):** `python3 scripts/export_task_list.py <list_id> ARTIFACTS/<слаг>/02-гипотезы/список-гипотез.md` — читаемый слепок списка (формулировки, метрики, источники, ICE и баллы; сортировка по баллу). Обновлять при КАЖДОМ изменении списка: после своих правок и после правок из прототипа (пункт C). Если у задачи несколько списков — `список-гипотез-<id>.md`. Дубль руками не правим: источник истины — JSON списка.
9. **Отдай результат: ссылку на список + короткое резюме** — сколько гипотез, топ-3 по баллу, что требует уточнения (метрики без baseline, C ниже 4 → research). Новый список сразу виден в боковом меню прототипа.

### B. Гипотезы в общий список

Тот же порядок, файл `data/lists/obshiy-spisok.json`, `type: "general"`, поле `problem` пустое. Цели — из файла. Такие гипотезы живут только в общем списке (без `srcList`) и не дублируются.

### C. Правки, сделанные вручную в прототипе

Пользователь присылает JSON вида `{"action":"sync_hypotheses_list","data":{"list":{…},"goals":[…],"items":[…]}}`:

1. Проверить: у каждой гипотезы есть `name` с «если/тогда/так как», `metric`, `src`, `I`/`C`/`E` в 1..10, `goals` — не больше двух пар. Ошибки — сказать пользователю, не «дорисовывать» за него.
2. Определить файл по `data.list.id`: `obshiy-spisok` → общий список; иначе `problema-<id без префикса problema->.json`.
3. Записать файл, прогнать `aggregate.py` (синхронит общий список), при необходимости `build_prototype.py`, обновить дубль в задаче (`python3 scripts/export_task_list.py <list_id> ARTIFACTS/<слаг>/02-гипотезы/список-гипотез.md`), сохранить локально (коммит без пуша: публикует администратор).
4. Вернуть ссылку на список и строку изменений (было/стало гипотез).

### D. Правки интерфейса прототипа

1. Правим `prototype/ocenka-gipotez_kalkulyator.html` и копию рабочего файла агента `/opt/data/2026-09-29_ocenka-gipotez_kalkulyator.html` — держим их идентичными.
2. Проверяем в браузере **через сервис** (не только файлом): открыть `http://127.0.0.1:8330/?list=obshiy-spisok`, прокликать изменённый элемент, посмотреть консоль (ошибок JS быть не должно), при правках геометрии — измерить замером (`getBoundingClientRect`), а не «на глаз».
3. Собрать `build/` и убедиться, что файловый режим тоже работает.
4. Коммит делает агент: сервис коммитит **только** `02-hypotheses/data`, всё остальное (прототип, скрипты, docs, скилл) — вручную.

## Серверный режим

Если прототип открыт как веб-сервис (`python3 02-hypotheses/server/serve.py --port 8330`, страница вида `http://<хост>:8330/?list=<id>`), то:

- списки читаются и сохраняются сервером: правки пользователя уходят в `data/lists/*.json` автоматически (автосохранение ~1,5 с), сервис сам делает `aggregate.py` и локальный коммит — отдельная синхронизация через чат не нужна;
- закрытие вкладки не теряет правку: при закрытии/скрытии страницы изменение досылается (keepalive);
- шапка страницы закреплена при прокрутке (sticky) — кнопка «Спросить Hermes» и заголовок всегда под рукой;
- переключаться между списками можно в интерфейсе: кнопка-бургер в шапке слева от заголовка открывает боковое меню со всеми списками (общий и по проблемам), с числом гипотез и бейджем типа списка; текущий список подсвечен;
- у каждой гипотезы в таблице видно авторство: «🤖 Hermes» (предложил агент) или «✍️ вручную» (добавили в форме); у копий в общем списке ещё бейдж «из «…»». В CSV-экспорте авторство — отдельная колонка «автор»;
- создание нового списка — `POST /api/lists` (тело `{"title":"...","problem":"..."}`) или сразу файлом + `aggregate.py`; id делается из **названия** (латиницей, до 48 знаков, с префиксом `problema-`), а не из текста проблемы — так ссылки остаются короткими;
- если список по проблеме удалить, его копии в общем списке уходят при следующем `sync_general.py` (чистка по жив`source`м);
- **канал «сайт → Hermes»** (кнопка в шапке страницы): справа в шапке — кнопка «🤖 Спросить Hermes», по клику открывается поп-ап с подсказкой (что можно писать: дополнить список, переформулировать, пересчитать ICE, разобрать проблему), полем ввода и кнопками «Отправить Hermes» / «Закрыть». Кнопка видна только в серверном режиме; пока агент работает, она показывает «Hermes работает…». `POST /api/ask` с телом `{"list":"<id>","text":"<запрос до 2000 знаков>"}` запускает агента скилла в фоне и отдаёт `task` (202); статус — `GET /api/ask/<task>` → `running | done | error | timeout` и `message`. Один запрос за раз (второй получает 409), таймаут 15 мин. **Странице уходит последняя строка финального ответа агента** — поэтому ответ всегда заканчиваем одной строкой-итогом (сколько гипотез и о чём). После `done` страница сама перечитывает список. Прогон, запущенный так, — это обычная сессия агента: контекст собираем сами (в запросе продакта его нет);
- **кнопка «Создать задачу» (режим `task`)**: `POST /api/ask` c `mode:"task"` отправляет агенту серверный промпт `ASK_PROMPT_TASK` (`server/serve.py`) — создаётся ОДНА Story в PB по всем отмеченным гипотезам. **Описание задачи — требования: как реализовать отобранные гипотезы в рамках этой задачи; данные гипотез в описание не дублируются** (формулировки, метрики, источники, оценки I/C/E, баллы, цели с α остаются только на странице списка). Формат — шаг 3 (`pb-task-writer`): цель, AS-IS/TO-BE, требования, критерии приёмки, зависимости, out of scope. После создания ключ вписывается в поле `jira` каждой гипотезы, `aggregate.py`, коммит и пуш;
- если сервис не запущен, работает файловый режим (открыть/сохранить список, синхронизация через чат).

## Установка прототипа (сервис + канал в Hermes)

**Развёртывание на сервере сотрудника — одной командой:** `cd 02-hypotheses && bash install/install.sh --port 8330 [--auth логин:пароль]` — скрипт проверит зависимости, создаст каталоги данных и пустой общий список, настроит автоподъём (cron: каждые 15 минут + при загрузке), поднимет сервис, проверит его и напечатает ссылку. Полная инструкция, ручная установка (в т.ч. пример systemd-unit), доступ снаружи, переезд на другой сервер, диагностика и чек-лист — в `install/README.md`. Скрипты: `install/hypoproto_ensure.sh` (автоподъём, тихий), `install/hypoproto_restart.sh` (перезапуск).

Ниже — что именно делает установка на конкретной машине:

1. **Сервис:** `cd /opt/data/iiko-product-process/02-hypotheses && python3 server/serve.py --port 8330` — порт из диапазона `PROTO_PORT_RANGE=8330-8339`, он уже проброшен наружу: `http://<хост>:8330/?list=<id>` (рабочий адрес — `http://hermes.iiko.ru:8330/`, запасной — `http://10.10.8.10:8330/`).
2. **Автоподъём:** watchdog `/opt/data/scripts/hypoproto_ensure.sh` (cron `c5c3e550126c`, каждые 15 минут) поднимает сервис, если он упал, и коммитит правки списков; после правок `serve.py` сервис перезапускается скриптом `/opt/data/scripts/hypoproto_restart.sh` (код читается один раз при старте).
3. **Канал «сайт → Hermes»** (кнопка «Спросить Hermes» в шапке страницы): `POST /api/ask` с телом `{"list": "<id>", "text": "<запрос>"}` запускает агента в фоне, `GET /api/ask/<task>` отдаёт статус (`running | done | error | timeout`).
   - **Все запросы с сайта идут в один чат десктоп-клиента** — сессии не множатся. id чата лежит в файле `/opt/data/hypoproto-ask-session.txt`, название чата — «🤖 Сайт → Hermes (гипотезы)». Если файла нет, сервис при первом запросе создаёт сессию сам (`hermes chat -q … -Q`), находит её id в `state.db` и переименовывает; дальше каждый запрос продолжает её (`hermes chat -q … --resume <id>`).
   - Настройка — переменными окружения сервиса: `HERMES_ASK_SESSION_FILE` (где хранить id чата), `HERMES_ASK_SESSION_TITLE` (название чата), `HERMES_BIN` (путь к `hermes`), `HERMES_STATE_DB` (база сессий, если она не в `/opt/data/state.db`).
   - **Переключить чат:** удалить файл с id — следующий запрос создаст новый чат (и переименует его). **Продолжить вручную:** открыть этот чат в десктоп-клиенте и написать — агент ответит в том же контексте.
   - Один запрос за раз (второй получает 409), таймаут 15 минут, в чат уходит последняя строка ответа агента — поэтому ответ всегда завершаем одной строкой-итогом.

**Важно про встраивание данных:** в серверном и файловом режимах данные встраиваются в HTML **сразу после `<body>`, до скрипта приложения** (`window.__HYPOTHESES__`, `window.__SERVER__`, `window.__DASH__`). Если перенести вставку к `</body>`, прототип не увидит данные и покажет пустой черновик — этот якорь не ломать.

## Создание задачи из гипотез (кнопка «Создать задачу»)

Под таблицей есть кнопка **«Создать задачу»** (активна, когда отмечены гипотезы в колонке «в работу»). Продакт отмечает одну или несколько гипотез, нажимает кнопку — открывается подтверждение с готовым текстом запроса и кнопкой **«Создать задачу в Jira»**; запрос уходит в Hermes (`POST /api/ask`, `mode: "task"`), и по всему набору создаётся **одна** задача.

Как агент выполняет такой запрос:

1. **Одна задача на весь набор** — гипотезы не разбивать на разные задачи. Проект PB, тип Story.
2. Summary — по общему смыслу набора (длиннее ~120 знаков — сжать). Description — каждая гипотеза списком: формулировка, метрика (baseline → target), источник данных, оценка I/C/E, итоговый балл, цель с α; в конце — ссылка на инструмент и на файл списка.
3. После создания **вписать ключ задачи в поле `jira` каждой отобранной гипотезы** в `data/lists/<id>.json` (остальные поля не менять), прогнать `aggregate.py`, сохранить — ключ сам появится в колонке «Jira» при следующей загрузке страницы.
4. Если у кого-то из набора поле `jira` уже заполнено — не создавать дубль: сказать об этом и предложить дополнить существующую задачу.
5. Ответ в чат — одной строкой: ключ и ссылка задачи + одна фраза, о чём она.

## Правила

- Метрика без источника — законная, но пишем «уточнить»; C в этом случае не выше 6.
- Список живёт в двух местах: прототип (`data/lists/<id>.json`) — рабочий источник истины; `ARTIFACTS/<слаг>/02-гипотезы/список-гипотез.md` — читаемый дубль для задачи, чтобы все данные проекта читались из одной папки. Дубль только генерируется скриптом.
- Больше двух целей на гипотезу нельзя; веса целей назначает продуктовый офис, по ходу не меняем.
- Ничего не удаляем молча: удалённые гипотезы убираем из файла, но в commit-сообщении пишем, сколько удалено.
- Правки копий в общем списке и в источнике: поле `upd` защищает свежую правку копии, но правка источника перетирает копию. При конфликте — сначала спросить пользователя, где правда.

## Pitfalls

- `data/hypotheses.json` — производный файл, правки только через `aggregate.py`.
- `build/` в git не хранится (в `.gitignore`) — собранный HTML отдаём, только если сервис недоступен.
- Имена файлов в репозитории — латиницей; русские названия только внутри JSON.
- Общее правило `button{padding:9px 14px}` в прототипе сжимает кастомные иконочные кнопки: у кнопок-иконок ставим `padding:0` и несжимаемый внутренний элемент (`flex:0 0 16px`), а полоски-псевдоэлементы тянем `left:0;right:0` — иначе иконка выглядит смещённой (проверено на бургере 29.09).
- Сервис коммитит только `02-hypotheses/data` — не жди, что правки прототипа попадут в git сами.
- Прогон, запущенный по каналу «сайт → Hermes», идёт в живом сервисе: сервис сохраняет `data/` локальным коммитом (своё сообщение вида «Списки гипотез: … (N шт.)»), поэтому финальный `git add -A && git commit -m "Шаг 2: гипотезы из прототипа — …"` может ответить «nothing to commit». Это не ошибка: посмотри `git status -sb` и добери `git push`; прототип/сервис/скилл коммить отдельным коммитом со своим сообщением.
- Длинный ответ с вложением может не дойти до десктоп-клиента пользователя: результат отдаём коротким сообщением со ссылкой; если сообщение всё же пропало — восстановить текст из `state.db` и переслать.
